# Design decisions

## 1. Raymarching, no Three.js

**Decision**: the whole scene compiles to a single GLSL fragment shader, rendered by raymarching signed distance fields (WebGL2).
**Why**: no dependency, a tiny runtime, and organic shapes (smooth unions) that plain rasterization cannot do.
**Accepted limits**: no imported models (GLTF); the cost grows with the number of objects.
**Later**: a WGSL/WebGPU backend, made possible by an intermediate step separate from GLSL. (Done: decision 90.)

## 2. Structure lives in `@scene`, not in HTML

**Decision**: objects are declared in a `@scene { cube.corner * 4; }` block.
**Why**: one self-contained file, easy to share and easy for an LLM to generate. No web components.

## 3. Multiplied ids are numbered automatically

**Decision**: `torus#hero * 3` creates `hero-1`, `hero-2`, `hero-3`. Without a multiplier, the id stays `hero`.
**Why**: practical, never a blocking error, and every object stays targetable.

## 4. Specificity: id 10,000, class 100, tag 1

**Decision**: specificity is a single number with widely spaced weights.
**Why**: as in CSS, no realistic number of classes beats an id, and `#hero.big` beats `#hero`.
With equal specificity, the last rule in the file wins.

## 5. Everything that can be computed at compile time is

**Decision**: the cascade, selectors and units (`70deg` → radians) are resolved by the compiler.
The shader only receives final values.
**Why**: a simpler, faster shader; the GPU knows nothing about CSS.

## 6. JavaScript holds the state, the shader draws

**Decision**: the camera, time and, later, hover and transitions live in TypeScript
and are sent to the shader as uniforms on every frame.
**Why**: a shader has no memory from one frame to the next.
**Update**: `@keyframes` animations are the exception, see decision 21. They only depend on time, so the shader computes them from `iTime`.

## 7. One material number per object

**Decision**: each instance has its own number (its index in the scene), used by `getMaterial`.
**Why**: numbers are always consistent, and every object stays identifiable, which `:hover` will need.

## 8. The AST keeps raw values

**Decision**: the parser stores selectors and values as tokens, without interpreting them.
**Why**: the parser only understands structure; meaning is given later, by the cascade and code generation.

## 9. Angles always have a unit

**Decision**: angles accept `deg`, `rad` and `turn`. Only `0` is accepted without a unit.
**Why**: as in CSS. Without a unit, `1.5` could mean degrees or radians.

## 10. Behavior changes are explicit

**Decision**: any change to how the language behaves comes with an updated test and an entry in this file.
**Why**: the language must never change as a side effect of a code change.

## 11. `@scene` declares, `scene` styles

**Decision**: `@scene { }` declares which objects exist; the `scene { }` rule styles the scene itself (floor, background, and later lights and fog).
Only the exact selector `scene` targets the scene: `.scene`, `#scene` and `scene.big` do not.
**Why**: structure and appearance stay separate, and scene styles benefit from the cascade (`@media`, `var()`, animations).

## 12. Every property is registered

**Decision**: every GSS property is described once, in `src/compiler/registry/registry.ts`.
The compiler rejects unknown properties and properties used in the wrong place.
The reference documentation is generated from the registry, and every example is compiled by the tests.
**Why**: a feature cannot exist without its documentation, and typos are never silently ignored.

## 13. `scale` is uniform

**Decision**: `scale` takes a single positive number, applied on all three axes.
**Why**: a uniform scale keeps distances exact (the distance is multiplied back by the scale). A non-uniform scale would distort the distance field and cause rendering artifacts.

## 14. Shape-specific properties

**Decision**: some properties only apply to some shapes (`size` to `cube`, `radius` to `sphere` and `torus`).
Using one with an explicit, incompatible tag is an error (`sphere { size: 2; }`).
Through a class or an id, it applies to compatible shapes and is ignored by the others, as in CSS.
**Why**: clear errors when the intent is obviously wrong, without breaking classes shared by several shapes.

## 15. Property families share a prefix

**Decision**: related properties share a prefix (`camera-target`, `camera-distance`…), as in CSS (`border-width`, `border-color`).
The bare name (`camera`) is reserved for a future shorthand.
**Why**: families are easy to read and document, and shorthands stay possible without breaking existing files.

## 16. The compiler also returns runtime settings

**Decision**: `compileScene()` returns the shader and the settings the runtime needs (the starting camera).
`compileGSS()` stays a shortcut that only returns the shader.
**Why**: some values are starting points that the mouse then changes; they belong to the runtime, not to the shader.

## 17. Speeds are written as durations

**Decision**: `camera-spin` takes the duration of one full turn (`20s`, `500ms`) or `none`, not an angle per second.
**Why**: as in CSS (`animation-duration`), a duration reads naturally and uses units everyone already knows.

## 18. Operations apply in declaration order

**Decision**: `operation` combines an object with every object declared before it in `@scene` (union, subtract, intersect).
The floor is added last and is never affected. The walls of a hole take the material of the object that carves it.
**Why**: it reads like drawing, then erasing, and needs no grouping syntax yet.

## 19. blend smooths any operation

**Decision**: `blend: <distance>` turns the object's operation into its smooth version (Inigo Quilez's smooth union, subtraction and intersection). `blend: 0` keeps the sharp version.
**Limit**: in the blend zone, the color switches from one object to the other halfway, without a gradient.
**Why**: smooth blending is the signature of signed distance fields; no other web 3D tool offers it in one property.

## 20. Percentages are their own token

**Decision**: `50%` is a `PERCENTAGE` token, not a `DIMENSION` with the unit `%`. A `%` separated from its number (`50 %`) is an error.
**Why**: as in the CSS tokenizer. A percentage is not a unit like `deg`, and a distinct type prevents `50%` from ever reaching `readAngle` by mistake.

## 21. `@keyframes` animations are computed in the shader

**Decision**: `animation: float 2s` compiles to a GLSL expression that uses `iTime`, for example `mix(vec3(…), vec3(…), progress)`. Nothing changes in `main.ts`.
**Why**: a keyframes animation only depends on time, which the shader already receives. Everything else is resolved at compile time (decision 5).
**Accepted limits**: an animation cannot be paused, restarted or started on an event.
**Later**: `:hover` and `transition` depend on events, so they will go through JavaScript and uniforms (decision 6).

## 22. Keyframes follow the CSS rules

**Decision**:

- `from` means `0%` and `to` means `100%`. `0%, 100% { … }` sets both offsets.
- A missing `0%` or `100%` uses the object's own value (`translate`, `color`…).
- A frame only animates the properties it declares. A property that no frame declares keeps its own value.
- The same offset twice, or two `@keyframes` with the same name: the last one wins.
  **Why**: people and LLMs already know these rules from CSS.

## 23. Several keyframes make a chain of `mix`

**Decision**: each pair of neighbouring frames becomes one `mix()`, and each `mix()` takes over when the previous one ends. The timing function (`ease-in-out`) applies to each segment, not to the whole animation, as in CSS.
**Why**: one method works for any number of frames and for any value that `mix()` accepts (`float` or `vec3`).
**Accepted limits**: the progress expression is repeated in every segment, so the generated GLSL gets long. The GPU does not mind.

## 24. Animatable properties

**Decision**: `translate`, `rotate-x`, `rotate-y`, `rotate-z`, `scale` and `color` can be animated. The other properties keep their fixed value.
**Why**: they are the ones that already produce a GLSL `float` or `vec3`, so `mix()` works on them directly.

## 25. The test scene has one zone per feature

**Decision**: `src/scene.gss` groups features into zones, separated in the file and in space: transforms at the center, operations behind (z = -6), animations in front (z = 6). Every object has its own id.
**Why**: a shared scene quickly becomes chaotic. A rule like `cube { … }` or a reused id silently changes another feature's objects.

## 26. `material` and `color` stay separate

**Decision**: `color` keeps the base color of the object. `material` says how its surface reacts to light. A material without its own color uses `color`, like `currentColor` in CSS.
**Why**: `color` stays animatable with `@keyframes`, even on a metal. And `color: #ff5a36; material: gold;` keeps a single, readable meaning: the material's own color wins.
**Accepted limits**: `material` cannot be animated.

## 27. Materials are functions, keywords are shortcuts

**Decision**: a material is a function with its settings, like `rgb()` in CSS: `matte()`, `metal(#d4af37, 0.2)`. The color is optional and always comes first. Keywords (`gold`, `chrome`) are shortcuts written in GSS: the compiler tokenizes their text and reads it again as a function.
**Why**: functions hold the settings, keywords are easy to guess for people and LLMs. A keyword adds no code: its checks and errors are the ones of its function.

## 28. Function arguments follow modern CSS

**Decision**: `readFunction` splits arguments on commas when there are some, otherwise on spaces. `metal(#fff, 0.2)` and `metal(#fff 0.2)` are the same, like `rgb(255, 90, 54)` and `rgb(255 90 54)`.
**Later**: nested functions such as `calc(var(--x) / 2)` are not supported yet (session 3). Done: decision 55.

## 29. One bounce for reflections

**Decision**: a reflection is one more ray, marched by `trace()`. What it hits gets diffuse lighting only: a metal seen in another metal looks matte.
**Why**: each bounce costs a full march per pixel.
**Accepted limits**:

- Roughness does not blur the reflection. It mixes the sharp reflection with diffuse light, because a real blur needs dozens of rays per pixel.
- Metals get a bit of diffuse light (0.3) so they stay readable on a dark background. It is a visual choice, not physics.
- The reflected ray starts 0.01 above the surface, otherwise it hits its own starting point.

## 30. Shader structure: reusable functions, one placeholder each

**Decision**: the shader is split into functions that can be called again: `march()` follows a ray, `trace()` tells what a ray sees, `diffuse()` lights a surface, `getMaterial()` returns a `Material` struct (color, kind, roughness). Values the whole shader needs are constants at the top: `MAX_DIST`, `BACKGROUND`, `LIGHT_DIR`.
**Why**: reflections, and later refractions, reuse the same functions. And `.replace()` only replaces the first occurrence: every `/*@…*/` placeholder must appear exactly once in the template.

## 31. Glass: one refraction in, one out

**Decision**: … Frost has four styles, all driven by one amount: the normals are bumped with smooth noise (`noise()`, stuck to the surface), like a normal map in a 2D glass shader. `frostSettings()` holds the size and strength of the bumps for each style. `frosted` adds a white patchy layer (the default), `wavy` and `hammered` only distort, `blurred` also averages 4 rays in a fixed cross, adds a tint, light on the bumps and speckles. Written `glass(1.5, hammered 0.4)`, style and amount in any order.
**Why**: we compared six techniques side by side. Random jittered rays were grainy and shimmered; smooth noise stuck to the surface gives distortion without grain.
**Accepted limits**: glass seen through another glass object looks matte (decision 29). Each glass pixel costs three more marches, six with `blurred`.

## 32. Glass must not touch the floor

**Decision**: glass objects float slightly above the floor in the examples.
**Why**: when the bottom face of a glass object is exactly on the floor, both surfaces are at the same place and the ray exiting the object gets confused: the render shows stripes.
**Later**: exclude the floor from `marchInside()`.

## 33. Code style: one formatter decides

**Decision**: `formatGss` sets the style of every GSS file. One instance per line in `@scene`. Rules are always expanded, one declaration per line, indented with two spaces. One space after the `:` of a declaration and none before; the `:` of a selector stays stuck (`cube:nth-child`). No column alignment. Blank lines written by the author are kept, but never more than one, and top-level blocks are always separated by one. Values are written as the author wrote them (`2.0`, `#BADA55`). Comments are kept exactly as written, on their own line or at the end of a line.
**How**: the formatter works on the tokens of `scan()`, which keeps comments and the position of each token. Between two tokens it only decides the whitespace: a line break after `{`, `;` and `}`, otherwise one space where the source had some and nothing where tokens touch. So it cannot change the meaning, and a test checks it on every documented example and on `scene.gss`.
**Where**: one function, used everywhere: the docs examples, the playground, `npm run format` (and `format:check`), and the VS Code / Cursor extension, which bundles the same file.
**Why**: readable diffs, no style debates, and the same result in the docs, the playground and the editor.

## 34. The playground: index.html, CodeMirror, the code in the URL

**Decision**: `index.html` is the playground. The editor is CodeMirror 6, colored by our own `classifyGss()` (the same as the docs), not by a CodeMirror grammar. The code lives in the URL (`#code=` + deflate + base64url), so the address bar is always a share link; nothing goes to a server. An "Examples" menu lists the first scene, the test scene and every example of the registry. A GLSL tab shows the shader the code becomes, read-only.
**Errors**: compile errors are `GssError`s with a `start` and an `end` in the source. Tokens get their position in `scan()`, kept in a WeakMap so the AST does not change; readers throw with `errorAt(tokens, message)`, and `locate()` gives a position to errors thrown deeper. The editor underlines the span and says "Line 6, column 14".
**Why**: the playground is what people open from a link, so sharing comes first. A textarea could not grow into line numbers, error marks, undo and later autocomplete from the registry. Keeping one classifier keeps the colors identical in the docs and the editor. The GLSL tab is the "readable path toward the shader" of Getting started.
**Accepted limits**: errors that are not about a written value (an unknown shape in `@scene`, a GPU compile error) have no position yet, only a message. CodeMirror adds about 120 kB (gzip) to the playground and to the docs' "Try it".

## 35. Custom shapes: path, a tube along an SVG path

**Decision**: a `path` object follows `d: path("…")`, written like the `d` of an SVG path (and CSS `path()`): M, L, H, V, C, S, Q, T, Z, absolute and relative. `stroke-width` is the thickness of the tube, in path units, with round ends. `view-box: x y width height` works like an SVG viewBox: its center is the origin of the object, so paths copied from one SVG stay aligned. y is flipped, so a path copied from Figma or an SVG keeps its way up. One path unit is one scene unit: an icon needs a `scale`.
**How**: strings are a new token (`STRING`). At compile time, curves are cut into segments that never stray more than 1/100 of the stroke width from the curve (fewer segments on gentle curves). Each path becomes a GLSL function written segment by segment (no array, no loop: much faster), with segments grouped by 8 behind a bounding box test, and the whole path behind its own box. Objects sharing the same path share the function.
**Why**: SVG paths are what front-end developers already copy from their design tools, and a tube is enough for icons and logos (the GSS logo is drawn in GSS: `src/playground/logo.gss`).
**Accepted limits**: no arcs (A) at first (they came with decision 49), no filled shapes (fill + extrusion comes later). A path costs more than a sphere: the logo renders about 10 times slower than the same scene with spheres in software rendering. Up to 512 segments per path.

## 36. Dimensions are full sizes, shapes are centered

**Decision**: every dimension a shape reads is a full size, and every shape is centered on its origin, like `size` for the cube. `height: 2` goes from y = -1 to y = 1 around the object's `translate`. The compiler halves the value before writing the GLSL, because Inigo Quilez's distance functions expect half sizes (`sdCylinder(q, 1.0, r)` for `height: 2`). `radius` stays a radius, as its name says.
**Why**: in CSS, `width` and `height` are full sizes; nobody writes half a height. Keeping one rule for every shape means a reader never has to know how a GLSL function counts. Centered shapes rotate and scale around their middle, which is what `rotate-*` and `scale` already do for cubes, spheres and tori.
**Accepted limits**: a shape does not stand on the floor at `translate: 0 0 0`: its y must be half its height (`translate: 0 1 0` for `height: 2`). A `transform-origin` could change that later.

## 37. The universal selector \*

**Decision**: `*` targets every object of the scene, never the `scene` settings. Its specificity is 0, as in CSS: a tag (1), a class (100) or an id (10000) always beats it, wherever it is written. `*` can only start a selector and can be followed by classes or an id: `*.big` is the same as `.big`. In the compiler, `*` is a selector with no tag, no id and no class, which `matches()` already accepted for every object: `parseSelector` only learns to read it.
**Why**: CSS does the same, so every front-end developer (and every LLM) already knows what it means. It gives one place for scene-wide defaults (`* { material: matte(); }`) and is needed later for `@media (prefers-reduced-motion) { * { animation: none; } }`.
**Accepted limits**: the cascade picks one value, it never combines them: `* { scale: 0.5; }` only changes the objects that have no `scale` of their own, and a `path.logo { scale: 0.1; }` keeps 0.1. `scale` also shrinks each object around its own center, so `* { scale: 0.5; }` makes objects smaller but does not bring them closer: to shrink the whole scene, positions included, use a scene-level scale.

## 38. !important: two passes in the cascade

**Decision**: a declaration ending with `!important` wins against every declaration without it, whatever their selectors. Between two `!important` declarations, specificity decides again, then the order of the file. The parser takes `! important` out of the value and marks the declaration (`important: true`, a field normal declarations do not have). `resolveStyles` walks the sorted rules twice: first the normal declarations, then the `!important` ones, which overwrite them. A `!` not followed by `important` is an error.
**Why**: CSS does the same, so front-end developers and LLMs already know it. It is the classic tool for accessibility overrides: `@media (prefers-reduced-motion) { * { animation: none !important; } }`. Two passes keep the sort by specificity untouched: `!important` is a second cascade on top of the first.
**Accepted limits**: the cascade still picks one value and never combines them: `* { scale: 0.5 !important; }` gives every object a scale of 0.5, it does not halve their own (the logo, scaled 0.1, becomes 5 times bigger). In `@keyframes` and in `scene { }`, `!important` is read but has no effect: the declaration counts as a normal one (CSS ignores `!important` declarations in keyframes). An animation still beats an `!important` value, where CSS would let `!important` win.

## 39. Selectors and shapes are documented from the registry

**Decision**: the docs have two new sections, generated like the others: "Selectors and cascade" (`SELECTORS`: `<shape>`, `.class`, `#id`, `*`, `a, b`, `!important`, each with its specificity) and "Shapes" (`SHAPE_DOCS`: one entry per shape, with a description and its default dimensions). A shape does not list its own properties: `renderShape` finds them in `PROPERTIES` through `appliesTo`. `codegen.ts` exports `shapeNames()`, and a test checks that `SHAPE_DOCS` documents exactly those shapes. Selector anchors are written by hand (`selector-universal`), shape anchors are prefixed (`shape-cone`).
**Why**: selectors and the cascade are the heart of "the CSS of the 3D web", and they were documented nowhere. The registry stays the single source (decision 12): every example compiles on the CPU and on the GPU, and a new shape cannot ship without its entry. Reading the properties from `appliesTo` means a new shape property shows up on its shape without touching the docs. A name like `*` or `.class` cannot be an HTML id or a CSS timeline name, hence the anchors.
**Accepted limits**: the specificity of a selector is written as text, not computed by `specificity()`: nothing checks they agree. Descriptions are plain text (escaped), so they cannot link to another section.

## 40. plane: a finite, flat, thin box

**Decision**: `plane` is a finite rectangle lying flat in the xz plane, centered on its origin, 1 × 1 by default. `size` takes one value (a square) or two (width and depth), as full sizes (decision 36). It is drawn with `sdRoundBox`, a fixed thickness of 0.02 and no rounded corners: no new GLSL function. `rotate-x: 90deg` stands it up like a wall.
**Why**: a flat surface to place and style (a mat, a wall, a card, a shelf) is what a front-end developer expects from the word, like a div in 3D. An infinite plane would duplicate the floor; as a cutting tool, it can come later under another name. A surface with no thickness would be jumped over by the ray and flicker.
**Accepted limits**: the thickness cannot be changed. A plane lying on the floor needs `translate: 0 0.01 0`, half its thickness.

## 41. prism: a polygon(), filled and given a depth

**Decision**: `prism` fills a contour and gives it a depth. The contour is `d: polygon(x y, x y, …)`, written like CSS `clip-path: polygon()`: commas between points, at least 3 points, the polygon closes itself. It follows the rules of `path` (decision 35): the prism stands in the xy plane facing the camera, is centered on its polygon or its `view-box`, and y is flipped so a polygon copied from SVG or CSS keeps its way up. `depth` is its full thickness along z, 0.2 by default (decision 36). `readPolygon` (values.ts) returns `null` when the value is not a `polygon()`, so `d` can later accept `path()` too.
**How**: `polygonFunction` (path.ts) writes one GLSL function per polygon, side by side, with no array and no loop: `segment2()` gives the distance to each side, and `crosses()` flips a sign each time a horizontal line from the point crosses a side (an odd count means inside). `extrude()` turns the signed 2D distance into a 3D one. Objects sharing the same polygon share the function (`useFunction`).
**Why**: `polygon()` is known by every front-end developer and every LLM, and it gives stars, arrows and letters with a few points. A real triangle mesh would cost one distance per triangle at every step of every ray: too slow beyond a few dozen triangles. The word "mesh" stays out of the language: `prism` says what it does, like `lathe` later.
**Accepted limits**: no `path()` contour at first, so no curves and no holes (both came with decision 50), no bevel. The cost grows with the number of sides.

## 42. The status bar shows real numbers from the compiler

**Decision**: the playground ends with a status bar (DESIGN.md § 6): `ok · 3 objects · glsl 412 lines · compiled in 4 ms`, then the frame rate on the right; after an error, only `1 error`. `compileScene` also returns `objects`, the number of instances (like the camera settings, decision 16); `renderer.load` returns the whole `CompiledScene`, and `renderer.sampleFrames()` gives the images drawn since its previous call. The texts come from pure functions in `runtime/status.ts` (`plural`, `statusParts`, `fpsText`), tested without a browser. The editor reports the numbers through `onStats`; its `status` badge becomes optional (the docs keep it).
**Why**: "honest numbers" is a rule of the design language, and these ones teach what GSS does: the GLSL line count grows with the scene, the compile time stays short. The object count is known only inside the compiler, hence the extra field.
**Accepted limits**: the compile time includes the GPU program creation (it is what the user waits for). A compile stops at the first error, so the count is always 1 for now.

## 43. A located error is written under its line

**Decision**: when a `GssError` knows its position, the editor underlines it (as before) and inserts a block under its line: `15:3  "height" only applies to …`, on the signal wash with a 2px signal rule. It is a CodeMirror block widget kept in a `StateField` (block widgets change the height of the document, which a view plugin may not do); it follows the text while typing and disappears at the next successful compile. An error with no position (a GLSL error) is still shown under the editor.
**Why**: the error sits where the eye already is, as in the design reference (`design/reference/png/02-playground.png`). line:column is the format of every compiler and of our own errors.
**Accepted limits**: one error line at a time, like one compile error at a time.

## 44. The docs show one entry per page

**Decision**: the reference is still generated as one HTML page (`renderDocs`), but `docs/pages.ts` shows one entry at a time, chosen by the hash: `#material` shows `material`, `#material--example-2` scrolls to its second example, a section (`#shapes`) opens at its first entry, anything else at the very first one (`resolvePage`). The layout follows `design/reference/png/03-docs.png`: the contents on the left (the current entry marked with `aria-current`), the entry in the middle with a breadcrumb and previous / next links (`neighbors`, across sections), "On this page" on the right (the value table, each example, and a link that opens the first example in the playground). The contents fold away on a small screen.
**Why**: one long page buried each entry among fifty others, and the design reference is a page per entry, like MDN. Keeping the whole reference in the HTML means every existing link (`#material`, `#object-properties`) still works, the tests of `render.ts` are unchanged, and the change of page is instant.
**Accepted limits**: "find in page" only searches the entry on screen. The highlight of what is being read (view timelines) is gone: with one entry on screen, `aria-current` says it. An open "Try it" is closed when the page changes (one WebGL canvas at a time).

## 45. group: a node that holds other objects

**Decision**: `@scene` becomes a tree. `group#letters { cube#L; cube#U }` holds objects, and groups can be nested. A group is written like any object (`group`, `#id`, `.class`, `* N`), so it is styled with the selectors and the cascade we already have: `#letters { translate: -6 1 0; }`, like an SVG `<g id="letters">`. Only `group` may have children; `cube#a { … }` is an error pointed at `cube`. `group#g * 2` duplicates the whole group (`g-1`, `g-2`). `expandScene` flattens the tree: it outputs only the drawn objects, numbered from 1 across the whole scene; a group never takes an index, and each object keeps the list of its groups, from the outermost to the innermost.
**Why**: moving five letters meant editing five `translate`s. A group gives one place to move, turn or scale them together, and each child's position becomes relative to the group. The first idea, `[letters] { … }` then `letters { … }`, was dropped: in CSS `[…]` is an attribute selector, and a bare name would collide with type selectors (`cube { }`): a group called `cube` would be ambiguous.
**Accepted limits**: styles and transforms of groups are not applied yet (resolve and codegen come next). The descendant combinator came right after (decision 47); no child combinator (`>`) yet.

## 46. The ";" is optional between @scene elements

**Decision**: inside `@scene` (and a group), the `;` after an element may be left out: a new element or a `}` is enough to end it. Inside a rule, the `;` stays required between declarations (still optional before `}`).
**Why**: one object per line reads like a list, and the grammar needs no newline to know where an element ends: after `cube#a.big * 2`, only `;`, `}`, `{` or a new name can follow. In declarations, a value can span lines (`path("…")`, `polygon(…)`), so a newline cannot mean "end".
**Accepted limits**: `cube#a torus#b` on one line is accepted too; the formatter puts one element per line.

## 47. The descendant combinator: a space means "inside"

**Decision**: `#letters #S #left` targets `#left` when it is inside the group `#S`, itself inside `#letters`, at any depth. `parseSelector` returns the last compound (the object) with its `ancestors`, from the outermost to the innermost. `matches` reads them from right to left, like a browser: each ancestor must match one of the instance's `groups`, further out each time. The specificity adds up all the parts, like CSS: `#g #c` beats `#c`. Two ids in one compound (`#letters#S`) are an error, in a rule as in `@scene`: an object has only one id, and the old parser kept the last one silently.
**How**: the tokenizer skips spaces, so `parseSelector` finds them back with the positions of the tokens (`spanOf`): a gap between two tokens starts a new compound. No new token, so no test of the tokenizer changes. The formatter keeps one space in a descendant selector, and now also starts a new line for every element of `@scene` or a group, with or without `;` (decision 46).
**Why**: styling "every cube of the letters" or "the left bar of the S" without an id on each object is what groups are for, and every CSS developer reads a space this way.
**Accepted limits**: no child combinator (`>`), no sibling combinators (`+`, `~`). A comment between two parts of a selector counts as a space. A selector made in code (without positions) is read as one compound.

## 48. group is documented next to the shapes

**Decision**: `group` has its own entry in the Shapes section of the docs, even though it draws nothing: that is where a reader looks for what can be written in `@scene`. `ShapeDef` gets an optional `takes`, the only properties that have an effect (translate, the rotations, scale and animation); the page lists them instead of "every object property". The test that compares the documented shapes with the compiler's now expects `group` on top of them. `@scene`, translate, the rotations, scale, animation and the `<shape>` selector say what they do on a group, and `@scene` has an example with a group.
**Why**: every feature gets its entry as soon as it exists (decision 12), and a group without docs is a group nobody finds.
**Accepted limits**: a property a group does not take (`color: red` on `#letters`) is silently ignored; an error or a warning would be better.

## 49. Arcs (A) in paths

**Decision**: `d: path()` accepts `A rx ry rotation large-arc sweep x y` and `a`, like SVG. Like SVG, radii too small to reach the end point are scaled up, a radius of 0 draws a straight line, an arc to its own start draws nothing, and the two flags may be glued (`a1 1 0 011 0` in minified SVG). A flag other than 0 or 1 is an error.
**How**: `arcCenter` turns the two points and the radii into a center, a start angle and a turn, with the conversion of the SVG spec (appendix B.2.4). The arc is then cut into segments like the curves, with the same flatness bound (curvature at most r × turn²), and its last point is the end point itself, so rounding never leaves a gap. No Bézier on the way.
**Why**: arcs are everywhere in icons exported from Figma or Illustrator (circles, rounded corners), and the error asked people to redraw them by hand.
**Accepted limits**: none left for prisms: decision 50 gave them `path()` contours, arcs included.

## 50. A prism accepts a path(): filled contours, with holes

**Decision**: `d` on a prism takes a `polygon()` or a `path("…")`. Every subpath of the path is a contour, closed even without `Z`, and all of them are filled together with the even-odd rule: a contour inside another one is a hole (the inside of an "o", the counter of an "a"). A logo exported as an SVG path becomes a solid object with `prism` instead of a wire with `path`.
**How**: `readPrismD` returns contours (one for a polygon); `polygonFunction` takes them all. The curves of a path are cut with a precision that follows the size of the shape (a thousandth of its width plus height), so a logo 400 units wide is as smooth, relative to its size, as a shape 2 units wide. Sides are grouped by 8 like the segments of a path: a group is skipped for the distance when its box is further than the nearest side found, and for the inside test when the horizontal line through the point does not cross its height. Far from the whole shape, the distance to its box is returned at once.
**Why**: logos and text are shapes, not lines, and the tube of `path` draws only their outline. The even-odd rule is the one the crossing test already used, so holes cost nothing more.
**Accepted limits**: SVG fills with the nonzero rule by default: a path drawn with overlapping contours in the same direction can show holes that the SVG does not. A detailed logo is heavy: the "Lucas" logo is 400 sides, fine on a GPU, very slow in software rendering.

## 52. calc(), sibling-index() and the CSS math functions, computed at compile time

**Decision**: loops are written the CSS way: `* n` makes the copies, and `sibling-index()` in `calc()` tells them apart, like in CSS: `@scene { cube.petal * 12; } .petal { rotate-y: calc(sibling-index() * 30deg); }`. GSS knows `calc()`, `sibling-index()`, `sibling-count()`, `sin()`, `cos()`, `tan()`, `min()`, `max()`, `clamp()`, `abs()`, `sqrt()`, `pow()` and the constants `pi` and `e`, in any value, even inside another function (`metal(#fff, calc(0.1 * 2))`). `calc.ts` computes them after the cascade, once per object (`compileScene`), and puts back a plain NUMBER, DIMENSION or PERCENTAGE token that keeps the position of the whole call: the rest of the compiler is unchanged. Units follow CSS: + and - need the same unit (angles are brought back to deg, durations to s), _ needs a plain number on one side, / by a plain number keeps the unit, and dividing two angles gives a number. + and - need spaces, like CSS. Siblings are the objects of the same @scene block or group, a group included, counted one by one after `_ n` (`expandScene`: `siblingIndex`, `siblingCount`). The functions are documented in the registry (`FUNCTIONS`, a "Values and math" section), and a test checks that every function of `calc.ts`is documented.
**Why**:`sibling-index()`, `sibling-count()`and the math functions are real CSS: LLMs and front-end developers already write them, and "when a notion exists in CSS, we take its syntax". One rule replaces a loop, which is the point of "Rules, not loops". Sass-like`@for` would need its own variables, interpolation (`#{$i}`) and math anyway, for a syntax that is not CSS. Everything is known at compile time, so the GPU only receives numbers: math costs nothing when drawing.
**Accepted limits**: `var()` came later (decision 55). No unary minus before a function (`-sibling-index()`is read as one name): write`calc(-1 _ sibling-index())`. `sibling-index()`has no meaning in`scene { }`and in`@keyframes`, shared by every object: an error says so. A math value cannot be animated per object, except in a `@keyframes`that uses variables, which is copied per object (decision 55).`@for`/`@each`may come later for what`_ n` cannot do: a different shape at each step, or a list of values.

## 53. The shader only contains what the scene uses

**Decision**: the GLSL of a scene holds only the functions it calls. The shapes (`sdSphere`…), the helpers of `path` and `prism` (`segment2`, `box2`, `crosses`, `extrude`), the rotation and the operations other than union (`rot`, `opS`, `opI`, `opSmooth*`), the materials other than matte (`metal()`, `jelly()`, `glass()` with their constants) and their lighting (`shadeMetal`, `shadeJelly`, `shadeGlass` and what they call: `trace`, `fresnel`, `thickness`, `noise`…) each go in only when needed. What always stays is the raymarcher itself: `map`, `getMaterial`, `matte()`, `opU` (the floor uses it), `march`, `calcNormal`, `diffuse`, `main`. An empty scene went from 418 lines to 104.
**How**: each family of functions is a table in `codegen.ts` (`SHAPE_FUNCTIONS`, `PATH_HELPERS`, `MAP_HELPERS`, `MATERIALS`, `SHADING`), cut out of the template word for word. `used(table, code)` keeps the functions whose `name(` appears in the generated code, then looks again in the functions it kept, until nothing new comes up: `shadeGlass` brings `noise`, which brings `hash3`. It returns them in the order of the table, which is the order of the template, so each function comes after those it calls, as GLSL requires. Each table is searched in the right code: the shapes and the operations in `map()`, the path helpers in the generated path and prism functions, the materials in `getMaterial()`, the lighting in the lines `if (m.kind == …)` of `main()`, themselves written only for the materials the scene uses. The frost styles, `FROSTED` included, come with `glass()`; `matte()`, `metal()` and `jelly()` pass `0` as `frostStyle`, which only glass reads. The output is tidy: a section comment is written only when its section has something (`section()`), a hole at the end of a line leaves no blank line (`moreLines()`), and runs of blank lines become one.
**Why**: the GPU compiles every function it receives, so a shader full of unused code is slower to start, and the GLSL tab of the playground showed 400 lines for an empty file. Reading the generated code, instead of having every shape and material declare what it needs, cannot forget a dependency: `plane` gets `sdRoundBox` because it calls it.
**Accepted limits**: a function is found by its name followed by `(`, so a table must not hold a name that ends another one: with `box` and `sdbox`, a call to `sdbox(` would bring `box` too. The constant `MATTE` stays for readability: a `const int` costs nothing on the GPU.
**Rejected**: normals from 4 samples (a tetrahedron) instead of 6 (central differences). It saves 2 calls to `map()` per pixel against dozens in `march`, a few percent at most, and it is less precise: its error grows with the curvature (about e × curvature, against e² for central differences), which could show in the sharp reflections of metal and in glass.

## 54. The camera does not spin by default

**Decision**: without `camera-spin`, the camera stays still (`none`); `readSpin` returns 0 instead of 0.3 radian per second (a turn in about 21 s). The registry says `initial: none`.
**Why**: a scene stays where its author put it; the camera moves when the author asks for it (`camera-spin: 20s`) or with the mouse. The registry said `21s` and the compiler turned at 0.3 radian per second; both now say `none`.
**Accepted limits**: the examples of the docs without `camera-spin` no longer turn; `scene.gss` sets `camera-spin: 100s` itself.

## 55. Custom properties and var(), inherited and animatable

**Decision**: a property whose name starts with `--` is a variable, valid on the scene, on groups and on objects, and in `@keyframes` frames: `validate.ts` lets it through without looking it up in the registry. `var(--name)` and `var(--name, fallback)` read it, like CSS. Variables are inherited: the scene plays `:root`, then each group from the outside in, then the object; the closest level wins (`compileScene`: `levels`, `seenAt`). `vars.ts` replaces every `var()` by tokens (`resolveVars`), after the cascade and before the math, so `calc(var(--x) * 2)` works and the rest of the compiler never sees a `var()`: `computeVars` also drops the `--` properties before codegen. A variable can use another one (`--big: calc(var(--size) * 2)`): its value is resolved in turn, with the chain of variables being resolved, so a loop is an error that shows it (`--a uses itself: --a → --b → --a`). The fallback is only read when it is used, like CSS: `var(--size, var(--nope))` is fine when `--size` exists. A frame can set a variable: every animatable property of the object that uses it, directly or through another variable (`usesVariables`), moves with it. A `@keyframes` that sets or reads a variable cannot be shared, since its values depend on the object: `animateVariables` makes a copy for each object that plays it, with plain values, under a name no file can write (`up (copy 3)`), and the object plays that copy. `var` is documented with the functions (`FUNCTIONS`, `fn-var`), and the highlighter gives `--name` its own color (`gss-variable`).
**Why**: custom properties are real CSS, the first thing a front-end developer reaches for to share a value. Replacing them at compile time keeps decision 52's promise: the GPU only receives numbers. Copying the `@keyframes` per object keeps codegen unchanged, and costs nothing on the GPU, where each animated value is already written inline. It also lifts a limit of decision 52 for these frames: their math runs per object, so `sibling-index()` works in a frame that uses variables.
**Differences with CSS**: a missing variable without fallback is an error, not an invalid declaration silently dropped (decision 12). A variable that uses another one is resolved where it is used, not where it is declared: with `scene { --big: calc(var(--size) * 2); }` and `#g { --size: 5; }`, the objects of `#g` get 10, where CSS would give the value computed on the root. An animated variable moves the values that use it smoothly, as if it were a registered `@property`; in CSS, an unregistered variable flips at the middle of the step.
**Accepted limits**: a property that cannot be animated (`radius`…) and uses an animated variable is an error that names both. The variables of the scene and of `@keyframes` without an object are not animated: `scene { }` plays no animation. `@property` (typed variables) is not supported.

## 58. rgb(), hsl() and the named colors, turned into hex at compile time

**Decision**: `colors.ts` turns `rgb()`, `rgba()`, `hsl()` and `hsla()` into a plain `#rrggbb` token (`resolveColors`), with the modern syntax (spaces) and the old one (commas). `rgb()` takes numbers from 0 to 255 or percentages, clamped; `hsl()` takes a hue as a number of degrees or in `deg`, `rad`, `turn`, wrapped around the circle (-120 is 240), and a saturation and a lightness as percentages or numbers. The 148 named colors of CSS Color 4 (`named-colors.ts`) become hex too, but only where a color is expected (`resolveNamedColors`): `color`, `floor`, `background`, and the first argument of a material (`metal(tomato, 0.2)`). This pass runs after the math, on objects, groups, the scene and `@keyframes` (`colorsOf`, `computeColors`), so the pipeline is: `var()` → math → colors → codegen, and `hsl(calc(sibling-index() * 45) var(--s) 50%)` works with no special case. `readColor` and the rest of codegen are unchanged: they only ever see a HASH token. `rgb()` and `hsl()` are documented with the functions (`fn-rgb`, `fn-hsl`); a test checks that `COLOR_FUNCTIONS` is documented.
**Why**: `rgb()`, `hsl()` and `tomato` are what a CSS developer writes without thinking. Converting them at compile time keeps the GPU receiving numbers only, like decision 52 and 55. Each pass does one thing and trusts the previous ones: the colors never need to know about variables or siblings.
**Named colors only where a color is expected**: `gold` is both a CSS color (`#ffd700`) and a GSS material (`material: gold`, decision 27). Replacing names everywhere would turn the material into a color, and every future GSS keyword could clash with one of 148 names. The property decides, like CSS, where `red` means a color in `color` but an animation name in `animation`.
**Accepted limits**: no alpha: `rgb(255 0 0 / 50%)` is an error ("GSS has no transparency yet"), not silently ignored (decision 12). No `transparent` and no `currentcolor`. An unknown name (`tomatoe`) is left alone and reported by `readColor`. A color written as a hex keeps 8 bits per channel: `rgb(127.5 0 0)` is rounded. `oklch()`, `oklab()`, `lab()`, `lch()`, `hwb()`, `color()` and `color-mix()` come later.

## 59. Textures: images projected on the faces of the object, a face styled like a pseudo-element

**Decision**: `texture: url("dirt.png")` paints an image on an object. SDF shapes have no UVs, so the image is projected along the normal (triplanar mapping, dominant axis): the point and the normal are moved into the object's space with the same lines as `map()` (`spaceN()`), so the image moves, turns and scales with the object, groups included. By default one image covers one face (the size of the cube, the diameter of the sphere); `texture-size` sets the size of one image in the object's units, and `fract()` repeats it, like `background-size`. The image is painted over the color by its alpha, like `background-image` over `background-color`: an image that is not loaded yet (one transparent pixel) or a transparent pixel of a PNG shows the object's `color`. `image-rendering: pixelated` (or `crisp-edges`) reads the center of the nearest pixel (`textureSize`), per object, in the shader; the texture itself stays smooth on the GPU, so one image used pixelated and smooth is still one texture. One face is styled with a pseudo-element, like `::part()` in CSS: `::face(top)`, `bottom`, `front` (+z), `back`, `left`, `right` (+x is right), in the object's space; `::top` and `::bottom` are shortcuts, for the faces a Minecraft-style block changes most. A face rule counts like a tag in the specificity, only takes `texture`, and closes the selector. Each object gets `faceStyles` from the same cascade, with only the rules of that face, and they go through `var()` with the object's variables. A face without a rule of its own shows the object's texture.
**How**: the compiler lists every image once, the object's first, then its faces in the order of `FACES` (`sceneTextures`, at most 16: the texture units WebGL2 guarantees), and gives each one a `uniform sampler2D uTextureN`. `textureColor()` picks the image of the object by its id and, when a face has its own, the face by `faceOf()`, which runs the same tests as `triplanar()` so a face and its projection always agree. `faceOf()` goes in only when a face has its own image (decision 53). The renderer keeps one texture per file (`createTextureStore`), shared by every scene it loads, so typing in the playground does not download an image again, and binds image N to texture unit N each frame.
**Why**: textures were asked for to redo a Minecraft dirt block, then a grass block. `url()`, `image-rendering` and pseudo-elements are CSS, so a front-end developer (or an LLM) writes them without learning anything. Numbered sides (`::side(1)`) were rejected: which one is 1 would have to be learned by heart; the names of `border-top`, `border-left`… need no explanation. Pixelated in the shader rather than on the texture keeps the choice per object, like CSS, with no second copy of an image.
**This lifts part of decision 1**: "no textures, everything is computed" is no longer true for objects that ask for an image; the rest of the rendering is unchanged.
**Accepted limits**: a round shape is cut like the cube around it: a sphere shows six regions with seams, the image stretched near their edges (a soft blend, or a spherical mapping with `texture-mapping`, may come later). The images of −x, −z and the bottom are mirrored, invisible on dirt, visible on text. Reflections and glass see an object's color, not its image (`trace()` does not call `textureColor()`). `image-rendering` is set on the object, not per face. `url("…")` needs quotes; images come from URLs only (no drag and drop in the playground, and a share link does not carry them); an image from another site needs CORS. No atlas: one file per image.

## 60. The Shadertoy export plugs the images into Shadertoy's channels

**Decision**: `toShadertoy()` removes our `uniform` lines (Shadertoy writes its own), so a scene with textures lost the declaration of `uTextureN`, and the export no longer compiled. The export now adds `#define uTexture0 iChannel0`, one line per image (`channelDefines`), under a comment that says which channel holds which image. A scene with more than 4 images is refused with a clear error ("Shadertoy has 4 image channels, this scene uses N images"), shown for a few seconds on the `→ shadertoy` button. The GPU test wraps the export in a header that declares `iChannel0`…`iChannel3`, like Shadertoy does.
**Why**: Shadertoy cannot receive our PNG files: its 4 channels are filled by hand from its own library. An empty channel reads as transparent, and `triplanar()` mixes the image over the color by its alpha (decision 59), so a textured object falls back to its `color` with no special case: the export works as is, and anyone can put an image in the channel afterwards. Removing the textures, or refusing the export, would have been more code for a worse result.
**Accepted limits**: at most 4 images in an exported scene. The channels are not filled with our images; the user picks them in Shadertoy.

## 62. :hover: a second cascade, uHover[] in the shader, a picking pass in the renderer

**Decision**: `:hover` is a pseudo-class, read anywhere after the tag (`cube:hover.big`) and on the groups of a descendant selector (`#letters:hover cube`). It counts 100 in the specificity, like a class, as in CSS. It works in four steps:

1. **Triggers** (`resolve.ts`): for each object, the objects that, hovered, put it in its hover state (`hoverTriggers`, ids from 1). `cube:hover` → the object itself; `#g:hover cube` → every object of `#g`, nested groups included, like hovering a child hovers its parent in CSS. Several `:hover` in one selector must all be true: the sets are intersected. Several rules add up.
2. **Hover styles** (`resolve.ts`, `index.ts`): a second cascade, with the `:hover` rules this time (`hoverStyles`). The normal cascade skips them. `:hover` rules follow the specificity (`#a` beats `cube:hover`) and `!important` like any other, and go through `var()`, the math and the colors with the object's variables (`cube:hover { --c: red; }`).
3. **Shader** (`codegen.ts`): each object with triggers gets a slot in `uniform float uHover[N]`, 0 at rest, 1 hovered. Every animatable property that `:hover` changes becomes `mix(rest, hovered, uHover[slot])`, on top of `@keyframes` (`hoverValue` wraps `animatedValue`), in `map()`, `getMaterial()` and the texture spaces. Only the object's own node is mixed, never its groups. A scene without `:hover` gets exactly the same shader as before.
4. **Picking** (`renderer.ts`, `runtime/hover.ts`): each frame, when the scene has slots and the mouse is over the canvas, the same shader is drawn on a 1 × 1 framebuffer with `uPicking` on: it aims at the mouse pixel (`uPick`) and writes the id it hits right after `march()`, before any lighting (red + 256 × green, 0 for the floor and the background). `readPixels` reads it back, `hoverValues` turns it into `uHover[]`, then the real frame is drawn. `pointerleave` clears the hover.
   **Why**: slots rather than ids: a scene of 50 objects where 3 react sends 3 floats, not 51 (a `uniform float[]` costs one vector slot per value). A number from 0 to 1 rather than a boolean: `transition` will only make JavaScript slide it, the shader will not change. GPU picking rather than raymarching the mouse ray on the CPU: `map()` only exists in GLSL, and the same shader cannot disagree with what is on screen. Triggers resolved at compile time, like the rest of the cascade (decision 5): at run time, the renderer only compares one id with a list.
   **Shadertoy** (decision 60): no picking there. `uHover` becomes a constant array of zeros and `uPicking` / `uPick` constants: every object stays at rest.
   **Accepted limits**: an object has one hover state: two `:hover` rules with different triggers (`cube:hover` and `#g:hover cube`) both apply as soon as either one is triggered. A `:hover` rule cannot style a group (`#g:hover { translate: … }` is an error: write `#g:hover cube`), nor a face (`cube:hover::top`). Only the animatable properties (decision 24) and variables can change. The change is instant until `transition`. `readPixels` waits for the GPU once per frame; if it shows on large scenes, pick only when the mouse or the scene moves (since decision 65, the pixel is read without waiting). On a touch screen the object stays hovered after the touch, like mobile browsers. No `cursor` yet. `:has()` comes next, as more triggers: `#g:has(sphere:hover) cube` → the spheres of `#g`.

## 63. Embedding: <gss-scene>, mount() and a Vite plugin, on a runtime without the compiler

**Decision**: a GSS scene can be embedded in any page, three ways, one per audience:

- **Designers**, no build step: `<script type="module" src="https://www.gss-lang.dev/embed.js"></script>` then `<gss-scene src="logo.gss"></gss-scene>`, or the code inline in a `<script type="text/gss">` child.
- **Developers**: `import { mount } from "gss-lang"` then `mount(canvas, source)`; it returns `update()`, `pause()`, `play()` and `destroy()`.
- **Developers who count the kilobytes**: `import scene from "./logo.gss"` with the plugin `gss-lang/vite`, then `mount` from `gss-lang/runtime`: the scene is compiled at build time, the page ships the runtime and the shader, not the compiler.
  The runtime is split in two: `runtime/view.ts` draws a `CompiledScene` and does not import the compiler; `createRenderer` (`load(source)`, used by the playground, the home page and the docs) compiles, then hands the result to the view.
  An embedded scene behaves like the playground by default: drag turns the camera, the wheel zooms, `:hover` works (`controls="none"` / `controls: false` keeps only `:hover`). It only creates its WebGL context when it comes into view, stops drawing when it leaves it (its clock stops too, so an animation resumes where it was), and freezes the time under `prefers-reduced-motion`. Images are resolved against the `.gss` file (`base`), like `url()` in a stylesheet; the Vite plugin turns relative images into assets.
  **Why**: a use-case page has to show what a visitor can do on their own site, and until now GSS only lived on gss-lang.dev. `<gss-scene>` is a web component, but it does not go against decision 2: the structure of the scene stays in `@scene`; the element only gives a scene a place in a page, the one thing plain HTML cannot do without a script. `embed.js` is served by gss-lang.dev, so the showcase and designers can use it before the repo is public or the package is published. Splitting the runtime is what makes "no Three.js" a real argument: a precompiled scene costs a small runtime and one shader.
  **Accepted limits**: the wheel zooms by default, so the page does not scroll while the pointer is over a scene (Ctrl/Cmd + wheel, like maps, was proposed and set aside for now). GSS has no transparency: the scene's `background` should match the page. A browser keeps about 16 WebGL contexts: a page with many scenes should use captures and start one scene at a time. The npm package is not published until the project has a license.

## 64. Performance is measured, never assumed: a public profiler, a bench for every change

**Decision**: a public playground profiler and a development benchmark. Neither is included in `embed.js`.
- **The profiler** (`src/profiler/`): a panel over the playground scene, on the public site too, closed by default (decision 87), shown or hidden with the `perf` button of the status bar or Alt+P, the visitor's choice remembered across reloads. It shows the frame time (median, p95, p99) and the fps from the mean frame time, the GPU time of a frame (`EXT_disjoint_timer_query_webgl2`, read a few frames later, never waited for; "unavailable" without the extension, never 0 ms), the CPU time of the draw (where a GPU wait shows), the real resolution in canvas pixels and the GLSL build time. A line over budget turns signal: under 55 fps, a frame p95 over 20 ms, GPU over 12 ms, CPU over 4 ms, a shader over 500 ms. `view.ts` only knows an optional `profile(gl)` option and four calls (`frameStart`, `drawStart`, `drawEnd`, `shaderBuilt`): without it, nothing runs. The playground imports the panel in development and production; a responsive layout keeps the panel and its toggle accessible on mobile.
- **The bench** (`npm run bench:compare -- main [--dpr 2] [--scenes …]`, `scripts/bench.mjs`, `bench.html`, `src/bench/`): another commit is benched in a git worktree with today's bench and profiler copied in (the same measuring tool on the old engine), then the working tree, **3 rounds each, alternating**, in a real Chromium on the machine's GPU. For each scene: two images with the time stopped at 0 (mouse outside, then over the middle, for `:hover`) and the profiler's numbers (mouse outside, then over the scene). The report (`bench-results/compare.md`) says **worse** or **better** only when the medians differ beyond a floor (10 % and 0.3 ms for the GPU) **and every round agrees**; the p95 are shown, not judged. Any pixel that moves by more than 2 (out of 255) is a change, with an image of the differences; exit code 1 on a regression. `--dpr 2` renders like a Retina screen.
**Why**: "a frame feels slow" is not a number, and a speed-up that changes the image is not a speed-up. The first bench, with one run per version and fixed thresholds, reported regressions on scenes whose shader had not changed: two runs of the same code differ more than any fixed threshold. Alternating rounds measure the machine's own noise; comparing `main` with itself gives "no regression" on every line. Rendering at dpr 2 matters: on an M4 Pro at dpr 1 every scene ran under the screen's frame time, so no GPU change could show.
**Accepted limits**: the timings need a quiet machine and a visible window; a busy machine gives rounds so far apart that nothing can be judged (the report shows the lowest and highest round, so it can be seen). The images are taken at time 0 only. The GPU timer is missing in some browsers (Safari). The bench's verdict on pixels: decision 74.

## 65. :hover reads its pixel without waiting for the GPU

**Decision**: the picking pass of decision 62 no longer reads its pixel with a blocking `readPixels`. `runtime/picker.ts` draws it into its 1 × 1 framebuffer, has the GPU copy it into a pixel buffer (`PIXEL_PACK_BUFFER`, `readPixels` with an offset), and puts a fence after it (`fenceSync`). Each frame, `poll()` checks the fence (`getSyncParameter`, never `clientWaitSync`); once it has passed, `getBufferSubData` reads the id at once. One pixel at a time: no new request while one is on its way. Until an answer comes back, the last hovered id holds; outside the canvas, nothing is hovered at once; a new shader forgets the old id.
**Why**: a blocking `readPixels` stops the CPU until the GPU has finished everything it was given, every frame the mouse is over a scene with `:hover`. Measured (bench, dpr 1, M4 Pro, mouse over the scene): CPU time of the draw 4.1 → 0.4 ms on orrery, 5.2 → 0.3 ms on macropad; the GPU median fell by 45 % too, since the GPU no longer sat idle while the CPU read. Every image identical, hover included.
**Accepted limits**: the hover answers one or two frames later (16 to 33 ms at 60 fps). When the GPU is saturated (dpr 2, a heavy scene), the one read that remains still waits behind the browser's GPU process: making the scene cheaper is what helps (decision 66). Picking only when the mouse or the scene moves is still possible.

## 66. map() skips a path or a prism when its bounding sphere is further than the nearest object

**Decision**: every shape gives the radius of a sphere, centered on its origin, that holds it (`SHAPES` returns `{ code, radius }`; `shapeRadius()`; for `path` and `prism`, `pathRadius` / `polygonRadius` in `path.ts`: their points around the view-box center, plus half the stroke or the depth, which also covers the box they return when far away). For `path` and `prism` only (`BOUNDED`), and only for a plain union, `map()` tests that sphere right after the object's own translate and before its rotations: `(length(q) - R * scale) * groupScales <= nearest`, where `nearest` is `res.x`, or `min(res.x, p.y)` when the scene only has plain unions and a floor (then `map()` is a plain `min()` and the floor counts from the start). The radius is rounded up with a 0.001 margin, for 32-bit floats.
**Why**: a `path` or a `prism` walks dozens of segments at every call of `map()`. GSS shapes are exact distances, so an object whose sphere is further than the nearest one would have lost anyway: the image does not change. Measured (bench, dpr 2, M4 Pro, 3 rounds): GPU median macropad 27.1 → 17.2 ms (−37 %, 120 Hz reached), logo 3.95 → 1.99 ms (−50 %), test scene 8.9 → 5.7 ms; every image identical. Bounding **every** shape was tried first and measured slower on scenes of simple shapes (spiral +44 %, todal +21 %): for a sphere the test costs as much as the shape, and one branch per object breaks the straight-line code GPUs run best. Scenes without path or prism compile to the exact same shader as before.
**Accepted limits**: a subtraction, an intersection or a blend is never skipped (far away, they still change the result). The radii of the simple shapes are computed and tested but unused: they are there for bounds on whole groups, or on the whole scene, later.

## 67. `dpr`: the pixel density of the render, chosen by the author

**Decision**: `scene { dpr: auto | max | <number>; }`, `auto` by default. `auto` is what every scene did before: the screen's `devicePixelRatio`, up to 2. `max` follows the screen, however dense. A number from 0.25 to 4 sets the density, never above the screen's (`dpr: 2` on a 1x screen renders at 1). The compiler reads it after `var()` and the math (`readDpr` in `compiler/features/dpr.ts`, called on the computed scene like `readCamera`) and returns it in `CompiledScene.dpr`; the runtime turns it into the canvas ratio with `pixelRatio(dpr, devicePixelRatio)` (`runtime/dpr.ts`), read at every `resize()`, so a new value applies at the next frame. A scene property (`scene { }`, with `floor` and `background`), not an at-rule: `@scene` lists the objects (decision 11), and a property is what `@media` will be able to change.
**Why**: the pixel density is the strongest lever on the GPU cost (dpr 2 renders 4 times the pixels of dpr 1), and only the author knows whether a scene must be sharp (`max`, a hero on a phone) or cheap (`1`, a heavy scene; below 1, a deliberately coarse look). A number is capped by the screen so that it never costs more than `max`: rendering above the screen (supersampling) would be a different feature. `auto` keeps every existing scene unchanged, and has a name so that a later `@media` rule can set it back.
**Accepted limits**: not animatable. The Shadertoy export ignores it: Shadertoy draws at its own size. Changing it with the screen waits for `@media`.

## 68. Easings and `transition`: one reading, computed in JavaScript for transitions and in GLSL for @keyframes

**Decision**: `compiler/values/easing.ts` reads every easing once: the CSS keywords (`ease`, `ease-in`, `ease-out`, `ease-in-out`, `linear`), `cubic-bezier(x1, y1, x2, y2)` (x from 0 to 1, y free, so a curve can overshoot) and `linear(…)` with its positions filled like CSS (first at 0%, last at 100%, a run spread evenly, a position never going back, two percentages = a flat step, two points at one moment = a jump). `findEasing()` finds the one easing among the tokens of a shorthand. Two engines compute it: `runtime/easing.ts` (`ease()`: Newton, then bisection when Newton stalls) for transitions, and the shader for `@keyframes` (`cubicBezier()`, a 16-step bisection, written only when a scene uses it; `linear()` as segments, `step()` for a jump). **`ease-in-out` stays a `smoothstep()` in `@keyframes`**: the scenes written before keep their exact motion and cost (the 98 shaders of the scenes and examples are unchanged); a `cubic-bezier(0.42, 0, 0.58, 1)` written out is drawn the same way. `transition: [all] <duration> [<easing>] [<delay>]`, one per object (`compiler/features/transition.ts`, `ease` by default like CSS): `CompiledScene.transitions` gives each hover slot an `enter` transition (from the object's styles in the `:hover` state, so a `:hover` rule can set its own) and a `leave` one (the styles at rest), like CSS. The runtime (`runtime/transitions.ts`, `createTransitions()`) moves each `uHover[slot]` from where it is to 0 or 1: the shader is unchanged (decision 62 had planned it). Going back halfway takes the share of the duration still to cover, like CSS's reversing; a positive delay is kept, a negative one starts partway. Under `prefers-reduced-motion` (`freeze()`), the change stays instant.
**Why**: transitions are state the runtime keeps (decision 6): the mouse decides when they start and when they turn back, which the shader cannot know. `@keyframes` are a function of time, so they stay in the shader (decision 21). One parser keeps both engines reading the same curve. The bisection in GLSL is slower than Newton but never stalls (a curve like `cubic-bezier(1, 0, 0, 1)` has a flat point that stops Newton), and it only runs in scenes that use these easings.
**Accepted limits**: one transition per object: `transition: scale 0.3s` or a list (`scale 0.3s, color 1s`) is an error for now, since an object has one hover slot. `transition` only plays with `:hover` (nothing else changes a style at run time yet). `steps()` came with decision 80. Since the default `animation` easing is `linear` (not `ease` as in CSS), an animation without an easing keeps a constant speed. The Shadertoy export ignores transitions (decision 62).

## 69. `:has()`: a group that holds a match, at compile time or under the mouse

**Decision**: `:has(<selector list>)` on a group, like CSS: the group matches when something inside it, at any depth, matches one selector of the list. Any selector works inside, a descendant one included, read from the group down (`#g:has(#inner sphere:hover)`: `#inner` must be inside `#g`). The parser no longer cuts a selector at the spaces and commas inside parentheses (`parseRules` in `parser.ts`, `parseSelector` and `splitAtCommas` in `resolve.ts`); `SimpleSelector.has` holds the list. `matches()` receives the scene: `inside(group, scene)` lists every object and group inside a group, each with its ancestors inside that group, and `matchesCompound` checks `has` with them. Without `:hover` inside, `:has()` is resolved by the compiler and costs nothing. With `:hover` inside, it adds hover triggers (decision 62): `triggersOf()` follows `:hover` and `:has()` at any depth (`hoveredBy`: an object, or every object of a hovered group; `hasTriggers`: the triggers of the matches inside the group), so `#g:has(sphere:hover) cube` puts the cubes of `#g` in their hover state while a sphere of `#g` is hovered; the shader, the picking and `transition` are unchanged. Specificity: the most specific selector of the list, like CSS. Errors: `:has()` on an object (`cube:has(sphere)`: an object holds nothing), an empty `:has()`, two `:has()` on one part (write a list), a `:has()` inside a `:has()` (CSS forbids it too).
**Why**: `:has()` is how CSS lets one element react to another; in a scene, it is how hovering a button lifts a lid, or a bulb lights its stand. The hover slots already took a list of triggers, so it only needed to find them. Lucas chose the whole selector syntax inside, rather than a simple selector only.
**Accepted limits**: a list mixing a selector that matches without the mouse and one with `:hover` (`#g:has(sphere, cube:hover) x`) is true at rest in CSS; in GSS the rule still waits for the mouse, and any hovered object triggers it. A `:has(…:hover)` rule styles objects, not the group itself (`#g:has(sphere:hover) { … }` is the same error as `#g:hover { … }`). Relative combinators were added in decision 73; no other pseudo-classes yet.

## 70. Animation controls: delay, iteration count, direction, fill mode, computed from `iTime`

**Decision**: the `animation` shorthand reads, after the name and the duration, in any order: an easing, a delay (the second time, negative = starts partway), an iteration count (a number, 1.5 stops halfway, or `infinite`), a direction (`normal`, `reverse`, `alternate`, `alternate-reverse`) and a fill mode (`none`, `forwards`, `backwards`, `both`), like CSS. Six longhands (`animation-duration`, `-delay`, `-iteration-count`, `-direction`, `-fill-mode`, `-timing-function`) win over the shorthand; alone, without `animation`, they are an error. `compiler/features/animation.ts` (`readAnimation` → `AnimationSpec`) reads them once; `codegen.ts` (`playback()`) turns the spec into a GLSL progress and a condition. **An animation still loops forever by default** (CSS plays once): every scene written before keeps its motion, and a plain loop or `alternate` without a delay or a count is written exactly as before (`fract(iTime / d)`, `1.0 - abs(mod(…))`), so the shaders of every existing scene and example are unchanged. Anything else goes through `playhead(t, duration, n, dir)`, a GLSL helper written only when used (in the `EASINGS` table): the iteration and the position in it, the end of the last iteration at 1, the direction applied per iteration. Like CSS, outside the animation (during a positive delay, after the last iteration) the object shows its own value, `((iTime >= delay && iTime < end) ? animated : own)`, unless `backwards` holds the first frame during the delay or `forwards` the last one after the end. Infinity is written as 1e9 iterations.
**Why**: a delay and a count are what make an entrance: a logo that lands once and stays. Everything depends only on the scene time, so the shader computes it, like the `@keyframes` themselves (decision 21), with no state in JavaScript. Keeping the loop as the default is the same choice as keeping `smoothstep` for `ease-in-out` (decision 68): no scene changes behind its author's back.
**Accepted limits**: the scene time starts when the page (or the scene) loads, not when the object appears, and a `@keyframes` change in the playground restarts nothing but the clock it already has. The longhands always win over the shorthand, whatever their order or specificity (CSS lets the cascade decide). `animation-play-state`, `animation-name` as a longhand, and several animations on one object (a comma list) are not there yet. The GLSL check of `playhead()` against the same formula in JavaScript matched to 8 bits.

## 71. `@media`: one compiled version of the scene per combination of its queries

**Decision**: `@media <query> { rules }`, like CSS. The parser keeps the query as text (`Rule.media`, rebuilt from the tokens with their spaces) and the browser evaluates it with `matchMedia`, so any media query CSS knows works (width, orientation, `prefers-color-scheme`, `prefers-reduced-motion`, `and`, `not`, commas). `compileScene()` compiles the scene once for every combination of the distinct queries (`2^n`, at most 4 queries, so 16 versions), keeping only the rules whose query is in the combination; a rule of a matching `@media` joins the cascade where it is written, like CSS. `CompiledScene.media = { queries, variants }`, `variants[mask]` being the version where the queries whose bit is set match; the fields of the scene itself are `variants[0]` (nothing matches), which is what Node, the tests and the Shadertoy export see. The runtime (`runtime/media.ts`: `pickVariant`, `watchMedia`, `matchesNow`) shows the version for the screen now and listens to each query: on a change, `view.ts` (`display()`) builds the other version's shader and keeps the camera where the mouse left it. The Vite plugin turns the images of every version into assets. `@media` holds rules only (`@scene` and `@keyframes` stay outside). `animation: none` stops an animation, for `@media (prefers-reduced-motion) { * { animation: none !important; } }` (the `!important` is needed, as in CSS: `*` weighs 0). A scene without `@media` compiles exactly as before.
**Why**: the runtime never holds the compiler (decision 63): a scene compiled at build time must still follow the screen, so every version is prepared in advance and the runtime only picks one. Compiling a few versions costs milliseconds; building a shader only happens for the version shown. Letting the browser read the query gives all of CSS's media features for free and the exact same answers as the page's own CSS. Uniforms that switch values inside one shader were considered: the cascade would have to become conditional, and `dpr`, the camera and the transitions (read by the runtime, not the shader) would need their own switches.
**Accepted limits**: at most 4 different queries per scene. Queries are about the page's window, like CSS, not the canvas (container queries would be another feature). A version switch rebuilds the shader (a frame or two) and restarts the hover state; the scene time goes on. The playground's status bar and GLSL tab show the version where nothing matches.

## 72. The compiler is sorted by pipeline stage

**Decision**: `src/compiler/` keeps only `index.ts` (`compileScene()`, the pipeline) at its root; every other module lives in the folder of its stage: `syntax/` (tokenizer, ast, parser, errors), `cascade/` (expand, resolve, validate, vars), `values/` (values, calc, colors, named colors, easing, svgpath), `features/` (animation, transition, camera, dpr, textures), `shader/` (codegen, path, shadertoy), `registry/`. A unit test sits next to its module; a test that goes through `compileScene()` from source to GLSL lives in `tests/`. Only the import paths changed: no code, no test, same 937 tests.
**Why**: 60 files side by side in one folder no longer said where a feature starts and ends. The stages are how the code is read (source → tokens → rules → styles → values → GLSL), and the runtime's type-only imports (`features/camera`, `features/dpr`, `values/easing`, `features/transition`) now say which part of the compiler it leans on.
**Accepted limits**: `codegen.ts` (about 1,750 lines) and `registry.ts` (about 850) are moved, not split; splitting them is a refactor of its own. `readAngle` and `readNumber` still live in `codegen.ts` though `camera.ts` uses them. (`codegen.ts`, `readAngle` and `readNumber`: decision 88.)

## 73. Child and sibling combinators, including relative selectors in `:has()`

**Decision**: `a > b` targets a direct child, `a + b` the immediately following sibling and `a ~ b` any following sibling, like CSS. Siblings share a parent and follow declaration order after `* n` expansion, including groups and empty groups; their 3D positions do not matter. Whitespace around explicit combinators is optional. Chains can mix these relations with descendants, selector lists, compound selectors and a final face. Specificity still sums the compounds; combinators weigh nothing. `SimpleSelector` keeps the preceding compounds in `ancestors`, with a parallel `combinators` list. One right-to-left matcher backtracks over complete paths for both static matching and hover triggers: conditions on one path intersect, alternative paths form a union. `expandScene()` retains all structural nodes in a WeakMap keyed by its drawable array, keeping empty groups available without changing shader indices or adding circular data to instances.

`:has()` accepts a leading relative combinator anchored to its subject: `group:has(> sphere)`, `cube:has(+ sphere)`, `cube:has(~ sphere:hover)` and mixed chains such as `cube:has(+ group > sphere)`. A selector without a leading combinator still starts inside the subject, preserving decision 69's scoped descendant behavior. Objects can use `:has()` when its list includes a leading sibling relation; a descendants-only `cube:has(sphere)` remains an error. Hover follows the same structural paths, including hovered sibling groups; empty groups cannot be hovered. The shader, picking and transitions use the existing hover slots without additional runtime work. The registry provides a documentation page and live example for each combinator; the tokenizer also feeds their highlighting and formatting, and VS Code recognizes them as selector operators.

**Why**: direct children let a group style one level without touching nested objects; siblings let one object react to its neighbours. Matching whole paths prevents an unrelated ancestor or sibling from becoming a hover trigger. Keeping empty groups is necessary for adjacency: `sphere; group {}; cube;` must not match `sphere + cube`.

**Accepted limits**: nesting style rules with `&` remains a separate, unfinished part of priority #7. The existing hover model still has one combined state per object, and a `:has()` list mixing static and hovered alternatives keeps decision 69's limitation. Nested `:has()`, hover changes to faces and rules that only animate groups remain unsupported.

## 74. The bench accepts stray pixels: GPU rounding, not a change of the scene

**Decision**: the bench's verdict on images (decision 64) no longer requires every pixel to stay within 2 of its old value. A changed pixel is **stray** when it is an edge flip (the silhouette moved by one pixel: its new color is already in the old image around it, and its old color still is in the new one; a row of them along the horizon included) or when it is isolated (none of its 8 neighbours changed). An image whose changed pixels are all stray, and no more than 0.05 % of it (about 1,000 pixels at dpr 2), is "✅ stray pixels only" and is not a regression. The diff image paints stray pixels yellow, the others red.
**Why**: moving the same arithmetic in the shader (decision 75) or skipping work that cannot win (decisions 76, 77) changes how the GPU compiler rounds a few operations; on a grazing ray (a contour, a reflection) that flips a pixel here and there. Measured on the three changes of Oct. 1: 14 pixels out of 2 million on L'Orrery, 4 on todal, each alone, at the edge of an object, invisible at full size; 64 pixels along the horizon of the spiral. A real change of the scene (an object that moves, a color that changes, a shifted outline) changes patches of touching pixels, or more than the budget.
**Accepted limits**: an isolated pixel can take any color; the budget and the isolation are what keep the check meaningful. The images are still taken at time 0 only.

## 75. Animations are computed once per pixel, in `animate()`

**Decision**: an animated value (`@keyframes`, an animated variable, a `:hover` mix) depends on the time, not on the point. Each animated or hovered translate, rotation matrix and scale of `map()` is now a global (`anim0`, `anim1`…), computed once by `animate()` at the start of `main()`, the Shadertoy export included; two objects with the same animation share one. `map()` only reads them. A scene where nothing moves has no `animate()`, and its shader is unchanged.
**Why**: `map()` runs about 150 times per pixel (the march, the normal, the reflection), and recomputed every `mix()`, `rot()` and easing each time. The same arithmetic, moved: put back in place, the shader of every scene of the repo is the exact text it was. Measured (bench, dpr 2, M4 Pro, 3 rounds): L'Orrery GPU 20.3 → 9.2 ms (−55 %), hovered 21.0 → 13.9 ms and its CPU 17.9 → 2.5 ms; the test scene hovered −29 %; the other scenes the same. Images: 15 stray pixels on L'Orrery, 2 on todal (decision 74).
**Accepted limits**: the animated values are still computed on the GPU, once per pixel. Computing them once per frame on the CPU and sending them as uniforms was set aside: it would only save that one evaluation, needs a JavaScript copy of every animation, easing and playback rule of the shader, and 64-bit JavaScript numbers would not give the GPU's 32-bit results.

## 76. A ray that passes by the sphere of the scene only meets the floor

**Decision**: `march()` starts with a sphere that holds every object at every moment of its animations, hovered included. A ray that starts outside it and passes by (or moves away) meets no object: with a floor, it returns the floor's distance (`-ro.y / rd.y`) at once, or nothing; without a floor, nothing. Each object's sphere is read from the GLSL of its translate and scale: a constant, or `mix()` of constants with a weight that stays in [0, 1] (`clamp(…, 0.0, 1.0)`, `smoothstep(0.0, 1.0, …)`, or `uHover[i]` when the object's transitions never overshoot: a `cubic-bezier()` with y1 and y2 in [0, 1], a `linear()` whose outputs are). A rotating group centers its children's sphere on its origin; a blend widens it. Any other value (an overshooting easing, a delay or iteration count that switches the animation off, a `transition` that can go past its target) gives the scene no sphere, and its shader is unchanged.
**Why**: most of the pixels of a scene are sky and far floor, and each of them marched up to 100 steps for nothing. Measured (bench, dpr 2, M4 Pro, after decision 75): todal 23.6 → 19.4 ms (−18 %), spiral 4.4 → 3.8 ms (−15 %), the others the same. It also ends the lost rays at the far edge of the floor: 64 pixels of the spiral's horizon change, one dark grey for another (decision 74), a correction Lucas accepted.
**Accepted limits**: a scene whose objects move far, or rotating groups, get a large sphere and gain little. A `cubic-bezier()` easing in `@keyframes` is not read yet (the scene keeps the plain march), even when it does not overshoot.

## 77. One bounding test for a group of 3 objects or more

**Decision**: in `map()`, the objects of a group (3 or more, all plain unions, every sphere known) are wrapped in one test: `if (length(p - C) - R <= nearest) { … }`, where the sphere (C, R) holds the spheres of decision 76 of all of them. When the point is further, none of them can be nearer than what `map()` already has: their transforms and shapes are skipped. Nested groups get their own test inside their parent's. The radius is rounded up with a margin, as in decision 66.
**Why**: decision 66 measured that a test per simple shape costs as much as the shape; one test for a whole group does not. Measured (bench, dpr 2, M4 Pro, after decisions 75 and 76): macropad 16.6 → 4.0 ms (−76 %), todal 19.4 → 3.9 ms (−80 %), L'Orrery 9.9 → 7.5 ms (−24 %, hovered −49 %), the others the same. Over the three decisions, from `main`: L'Orrery 20.3 → 7.5 ms, macropad 17.4 → 4.0 ms, todal 24.3 → 3.9 ms, every scene of the bench under 8.3 ms (120 Hz) at dpr 2. Images: stray pixels only (decision 74).
**Accepted limits**: a group of 2 objects, or one with a subtraction, an intersection or a blend, keeps one line per object. A ring of objects (todal's dial) gets a sphere as large as the ring.

## 78. The rest of the CSS math functions, computed at compile time like the first ones

**Decision**: `calc.ts` knows every math function of CSS Values 4 and 5 that makes sense without a box: `asin()`, `acos()`, `atan()`, `atan2()`, `sign()`, `round()`, `mod()`, `rem()`, `hypot()`, `log()`, `exp()` and `progress()`. They follow CSS: the inverse functions return an angle (in deg), `atan2(y, x)` takes two values of the same unit; `round()` takes an optional strategy first (`nearest`, the default, where halfway goes up, `up`, `down`, `to-zero`) and an optional step (1 by default), `round(37deg, 15deg)` is `30deg`; `mod()` takes the sign of the divisor and `rem()` the sign of the value (`mod(-7, 3)` is 2, `rem(-7, 3)` is -1); `log(x, base)` has an optional base; `progress(value, start, end)` is clamped to 0–1. Documented as four registry entries (`fn-inverse-trig`, `fn-stepped`, `fn-exponential`, `fn-progress`).
**Why**: decision 52 put math at compile time; these are the same mechanism, one case each in `apply()`, and every one of them helps to place copies (`mod()` and `round(down, …)` turn a list into a grid, `progress()` into a 0–1 ramp, `atan2()` turns an object toward a point).
**Different from CSS**: a division by zero in `mod()`, `rem()` or `round()` (a step of 0), or `progress()` with the same start and end, is an error instead of `NaN`; `progress()` has no `no-clamp` keyword; `infinity` and `NaN` are not constants.

## 79. The rest of the CSS color functions, computed at compile time

**Decision**: like `rgb()` and `hsl()` (decision 58), every color function becomes a `#rrggbb` at compile time: `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color(<space> …)` (srgb, srgb-linear, display-p3, xyz, xyz-d65, xyz-d50), `color-mix()`, `light-dark()` and `contrast-color()`. The conversions are in `values/color-spaces.ts` (matrices of the CSS Color 4 sample code), all through linear sRGB. Percentages follow CSS (100% is 100 for the Lab lightness, 125 for a and b, 150 for the LCH chroma, 1 for the OKLab lightness, 0.4 for a, b and the OKLCH chroma). `color-mix()` takes `in` and one of srgb, srgb-linear, lab, lch, oklab, oklch, hsl, hwb, `shorter hue` (the default) or `longer hue`, colors written in any form (a name, a hex, another function), percentages completed and scaled like CSS; a gray has no hue and takes the other color's. `contrast-color()` gives white or black by the WCAG 2 contrast, white when they tie. `light-dark()` makes the compiler add the query `(prefers-color-scheme: dark)` to the `@media` queries of the scene (shared with an `@media` written the same way, and counted in the 4): each version resolves `light-dark()` with its scheme.
**Why**: the same mechanism as decision 58, and `light-dark()` the same as decision 71, so the shader and the runtime do not change. OKLCH and `color-mix(in oklab, …)` give palettes of even lightness, which `hsl()` cannot.
**Different from CSS**: a color outside sRGB is clipped channel by channel, not gamut-mapped (CSS lowers the chroma), since the render is sRGB; percentages of `color-mix()` that add up to less than 100% are an error (CSS makes the color transparent); no `none` channel, no relative colors (`rgb(from …)`), no `currentcolor`, no `increasing` / `decreasing hue`; `light-dark()` follows the system setting, not a `color-scheme` property. `alpha()` waits for transparency.

## 80. `steps()`: a third kind of easing, computed by the same two engines

**Decision**: `steps(<count>, <position>?)` with the CSS positions `jump-start`, `jump-end` (the default), `jump-none`, `jump-both`, the old names `start` and `end`, and the keywords `step-start` and `step-end`. It is a third type of `Easing` (`{ type: "steps", count, position }`), read in `values/easing.ts`. Like CSS, the progress x becomes `min(floor(x · count) + offset, jumps) / jumps` (`stepsShape()`: offset 1 for jump-start and jump-both; jumps = count, count + 1 with jump-both, count − 1 with jump-none). The shader writes that line in place, with no helper function; the runtime (`ease()`) computes the same formula, copied because the runtime never imports the compiler (decision 63). A steps() transition stays in [0, 1], so it keeps the sphere of the scene (decision 76).
**Why**: CSS has it, and it is the only easing a `linear()` cannot write without one point per jump. A new type keeps the GLSL to one line whatever the count, where turning it into a `linear()` would write two segments per step.
In a chain of @keyframes segments, a segment that has not started has a local progress of 0; an easing that is not 0 there (steps() with jump-start or jump-both, or a linear() whose first output is not 0) would cover the segments before it, so from the second segment on its weight is multiplied by `step(start, progress)`. Other easings are 0 at 0: their shaders do not change.
**Different from CSS**: the "before flag" of CSS (a jump-start animation during a negative delay) does not exist: GSS reads the delay itself (decision 70).

## 81. `random()`, `if()` and gradients in the background

**Decision**:
- **`random([--name || element-shared | fixed <number>,]? min, max, step?)`** is computed at compile time in `calc.ts`. Its random number comes from a hash (FNV-1a, then mulberry32) of a seed: the place of the object in `@scene` (`group#ring:2 > sphere:3`: tags, ids and sibling indexes, so adding objects after it changes nothing), the property and the number of the call in the value (or the `--name`), and the arguments. The same scene gives the same values at every reload, in every `@media` version, at rest and in `:hover`. `element-shared` drops the object from the seed, `fixed` gives the number. With a step, one of min, min + step, … up to max.
- **`if(<condition>: <value>; …; else: <value>)`** is resolved after `var()` (`values/conditionals.ts`), on objects, groups, faces, the scene and in `@keyframes`. Conditions: `media(<query>)`, `style(--x)` (set, here or inherited), `style(--x: <value>)` (compared token by token, through `var()`), `else`, and `not` / `and` / `or` (no mixing, like CSS). Each `media()` query becomes an `@media` query of the scene (`mediaQueriesOf`, shared with an `@media` written the same way, counted in the 4): the version being compiled knows which queries are true (`activeMedia` in `index.ts`, which also replaced the color scheme of decision 79). The parser keeps a `;` between parentheses in the value; the tokenizer knows `<` and `=`, so `@media (width < 600px)` works too.
- **Gradients** (`shader/gradient.ts`): `background` takes `linear-gradient()`, `radial-gradient()` and their `repeating-` forms. The shader gets a `vec3 background(vec3 rd)` with the geometry of CSS Images 3 (length of the gradient line, "magic corners", circle and ellipse sizes, `at <position>`) over the canvas (`iResolution`), and `#define BACKGROUND background(rd)`; a plain color stays the constant it was, so existing shaders do not change. Stops are completed like CSS and mixed in sRGB. The point of the canvas is where the ray points, seen through the camera (decision 82).
**Why**: `random()` with a stable seed is what generative scenes need, without the scene changing at each reload; `if()` and gradients reuse the machinery of `@media` and the shader's background constant.
**Different from CSS**: `random()` is fixed at compile time, not per page load; a failed `if()` with no `else` is an error, not an invalid value; `supports()` is not a condition; no color hints or `in <space>` in gradients, no `conic-gradient()`.

## 82. Gradients by direction in the background, and on objects

**Decision**:
- **The background follows the direction of the ray**, not the pixel: `background(rd)` projects `rd` through the camera onto the canvas (`camForward`, `camRight`, `camUp`, set at the start of `main()` only when the background is a gradient). A primary ray lands on its own pixel, so the image of decision 81 does not change; a reflection or a refraction sees the gradient where it points. A ray that goes sideways or back reaches the edge of the canvas: the point is clamped to it, like CSS, where nothing exists outside the box.
- **Gradients on objects**: `color: linear-gradient(…)` and a gradient as the first argument of a material (`metal(radial-gradient(…), 0.2)`, which wins over `color`, like a material's own color). The gradient covers the object seen from the front, x to the right and y up, in the object's space (it moves, turns and scales with it): `to top` goes from its bottom to its top. A `plane` is seen from above, the top away from the camera. The rectangle is the size of the shape (`gradientBox()`: a cube's size, a sphere's diameter, a cylinder's diameter and height…; the bounding sphere for `path` and `prism`). In the shader, `gradientColor(id, p, color)` is called right after `getMaterial()`, before the textures (an image is painted over the gradient, by its alpha), and in `trace()`, so reflections see it; `getMaterial()` gets the mean of the stops. Objects share one `spaceN()` with the textures. `readFunction` now splits arguments only at the commas of its own call, not those of a call inside it.
**Why**: Lucas saw the stripes of a repeating background on chrome spheres: decision 81 showed the background of the pixel a reflection was cast from, as if the sphere were transparent. A gradient on an object is the same geometry with another rectangle and another point, so both share `gradientLines()`.
**Accepted limits**: a gradient is not animated, and `:hover` cannot change it (both are errors, not ignored); a gradient on an object is flat, drawn from the front, not wrapped around it.

## 83. `filter`: pixel filters in the scene's shader, `blur()` and `bloom()` as passes

**Decision**: `scene { filter: … }` takes a list of functions applied in order, like CSS `filter` on the whole canvas (`features/filter.ts`, `compileFilter()`). The filters that read only their own pixel are a few lines at the end of the scene's `main()`, on `col`, with no extra pass: `brightness()`, `contrast()`, `invert()`, and the color matrices of CSS Filter Effects for `saturate()`, `grayscale()`, `sepia()`, `hue-rotate()` (computed by the compiler, written as three dot products), each clamped to 0–1 like CSS; plus `grain(<amount>)`, a noise that changes at every frame (`grain()` in GLSL, written only when used). The filters that read the pixels around are passes after the scene: `blur(<px>)` is a gaussian of that standard deviation in CSS pixels, in two passes (across, then down, 65 samples each read with `texelFetch`, spread wider for large blurs); `bloom(<amount>, <px>)` takes the bright parts (`smoothstep(0.35, 0.9, luminance)`), blurs them in two passes and adds them to the image in a third. `CompiledScene.passes` lists `{ shader, inputs }`: image 0 is the scene, pass n draws image n + 1, the last pass draws the screen; pixel filters before the first pass stay in the scene's shader, those after a pass end that pass. `runtime/post.ts` (`createPost(gl, link)`) keeps one RGBA8 image per pass but the last, of the size of the canvas, and `view.ts` only calls it when the scene has passes: every other scene is drawn as before. `uRatio` (canvas pixels per CSS pixel) keeps `blur(4px)` at 4 CSS pixels whatever the `dpr`.
**Why**: CSS's own list, so an author already knows it, and the cost is paid only by what is used: a contrast or a grain costs a few instructions, a blur or a bloom one image and two or three passes. Several shaders, but still one raymarcher for the whole scene.
**Different from CSS**: `opacity()` and `drop-shadow()` are errors (GSS has no transparency); `bloom()` and `grain()` are GSS's own. The filters work in sRGB, without `color-interpolation-filters`. The Shadertoy export keeps the pixel filters and leaves out the passes.

## 84. `filter` on objects and groups: pixel filters on their own pixels, layers for `blur()` and `bloom()`

**Decision**: `filter` also applies to objects and groups (`appliesTo: "everywhere"`, and in the `takes` of `group`), like CSS on an element. `objectFilters()` (`features/filter.ts`) gives each object its pixel filters, its own first, then those of its groups from the inside out (CSS applies a child's filter before its parent's): in the shader, `objectFilter(id, c)` changes the color of the pixels of that object, right after shading, and in `trace()`, so reflections see the filtered object. An object or a group with a `blur()` or a `bloom()` is a **layer**: a number from 1 to 255 that the scene writes in the alpha of its image (`objectLayer(id)`; 0 for the floor, the background and the other objects). The passes of a layer read only the pixels with its number (`texelFetch`, exact, never interpolated): `bloom()` blurs its bright parts and adds them; `blur()` blurs its color and its coverage (premultiplied), blurs what is around it the same way to estimate what it hides, and lays the blurred layer over that, so its edges melt into what is behind instead of keeping a sharp outline. Layers come first, the scene's `filter` after them; every pass but the last keeps the alpha, the last one draws an opaque screen.
**Why**: Lucas wanted filters on shapes too. One raymarched image has no separate layers, so the alpha carries which object each pixel shows, and the blurred surroundings stand in for what is hidden.
**Accepted limits**: on an object, its pixel filters come before its `blur()` / `bloom()` whatever the order written; an object and one of its groups cannot both have a `blur()` or a `bloom()` (an error); what a blurred object hides is an estimate (the blurred pixels around it); reflections see the pixel filters of an object, not its blur or bloom; at most 255 layers. A `blur()` on an object costs five passes, a `bloom()` three.

## 86. A compile reports every error it finds, not only the first one

**Decision**: errors are gathered in an `ErrorSink` (`syntax/errors.ts`) instead of stopping the compile; one error is thrown as it always was (a `GssError`), several as a `GssErrors`, a `GssError` whose `errors` lists them in the order of the text, each one once, and whose start and end are those of the first. Every stage goes on where it can:
- **The text**: the tokenizer skips an unexpected character (or a `#` / `@` with no name) and goes on; an unclosed comment or string runs to the end. The parser keeps the error of a declaration, an element of `@scene` or a rule, skips to its `;` or to the end of its block (`skipDeclaration`, `skipStatement`), and reads the rest; an at-rule it does not know is skipped with its block; a `}` that closes nothing is reported, and the next rule is read as usual. An error at the end of the file (a block never closed) ends the reading: one error, at the `{` that is never closed.
- **The values**, only once the text has no error: an error of the text often leaves a rule or an element out, and what comes after would report its consequences (a missing `d`, a `@keyframes` that does not exist) rather than mistakes of the author. `validateProperties` and `validateKeyframes` keep each wrong rule or declaration and return the others; each object is computed on its own (`var()`, the math, the colors); when the shader fails, each object is compiled on its own (and the scene with no object), so every object with an error is reported; the scene's own properties (camera, `dpr`, `filter`) each report theirs. The same error in several `@media` versions of the scene is reported once.
- **Where they show**: the playground and every "Try it" underline each error and write it under its line (two errors on one line: one block, one per row), the status bar counts them (`3 errors`); an error without a place (a GLSL error) still goes under the editor. The Vite plugin writes each error with its line and column (`describeErrors()`); `<gss-scene>` shows their messages, one per line.
**Why**: fixing one error, recompiling, then finding the next is slow, and an LLM that writes a scene needs every mistake at once to fix it in one pass. A scene that compiles gets exactly the same shader: the 193 shaders of the scenes and registry examples (and their Shadertoy exports) are identical, byte for byte.
**Accepted limits**: an error in the text hides the errors of the values until it is fixed. A broken rule in the middle of a file can still give a second error when the skip ends in the wrong place (a `}` missing inside a rule). A `:` missing before the `}` of a block points at the `}`.

**Decision**: the performance panel of decision 64 ships with the playground on gss-lang.dev, not only in development. ## 88. The code generator is one folder, one file per part of the shader

**Decision**: `shader/codegen.ts` (about 2,300 lines) becomes `shader/codegen/`, its code moved without a change (cut and paste, never retyped): `index.ts` (`generateShader()`, which fills the template, and the map of the folder), `glsl.ts` (`glslFloat`, `vec3`, `label`, `section`, `used`…), `read.ts` (GSS values → GLSL: translate, size, color, light, rotations), `library.ts` (the GLSL tables of shapes, path helpers, easings, operations, materials), `shading.ts` (the lighting of metal, jelly and glass), `template.ts` (the shader skeleton and the picking pass), `shapes.ts`, `operations.ts`, `materials.ts`, `animation.ts` (`@keyframes`, easings and `:hover` as GLSL expressions), `transforms.ts` (the moves into a node's space, `animate()`), `bounds.ts` (decisions 76, 77), `textures.ts`, `gradients.ts`, `filters.ts` (decisions 83, 84: `filterCode()`, the only function newly extracted from `generateShader()`). `readNumber` and `readAngle` move to `values/values.ts`: they read a GSS value and write no GLSL, and `features/camera.ts` no longer imports the shader generator.
**Why**: every feature since decision 59 added to the same file, and its size was the first thing in the way of reading it, reviewing it or teaching it. A file per part of the shader says where a new feature goes.
**Checked**: tests and TypeScript green; the shaders and Shadertoy exports of the 193 scenes and registry examples are byte for byte the same before and after.

## 89. The editor suggests property names, from the registry

**Decision**: in the playground and every "Try it", typing a property name opens a list of the properties the rule can take (`runtime/completion.ts`, `propertySuggestions(code, pos)`, wired with `@codemirror/autocomplete` in `editor.ts`). It reads the code up to the cursor with the tokenizer (comments and unfinished code included) and knows which block it is in: a rule, a frame of `@keyframes`, `@scene`, `@media`. A name is expected right after `{` or `;`, or while one word is being typed there; never in a value, a selector, `@scene`, outside a rule, or for a custom property (`--x`). The list follows what `validate.ts` accepts: `scene` takes the scene's properties; a shape, the object properties and its own (`sphere` gets `radius`, not `corner-radius`); a class, an id or `*`, every object property; `group`, what a group takes; `:hover`, what can be animated, and `transition`; a face, `texture`; a frame, what can be animated. The list opens as soon as a letter is typed, or with Ctrl+Space on an empty line.
**Why**: the registry already knows every property and where it applies; the editor offering exactly those is how someone who knows CSS discovers what GSS has, without leaving the code.
**Accepted limits**: property names only, not values (`material: g…` does not suggest `gold`), nor shapes in `@scene`, nor selectors. The VS Code extension does not have it yet.

## 90. GLSL and WGSL targets, with native WebGPU rendering

**Decision**: `compileScene()` (also exported as `compile`) keeps `shader` as GLSL and adds `wgsl`, on each media variant and each filter pass. `{ target: "glsl" }` omits the second target; `compileGSS(source, "wgsl")` returns WGSL alone. The scene generator remains shared: an explicit typed parser lowers its restricted generated shader language into WGSL (`shader/wgsl/`). This is a migration bridge, not a general-purpose GLSL transpiler or a pair of independently maintained GSS generators. Scalar/vector promotion, constructors, vector comparisons, GLSL modulo, mutable parameters and swizzle writes have explicit lowering rules. Gradient BACKGROUND is the one supported object-like macro. Shadertoy continues exporting the GLSL target.

`runtime/webgpu.ts` uses native WebGPU, without vgpu or another rendering dependency. Uniforms use three vec4 slots followed by one vec4 per hover slot (16-byte stride), shared by scene shaders and passes. Textures use explicit samplers and level-zero sampling, matching the existing non-mipmapped WebGL store and avoiding derivative-uniformity requirements. Fragment coordinates stay bottom-up in the generated scene language; intermediate WebGPU images reverse sampling coordinates and texel indices. Scene and post-processing targets retain RGBA8 semantics. Picking renders into a separate 1×1 RGBA8 texture, copies into a 256-byte readback buffer and maps asynchronously; stale results from replaced scenes are ignored. Pipelines are prepared before committing an update; invalid updates keep the previous scene. Textures are cached across updates and rebound when downloads complete. GPU buffers, textures, listeners, frame loops and media subscriptions are disposed.

`createViewAsync()` and `mountAsync()` default to `backend: "auto"`: WebGPU first, WebGL2 if adapter/device acquisition fails before acquiring the canvas context. Forced `webgpu` reports failure; forced `webgl` uses WebGL2. Existing synchronous `mount()`, `createView()` and `createRenderer()` retain WebGL2. Build-time embeds still ship no compiler. `<gss-scene backend="auto|webgpu|webgl">` opts into asynchronous rendering; no attribute retains the existing synchronous WebGL2 behavior. A new canvas is used when an element restarts, since a canvas cannot change context API. The playground uses the asynchronous renderer and defaults to auto; query parameters force a backend. Its editor handles asynchronous errors and ignores stale results, and displays GLSL or WGSL. The profiler supports both backends (decision 91).

**Why**: support modern browser GPU APIs without dropping WebGL2 or changing GSS authoring syntax. Use the existing compiler's full feature coverage rather than independently porting each new language feature in two generators. Keep asynchronous device and pipeline creation explicit in the public API.

**Validation**: every scene and documented example, including media variants and filter passes, validates as WGSL and as a WebGPU render pipeline in Chromium. Differential render tests compare WebGL2 and WebGPU at frozen time for materials, gradients, transforms, animation, textures, post-processing and hover. Tests also cover automatic fallback, failed updates, resize/disposal and playground backend selection.

**Accepted limits**: no automatic recovery after device loss (`gss-error` is emitted on the canvas); initial fallback applies to device acquisition only. Cross-browser/hardware performance and visual parity still require testing on physical GPUs; SwiftShader comparisons prove functional parity on the test implementation, not performance gains. The typed lowering layer is intentionally restricted to compiler-generated shaders and should evolve into shared shader IR if future features make that bridge costly.

## 91. WebGPU performance panel with optional timestamp queries

**Decision**: the playground mounts the performance panel for both backends, including auto selection, and labels the active engine. `profileWebGPU(device)` provides the same frame, FPS, CPU, resolution and shader preparation statistics as the existing WebGL probe. Device acquisition requests `timestamp-query` only for profiled rendering, only when the adapter advertises it, and retries a plain device if the feature request fails. Missing timestamps never prevent rendering or CPU/FPS profiling: GPU time is reported as unavailable.

The timer writes timestamp 0 at the beginning of the first render pass and timestamp 1 at the end of the last. This includes picking, intermediate copies and scene/post-processing passes, with no per-pass query limit. It resolves the pair and maps a readback buffer asynchronously after submission, without waiting in the render loop. A pool of at most eight query/buffer slots skips measurement while all reads are pending. Integer nanosecond timestamps are subtracted before conversion to milliseconds; zero, reversed and invalid samples are discarded. Shader resets reject stale samples; destruction frees queries and buffers and ignores late mapping results. Query resources and measurement begin only after the panel first opens, preserving decision 87.

The public development hooks carry WebGPU types, so `@webgpu/types` is a type-only package dependency and its reference is preserved in emitted declarations. No profiling implementation is imported into the embed runtime; embedding options remain optional.

**Validation**: unit tests cover unsupported timestamps, nanosecond conversion, deferred readback, pending-query limits, reset/disposal and optional-feature acquisition failure. Chromium tests exercise the WebGPU panel with numeric GPU measurements when timestamps are supported, CPU/FPS statistics, and switching back to WebGL2. Software-renderer timing demonstrates correct instrumentation, not physical GPU performance.

## 92. Structural pseudo-classes: `:nth-child()` and its family

**Decision**: GSS takes the structural pseudo-classes of CSS, with their syntax and their behavior: `:nth-child(An+B [of S])`, `:nth-last-child()`, `:nth-of-type()`, `:nth-last-of-type()`, and the shortcuts `:first-child`, `:last-child`, `:only-child`, `:first-of-type`, `:last-of-type`, `:only-of-type`. They are read at compile time, on the tree of `@scene`, like the combinators (decision 73): no shader cost.

- **Siblings**: the elements of the same `@scene` block or group, groups (empty ones included) counted like objects. **The copies of a `* n` are siblings one by one** (confirmed by Lucas, Oct. 2): in `@scene { cube * 4; sphere; }`, `cube:nth-child(odd)` is cubes 1 and 3 and the sphere is child 5. `:nth-child()` and `sibling-index()` (decision 52) always count the same way.
- **Type** = the shape name (`cube`, `sphere`, `group`…), the tag of the element.
- **An+B** like CSS: `odd`, `even`, an integer, `n`, `-n+3`, `2n + 1` (spaces only around the sign of B), case-insensitive. Anything else is an error that shows the accepted forms.
- **`of S`**: a selector list, any selector except `:hover`; only the siblings that match S count, and the object must match S. Not on the `-of-type` forms, like CSS.
- **Specificity** like CSS: 100 per pseudo-class (a shortcut counts once, `:only-child` included), plus the most specific selector of `of S`.
- They combine with everything else: `:hover`, combinators, inside and around `:has()` (`group:has(> sphere:last-child)`).

**Differences from CSS**: none in the matching itself. `of S` refuses `:hover` for now (the order would change with the mouse; the picking pass would need an inverted trigger, like `:not(:hover)`), with a clear error.

**Why**: the vision example of GSS (`.corner:nth-child(odd)`) and every LLM write these selectors; with `* n` they style one copy out of two or three without a class per copy. Reading them at compile time keeps the cascade the only place that decides, and costs nothing at render.

## 93. `:not()`

**Decision**: `:not(<selector list>)`, like CSS (Selectors 4): the object matches when no selector of the list matches it. Any selector goes inside, complex ones included, read from the object outwards (`cube:not(#g cube)`: every cube outside `#g`), the structural pseudo-classes (decision 92) and `:has()` (`group:not(:has(sphere))`). Several `:not()` can follow each other. Read at compile time: no shader cost.

- **Specificity** like CSS: each `:not()` weighs like the most specific selector of its list (`:not(*)` weighs 0).
- **Errors**: an empty `:not()`; a face inside (a pseudo-element, invalid in `:not()` in CSS too); a leading combinator; a `:has()` reached through `:not()` inside another `:has()` (CSS forbids nested `:has()`).

**Differences from CSS**: `:hover` inside `:not()` is an error for now. `:not(:hover)` would be a trigger that switches off when its object is hovered: the picking pass and `uHover[]` can carry it (a slot that goes from 1 to 0), but the cascade would need a third state between rest and hover. Written the other way round (the rest state, and a `:hover` rule for the change), every case already works.

**Why**: the most written CSS pseudo-class after `:hover`; with `* n` and the structural pseudo-classes, it says "all but these" without a class on each object.

## 94. `currentColor`

**Decision**: the CSS keyword `currentColor` (any case, like CSS) is the object's own `color`, wherever a color is expected: in a color function (`color-mix(in oklab, currentColor 60%, white)`, `light-dark()`), in the stops of a gradient, as a material's color. It is replaced like a variable, after `var()` and before the math and the colors (decisions 52, 55, 58): the code generator never sees it.

- **The color it reads** is the object's `color` after `var()`, so `calc()`, `sibling-index()` and color functions inside it work. An object without `color` reads the initial `#e6e6e6`. In the hover state, it reads the hovered color.
- **In a variable**, it is read where the variable is used, with the color of the object that uses it (`scene { --shade: color-mix(in srgb, currentColor, black); }` darkens each object's own color): the same rule as every variable (decision 55).
- **As a material's color**, `metal(currentColor, 0.2)` is `metal(0.2)`: the material already takes `color` when it has none of its own (decision 26), so `color` stays animated, changes on `:hover`, and can be a gradient.

**Errors**: `color: currentColor` (also through a variable, inside a function or in a `@keyframes` frame) refers to itself; the scene has no color (`scene { floor: currentColor; }`); a gradient `color` mixed or placed in a stop (`color-mix()` of a gradient means nothing).

**Differences from CSS**: CSS resolves `color: currentColor` to the inherited color; GSS does not inherit `color` from a group, hence the error. Outside the material's own color, `currentColor` is read once, with the color at rest (or the hovered color in the hover state): a `@keyframes` that animates `color` does not move a `color-mix()` of it, since `material` is not animatable.

**Why**: one rule tints many objects of different colors (a lighter shell, a darker gradient) without a variable per object; with `:nth-child()` (decision 92), colors set per object and shared derived styles stay apart, as in CSS.

## 95. `:active`

**Decision**: `:active`, like CSS: the object is pressed, with the mouse button or a finger. It goes wherever `:hover` goes (decision 62): on the object, on a group (`#g:active cube`: pressing any object of `#g`), through combinators (`sphere:active + cube`), inside `:has()` (`#lamp:has(#switch:active) #bulb`). Same limits as `:hover`: the animatable properties only (plus variables and `transition`), objects not groups, not on a face, not inside `:not()` or `:nth-child(… of S)`. Specificity 100, like a class.

- **The press**, like CSS: the object under the pointer when the button goes down, until it goes up, even if the pointer leaves it (the button is listened to on the window). A touch has no hover before it: the press also aims the picking pass, and its first answer picks the object.
- **The pressed state is drawn over the hovered one**: a pressed object is under the pointer, so its styles are the cascade with the `:hover` and the `:active` rules. One more cascade per object, `activeStyles`, next to `hoverStyles`, with its own triggers (`activeTriggers`).
- **The shader**: `:active` reuses `uHover[]`, with slots of its own after the hover slots, and the same picking pass. A property is `mix(mix(rest, hovered, uHover[h]), pressed, uHover[a])`; a layer that changes nothing is left out. A scene without `:active` compiles exactly as before (shaders compared byte for byte on every scene and example), and the WGSL lowering, the uniform layout and the Shadertoy export (every slot at 0, at rest) do not change.
- **`transition`**: pressing takes the transition of the pressed state, releasing the one of the hovered state, like CSS (the transition of the state the object goes to).
- `CompiledScene.active`: for each `:active` slot, the ids that set it to 1; absent when the scene has no `:active`.

**Differences from CSS**: the same approximations as `:hover` (one hovered and one pressed state per object, the triggers of all its rules together). A rule with both (`cube:hover:active`) is read as pressed.

**Why**: the second interaction a designer reaches for after `:hover`: buttons, switches, a scene that answers a tap on a phone, where `:hover` does not exist.

## 96. `animation-timeline: scroll()` and `view()`

**Decision**: scroll-driven animations, with the syntax of CSS: `animation: spin 1s linear; animation-timeline: scroll();`. The progress of the timeline, from 0 to 1, replaces the time of the animation; `@keyframes`, easings and everything else do not change.

- **`scroll([root | nearest] || [block | inline | x | y])`**: the scroll of a scroll container, from its start to its end. `nearest` (the default, like CSS) is the closest ancestor of the scene that scrolls on that axis, across the shadow root of `<gss-scene>`; `root` is the page. **`view([block | inline | x | y])`**: the scene's canvas crossing its scroll container, 0 when its start edge enters at the end (the bottom), 1 when its end edge leaves at the start (the top). GSS writes horizontally: `block` is vertical.
- **Timing**, like CSS: the whole timeline is the whole animation. The duration and the delay do not count (the shorthand still needs a duration); the iteration count and the direction do. `infinite`, the GSS default (decision 70), plays once along a timeline. No fill mode is needed: the progress stays between 0 and 1.
- **The shader**: `uniform vec4 uTimeline`, one component per different timeline of the scene (4 at most, an error beyond), written only when the scene uses one, so every other scene compiles exactly as before (compared byte for byte). The progress replaces `iTime` in `playback()`: `uTimeline.x` alone for one normal iteration, `playhead(uTimeline.x * n, 1.0, n, dir)` otherwise. In WGSL, `timeline` comes after the `hover` array, so no other offset moves. Shadertoy shows the start (`const vec4 uTimeline = vec4(0.0)`).
- **The runtime** reads the progress every frame from the layout (`scrollTop`, `getBoundingClientRect()`): no scroll listener, and a container that starts scrolling is found. `CompiledScene.timelines` says what each component follows.
- **In the playground, the docs and the home page**, which do not scroll, a slider over the scene stands in for the scroll (`scrollSlider` option of the view); it shows only while the scene has a timeline and drives every timeline at once.

**Differences from CSS**: no `animation-range`, no named timelines (`scroll-timeline-name`, `view-timeline-name`, `timeline-scope`), no `view()` inset, no `self` scroller (the canvas does not scroll): each one is a clear error or not read yet. The writing mode is always horizontal. `@keyframes` time-based delays are ignored, as CSS does for scroll timelines.

**Why**: the scroll is how a page tells a story; a 3D scene that turns, opens or rises as you scroll is the most asked-for effect of landing pages, and CSS already has the syntax designers and LLMs know.

## 97. Motion path: `offset-path`, `offset-distance`, `offset-rotate`

**Decision**: the CSS motion path. `offset-path: path("…") | ray(<angle>) | none`, `offset-distance` (animatable: `@keyframes`, `:hover`, the scroll), `offset-rotate: [auto | reverse] || <angle>`. On objects and groups.

- **The plane** (Lucas, Oct. 2): the path is in the node's own **xy plane**, facing the camera, with the rules of the `path` shape (decision 35): centered on itself, y up, one path unit for one scene unit. A `path` shape and an `offset-path` with the same `d` draw a track and the way along it, one over the other. A path on the floor is a group turned with `rotate-x: 90deg`. (Claude first suggested the xz plane, before noticing that `path` and `prism` stand in xy.)
- **The order**, like CSS: translate, the rotations, scale, then the offset. `translate` moves the whole path, `scale` scales it.
- **`offset-distance`**: a number is a length along the path in its units (GSS has no `px`); a percentage is a share of its length. An open path stops at its ends; a path ending with `Z` is closed and goes round, like CSS. A ray has no length: a percentage is an error.
- **`ray(<angle>)`**: 0deg up, clockwise, like CSS (y up in the scene); no size keyword, no `contain` (the scene has no containing block).
- **`offset-rotate`**: `auto` (the default, like CSS) turns the node's x axis along the path; `reverse` the other way; an angle turns like `rotate-z`, added to `auto` / `reverse` when both are written.
- **The shader**: a fixed distance is computed at compile time (two lines on `q.xy`, constants; no turn when the direction is already x). A moving distance calls `offsetPathN(s)`, a function written per path, segment by segment like the `path` shape (cut 4 times finer than a prism, so the motion shows no corner), returning the point and the direction; it is computed once per pixel in `animate()` (decision 75). The bounding spheres grow by the reach of the path (decisions 66, 76, 77); a ray at a moving distance gives up its sphere.
- `offset-distance` or `offset-rotate` without `offset-path` is an error (CSS ignores them).

**Differences from CSS**: no `offset-position`, `offset-anchor` or `offset` shorthand, no basic shapes (`circle()`, `inset()`…) or `url()` as a path, no `ray()` size; the path is centered on itself like the `path` shape, not placed in a containing block. The direction changes by segment (the segments are short enough not to show).

**Why**: "make it follow this curve" is the next thing after keyframes, and designers draw curves in Figma: an SVG `d` becomes a trajectory with no math. With `animation-timeline: scroll()` (decision 96), an object travels along a path as the page scrolls.

## 98. `conic-gradient()`

**Decision**: `conic-gradient([from <angle>]? [at <position>]?, <color> [<angle> | <percentage>]{0,2}, …)` and `repeating-conic-gradient()`, like CSS (Images 4), wherever the other gradients go (decisions 81, 82): `background`, `color`, the first argument of a material.

- The angle turns clockwise from the top, like CSS, around the center of the gradient's box (the canvas, or the object seen from the front): `t = fract(atan(p.x, p.y) / 2π - from)`. The center itself, where the angle has no direction, is the first color.
- Its stops take angles as well as percentages, a full turn being 100%; the other gradients still refuse angles. Stops are completed, spread and repeated with the same code as the other gradients.
- `at <position>` is read by the code `radial-gradient()` already used, moved into `readPosition()` by cut and paste (shaders compared byte for byte on every scene and example).
- WGSL: `atan(y, x)` lowers to `atan2(y, x)`.
- The setup (`from`, `at`, the direction of a linear gradient, the shape of a radial one) is now read before the stops, so its error is the one reported.

**Differences from CSS**: colors are mixed in sRGB (like the other GSS gradients), no `in <colorspace>` interpolation; the center pixel is the first color.

**Why**: a color wheel, a pie chart, a dial, the sweep of a clock hand, the stripes of a beach ball: shapes that turn, which linear and radial gradients cannot draw.

## 99. The screen is not mirrored

**Decision** (Lucas, Oct. 2): the camera no longer mirrors the scene. Its right vector was `cross(up, forward)`, which pointed to −x: a scene was drawn as in a mirror, `translate: 2 0 0` on the left, `rotate-z` counterclockwise, and everything drawn in an object's own space (gradients, textures, `path` and `prism`, the motion path) flipped left to right. It is now `cross(forward, up)`, and `up` is `cross(right, forward)`.

- The axes are those of a CSS page: x to the right, y up, z toward the viewer. `rotate-x`, `rotate-y` and `rotate-z` turn like CSS `rotateX()`, `rotateY()` and `rotate()` (a positive `rotate-z` is clockwise). `ray()`, `conic-gradient()` and `linear-gradient(to right)` now show on screen what decisions 82, 97 and 98 described.
- `light` and `camera-angle` keep their meaning in the scene's space (azimuth 0deg on +z, 90deg on +x), so 90deg is now on the right.
- To keep the look of every existing scene, the scenes of the repo were mirrored in x (the x of `translate` and `camera-target`, the angles of `rotate-y` and `rotate-z`, the azimuth of `light` and `camera-angle`), and the runtime turns the camera the other way (`camera-spin`, the mouse drag, the Shadertoy export), so a spinning or dragged scene moves on screen as before. The default light becomes `-45deg 54.7deg` (from the upper left, in front), the light every scene had on screen.
- What an object draws in its own space was not mirrored: it now appears as written. The perfume label reads "S", the macro pad's labels and the pixel textures read the right way, the conic dial turns clockwise. The home logo drops the `rotate-y: 180deg` that compensated for the mirror.
- Checked by rendering the 222 scenes and examples before and after (WebGL2, SwiftShader, at 0 s and 1.3 s): 197 identical to the pixel; the others differ only by the content above, the `random()` examples, and the grain of frosted glass (a noise in world space).

**Accepted limits**: scenes written for 0.0.2 or earlier, and links shared before, show mirrored; the changelog says what to negate. The `random()` examples draw their mirror image.

**Why**: GSS takes the behavior of CSS where a CSS notion exists, and the mirror broke it everywhere x appears: `translate`, `rotate-y`, `rotate-z`, gradients, images, SVG paths. A logo pasted from Figma came out backwards.

## 100. The object filters are written before the lighting of metal, jelly and glass

**Decision**: in the shader, `grain()`, `objectFilter()` and `objectLayer()` are written just before the lighting of metal, jelly and glass (`shadeMetal()`, `trace()`…), no longer just before `main()`. `trace()`, which draws the reflections and refractions, calls `objectFilter()` (decision 84), and GLSL refuses a call to a function written further down: a scene with a pixel `filter` on an object and a metal, jelly or glass material did not compile on WebGL2 (`'objectFilter' : no matching overloaded function found`). WGSL accepts functions in any order, so WebGPU rendered it, and the fallback and the captures failed.

- A function placed above, not a prototype (`vec3 objectFilter(float id, vec3 c);`): the WGSL is lowered from the GLSL by a typed parser, and a prototype would have been one more construct for it to read.
- `gpu.test.ts` compiles a filtered object next to a metal on WebGL2. The test of decision 84 only read the shader's text.
- Every scene of `src/scenes/` and every registry example compiled before and after, in GLSL and WGSL: the shaders are the same, byte for byte, except the one scene that had the bug (`starorbit.gss`, in progress). Without metal, jelly or glass, the lighting section is empty and the filters stay where they were, just before `main()`.

**Why**: the reflections must see the filters of the objects they meet (decision 84), and the scene must compile on every backend.

## 101. `texture: element(#id)`: an HTML element as a live texture

**Status**: built (Oct. 3, Lucas: build it now, and come back to it after the origin trial ends on Oct. 20 if needed): the texture, the runtime, `<gss-scene>`, the docs examples with HTML, and the HTML tab of the playground. The choices below are Lucas's (Oct. 2).

**Decision**: `texture: element(#card)` paints a live image of an HTML element of the page on an object, like CSS `element()` (Images 4; `-moz-element()` in Firefox). It goes wherever `url()` goes: `texture`, and `::face()`. HTML and CSS make the content of a surface, GSS makes the world around it.

- **Always live, like CSS**: no `@texture` at-rule, no `update: once | auto | 30fps` property. The image is redrawn when the element's rendering changes, and only then.
- **Engine: HTML-in-Canvas** (WICG): the `layoutsubtree` attribute on the canvas, `texElementImage2D` (WebGL2), `copyElementImageToTexture` (WebGPU), and the canvas's `paint` event, which says when the element changed. The browser renders the element itself: real CSS, real fonts, nothing approximated.
- **The element is a child of the scene's canvas**, as the API requires: `<gss-scene>` takes its HTML children (other than `<script type="text/gss">`) as the sources, so `<gss-scene src="card.gss"><article id="card">…</article></gss-scene>`; with `mount()`, the page writes them inside the `<canvas>`. The element stays in the DOM, so it stays accessible.
- **Without the API**, the texture stays empty and the object shows its `color`, like an image not loaded yet (decision 59): no special case. No html2canvas: a heavy dependency that only approximates the rendering, and the runtime without the compiler must stay small.
- **The compiler stays pure**: an `element()` is one more texture slot (within the 16 of decision 59), filled by the runtime. The Shadertoy export leaves its channel empty, so the object shows its color (decision 60).
- **The playground gets an HTML tab from the start**, beside the GSS one, and a share link carries both. A registry example can carry HTML, so the docs' "Try it" shows it too.

**As built** (Oct. 3, checked in Chromium 153 with the `CanvasDrawElement` flag, which the GPU tests turn on):
- **The compiler**: `readTexture()` reads `element(#card)` into the slot `"element(#card)"`, one of the 16 (`sceneTextures()`); the shader samples it like an image, and the Shadertoy export leaves its channel empty.
- **The runtime, WebGL2** (`createTextureStore()`, `runtime/textures.ts`): a transparent pixel first; the canvas gets `layoutsubtree`, a `paint` listener and a `requestPaint()`, and each paint uploads every element with `texElementImage2D` (an element has no picture before its first paint: "No cached paint record"). The API moved during the trial: Chromium 148 to 150 take `(target, level, internalformat, format, type, element)`, Chromium 153 `(target, internalformat, element)` with `RGBA8`; the runtime picks by the function's length. `UNPACK_FLIP_Y_WEBGL` applies, so an element is oriented like an image. A restyle fires `paint`, so a changing element is uploaded again, and only then.
- **Finding the element** (`findElement()`): a descendant of the canvas, or an element that a `<slot>` inside the canvas shows. `<gss-scene>` keeps its canvas in its shadow root with `<canvas layoutsubtree><slot></slot></canvas>`: its HTML children stay in the page, with the page's styles, and are drawn from there (checked: a slotted element is drawn).
- **The docs**: an example of the registry can carry `html` (`Example.html`): the page shows it under the code, and "Try it" puts it inside its canvas (`docs/playground.ts`), whose renderer is WebGL2. `element()` has its own entry (`fn-element`, beside `texture`), and an entry of `FUNCTIONS` can say when it is computed (`computed`): the gradients and `noise()` at each pixel, `element()` by the browser, the others at compile time.
- **The playground**: an `html` tab beside `gss` (`#html`, CodeMirror with a small HTML reader, `runtime/html-language.ts`); what it holds is the content of the scene's canvas, so a change is drawn at the next paint. A share link carries it after the code, `#code=…&html=…` (`encodeCode(code, html)`, `decodeHtml()`), and a link without HTML is the one of always. An example of the menu brings its HTML (an example is a whole scene: none clears the tab), and "Open in playground" in the docs passes it on. With `auto`, a scene that opens with HTML or `element()` gets WebGL2; one that starts using `element()` on WebGPU shows a note in the status bar that says to choose WebGL2.
- **WebGPU**: no Chromium copies an element to WebGPU yet (neither `copyElementImageToTexture` of the trial nor `drawElementImageToTexture` of the latest explainer is there), so the slot stays a transparent pixel and the object keeps its color; `mountAsync()` with `backend: "auto"` draws a scene that uses an element with WebGL2 (`usesElements()`), and `<gss-scene>` uses WebGL2 by default.

**Differences from CSS**: CSS `element()` is an image anywhere an image goes (`background-image`…); in GSS it only goes in `texture`, not in `background`, `color` or a material.

**Why**: one line puts any existing web UI (vanilla, React, Vue…) on a 3D surface. `element()` is CSS's own notion, so an author or an LLM already knows it. This does not reopen decision 2: the HTML is the content of an image, objects are still declared in `@scene`.

**Accepted limits**: Chromium only while the API is in origin trial. Display only: a click on the 3D surface does not reach the HTML (mapping a pixel back through the projection is another project). The −x, −z and bottom faces are mirrored (decision 59), which shows on text: `::face(front)` avoids it. Reflections and glass do not see textures (decision 59). HTML that animates is uploaded to the GPU at every change.

## 102. Animated gradients: a gradient changes into another of the same kind

**Decision**: a gradient in `color` can be animated by `@keyframes` and changed by `:hover` / `:active` (with `transition`), which lifts a limit of decision 82. A gradient is read into its numbers (`readGradient()`, `shader/gradient.ts`): the angle of a `linear-gradient()`, the center of a `radial-` or `conic-gradient()`, the start angle of a conic one, and the position and color of each stop, once the stops are completed like CSS. Each number has a name (`channels()`: `angle`, `cx`, `cy`, `from`, `at0`, `color0`…), and `movingGradient()` (`codegen/gradients.ts`) gathers every value the property takes, at rest, in the frames of its animation and in each `:hover` / `:active` layer. A number that never changes stays a constant; one that changes becomes the expression `hoverValue()` already writes for any animated value, so easings, delays, directions, `scroll()` / `view()` and transitions apply as they do elsewhere. `linesOf()` writes the lines of the gradient from those numbers: a still gradient, or one whose animation touches something else, keeps exactly the lines it had (all 219 shaders of the scenes and registry examples are identical, byte for byte).
- **Through a variable**, the CSS way: `linear-gradient(var(--angle), …)` with `@keyframes spin { to { --angle: 1turn; } }`. The copies of decision 55 already turn the variable into frames that set `color`, so this needs nothing more, and one number moves alone.
- **A gradient into another**, written in a frame or a `:hover` rule: allowed when both have the same function (`linear-gradient()` stays linear, `repeating-` stays repeating), the same shape and size for a radial one, and as many stops once completed (a color with two positions counts twice). Otherwise an error says which: `a linear-gradient() can only change into another linear-gradient(), not a radial-gradient()`. A color does not change into a gradient, nor a gradient into a color.
- **The direction of a linear gradient moves as an angle**: a side is its CSS angle (`to left` is 270deg), a corner the angle of its diagonal, computed from the size of the box (`atan(x * size.y, y * size.x)`), so `to top right` can turn into `0deg`. The angle moves like a number: 0deg to 360deg is a full turn.
- **The positions** of moving stops are divided by `max(b - a, 0.00001)`, so two stops that meet never divide by zero; the period of a repeating gradient the same way.
- **getMaterial() keeps the mean color of the gradient at rest**: the color moves in `gradientColor()`, which the lighting and the reflections already call (decision 82).
**Why**: Lucas's first item after 0.0.3, and the first step toward flat, moving images (fields of color, posters) without a separate 2D mode: the vocabulary of images grows where it already is. One interpolation, written once, serves `@keyframes`, variables and `:hover`.
**Different from CSS**: browsers do not interpolate gradients today: a gradient in `@keyframes` or a transition jumps, and the CSS way is a registered `@property` used inside it. GSS interpolates two gradients of the same kind, number by number, and its variables already move like registered properties (decision 55). Colors are mixed in sRGB, like the stops themselves.
**Accepted limits**: the gradient of a material (`metal(linear-gradient(…))`) stays still, since `material` is not animatable: its color cannot change (an error that says to write the gradient in `color` and `metal(0.2)`). The keywords of a radial gradient (`circle`, `closest-side`…) do not change.

## 103. The scene plays an animation: its background

**Decision**: `animation` and its longhands apply to the scene too (`appliesTo: "everywhere"`), and `background` is animatable. On the scene, an animation changes the background and the variables of the scene: a color into another color, a gradient into another gradient (decision 102), or a gradient through a variable of the scene (`animateVariables()` makes a copy for the scene as for an object, decision 55). A frame that sets another property is an error: `On the scene, an animation only changes background and variables: translate is a property of objects`. A background that changes is written as `vec3 background(vec3 rd)` and `#define BACKGROUND background(rd)`, the form a gradient already had (decision 81), so the WGSL lowering needs nothing new; a background that does not change stays `const vec3 BACKGROUND`. `scroll()` and `view()` work on the scene: its styles join the timelines of the objects (`sceneTimelines()`).
**Why**: with the empty `@scene { }`, `floor: none` and `filter`, an animated background is a flat, moving image computed for each pixel, like a 2D shader: what Lucas wanted to explore, without a 2D mode. `background` and the background gradient already had the geometry; only the time was missing.
**Different from CSS**: in CSS, a custom property animated on `:root` moves everything that inherits it. In GSS, the objects do not follow a variable that the scene animates: each object plays its own animation, so it is the scene's background that moves, not the objects that read the same variable.
**Accepted limits**: the other properties of the scene (`light`, `ambient`, `floor`, the camera, `filter`) are not animated; a `var()` animated by the scene in one of them is an error (`light cannot be animated`). This lifts the limit of decision 55 for the scene's own properties only.

## 104. A computed value out of its range is clamped to it, like CSS

**Decision**: a value given by a math function (`calc()`, `sibling-index()`, `clamp()`…) that falls outside the range its property allows is clamped to that range instead of being an error. `color-mix(in oklab, #ff5a36, #3a7bff calc(sibling-index() * 40% - 20%))` gives 140% to the fourth copy: it is read as 100%. `toToken()` (`values/calc.ts`) marks each token it creates in a `WeakSet`, like the spans, and `clampComputed(token, min, max)` clamps a marked token and leaves any other as written; each check of a range calls it before it compares. A value written as is keeps its error (`color-mix(in srgb, red, blue 140%)`). It applies to every range with a bound that is allowed:
- `color-mix()` percentages, 0% to 100%;
- the amounts of `filter` functions, 0 or more;
- the x of `cubic-bezier()`, 0 to 1;
- a `transition` duration and `animation-iteration-count`, 0 or more;
- the numbers of GSS that allow 0 (`blend`, `ambient`, `corner-radius`), the radii of a cone, the frost of `glass()` (0 to 1) and `dpr` (0.25 to 4).
A range whose bound is excluded keeps its error, computed or not: no number is the closest to "more than 0" (`size`, `radius` of a sphere, an animation duration).
**Why**: a row of copies often walks a value past its end, and only the last copies go out of range: an error on the whole rule for them breaks the scene, where CSS would hold the value at its end. The rule is the one of CSS, so a stylesheet that works in a browser works here.
**Different from CSS**: none for the ranges CSS has. CSS clamps a computed value to the range even when the bound is excluded, as close as it can; GSS keeps the error there, since it has no such value. `blur()` takes a length in px, which math does not compute yet, so its length cannot go out of range.

## 105. `@property` and `setProperty()`: variables the page sets without compiling again

**Decision**: a variable registered with `@property`, like CSS, is set from the page at any moment without compiling the scene again: `scene.setProperty("--lift", "2")`, `getPropertyValue()`, `removeProperty()`, on what `mount()` / `mountAsync()` return and on the `scene` of `<gss-scene>`. Lucas's choices (Oct. 2): only registered variables (not a recompile of any variable), one value for the whole scene, and in the end everywhere a value reaches the shader.
- **`@property --name { syntax; inherits; initial-value; }`**: the three descriptors are required, like CSS (`readPropertyRules()`, `features/properties.ts`). The syntaxes GSS reads: `"<number>"`, `"<angle>"`, `"<percentage>"`, `"<color>"`, and `"<length>"` in px (third step); another one is an error that lists them. The initial value is checked against the syntax, after its colors and math are computed.
- **One value for the whole scene**, like a variable on `:root`: `scene { --lift: 2; }` gives its start value (it wins over `initial-value`); declaring it on an object, a group, a `:hover` / `:active` rule, a face or in a `@keyframes` frame is an error. `inherits` is read but changes nothing, since every object sees the scene's value.
- **In the shader**: `uniform vec4 uProperties[n]`, one `vec4` per registered variable, in the order of the rules: a number, an angle in radians or a percentage as written in `.x`, a color in `.rgb`. `var()` gives a token of its own (`EXPR`, never written by the tokenizer) whose GLSL is `uProperties[i].x` or `.rgb`; the readers of the properties (`liveRead()`, `codegen/properties.ts`, called by `animatedValue()`) write it where a number, an angle or a color would go, so `:hover`, transitions and `@keyframes` on the same property mix with it as with any value. `animate()` computes it once per pixel like the animated values. In WGSL, `properties: array<vec4<f32>, n>` after the timelines; the Shadertoy export writes the initial values as a constant array.
- **The runtime** (`runtime/properties.ts`, no compiler import) reads the page's value against the syntax: a string like CSS (`"90deg"`, `"0.25turn"`, `"50%"`), a number for a `<number>`, any CSS color read by the browser itself through a 2D canvas (named colors, `rgb()`, `hsl()`, `oklch()`, `color-mix()`…), in sRGB like the compiler. `getPropertyValue()` gives the value back like a computed CSS value (`"180deg"`, `"#ff0000"`), `""` for a variable the scene does not register. A value set stays when `update()` gives another scene, as long as the variable keeps its syntax. `CompiledScene.properties` lists each variable with its syntax and its 4 starting floats.
- **First step: where it can go**: `translate`, `rotate-*`, `scale`, `color`, `offset-distance` (a number, or a percentage of the path) and `background`, the values the shader already computes at every frame. Anywhere else it is an error that says where it can go, for now. An object that a registered variable moves gives up its bounding sphere (its place is not known at compile time), like a motion path whose reach is unknown.
- **Second step: inside math and colors**. In `calc()` and the math functions, a quantity that depends on a registered variable carries its GLSL instead of its value (`calc.ts`: `code` on a `Quantity`); the units are checked as before, what does not depend on it is still computed (`sibling-index()`), and the result is an `EXPR` token like `var()` gives: `calc(sibling-index() * var(--h))` is `(2.0 * uProperties[0].x)` for the second copy. Angles are in degrees inside math, like the other angles, and go back to radians for the uniform (`degrees()` and `radians()` cancel when they meet). `round()`, `mod()`, `rem()`, `hypot()`, `progress()`… have their GLSL; `random()` refuses it (a random value is chosen once, at compile time). In the color functions (`rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()`, `color-mix()` in its 8 spaces and both hue methods, `light-dark()`, `contrast-color()`), a registered variable turns the call into GLSL, with the same formulas and matrices as `color-spaces.ts` (`codegen/color-library.ts`, pasted only when used), clipped to sRGB like the colors computed at compile time; a GPU test renders each function with a variable and with the same value written as is, and finds the same color on WebGL2 and WebGPU. A percentage of `color-mix()` set from JS is clamped to 0–100%, and percentages that add up to less than 100% are normalized instead of being an error. Any other function around a registered variable is an error that names it. The WGSL lowering learned `trunc`, `tan`, `asin`, `acos`, `log`, `degrees`, `radians`, and no longer reads `vec3((…` as a function declaration.
**Why**: a page drives a scene from a slider, the scroll or its data, the way it drives CSS with `element.style.setProperty()`. A uniform costs nothing to change, needs no compiler in the page (`gss-lang/runtime` keeps working), and a scene without `@property` compiles exactly as before: all 219 shaders of the scenes and registry examples are identical, byte for byte.
**Different from CSS**: in CSS, any custom property can be set and `@property` only types it; in GSS, `setProperty()` on a variable the scene does not register is an error, since only a registered variable is a uniform. One value per scene, not per element. The syntaxes are limited to the five above, without combinations (`"<number> | <angle>"`), and a `<length>` is only in px.
- **Third step: everywhere a value reaches the shader**. The shapes, gradients, textures, materials and lights compute with `Num` (`codegen/live.ts`): a number known at compile time, or GLSL; two numbers give a number written as before, so a scene without `@property` keeps its exact shader. The sizes of the shapes (`radius`, `size`, `height`, `thickness`, `corner-radius`, `stroke-width`, `depth`) are kept above 0 (`max(x, 0.0)`), a capsule too short becomes a sphere instead of an error; the object then has no bounding sphere, nor the scene. The numbers of a gradient (angle, center, start, stop positions and colors) are written in GLSL like the numbers an animation moves (decision 102); a position that never goes back becomes `max()`. The settings of a material are clamped to their range, the gradient box and `texture-size` follow the size. `floor`, `ambient` (and the direct light, `1 - ambient`), `light` (a function `lightDirection()` and `#define LIGHT_DIR`, since a GLSL constant cannot read a uniform; the WGSL lowering now replaces every object-like `#define`, word by word, which also covers `BACKGROUND`), `camera-target`, `blend` (always smooth, never 0, and the scene gives up its sphere since its reach is not known), `offset-rotate` and the filters. Filters read amounts and angles (their color matrices computed on the GPU) and a new `"<length>"` syntax in px for the radius of `blur()` and `bloom()`; a pass that reads a variable declares the uniforms of the scene before it (`withProperties()`), in the same order, so its WGSL reads them where the scene writes them in the buffer they share, and the WebGL passes receive `uProperties[]`. GPU tests render each kind of value with a variable and with the same value written as is (shapes, gradients, materials, lights, blends, filters in the scene's shader and in the passes), and find the same image on WebGL2 and WebGPU.
**Not read when the scene runs**: what builds the scene at compile time (the copies of `* n`, `d`, `view-box`, `operation`), the timing of animations and transitions, the camera the mouse moves (`camera-distance`, `camera-angle`, `camera-spin`) and `dpr`, which the runtime reads once. A variable there is an error that names the property and lists those that take one. A registered variable cannot be set by `@keyframes` or `:hover` (the page owns it); a frame or a `:hover` rule can read it.

## 106. Nesting with `&`, unfolded by the parser

**Decision**: a rule can hold rules, like CSS Nesting: `#g { color: red; cube { &:hover { … } } > sphere { … } }`. The parser unfolds them into flat rules (`parseRuleBlock()`, `syntax/parser.ts`), so the cascade, the validation and every later step see only flat selectors, as before. `&` is a token of its own (`PUNCT`), replaced by the selector of the rule around it (`nestSelector()`, `syntax/nesting.ts`); a nested selector without `&` gets the parent and a space in front (`cube` is `#g cube`, `> sphere` is `#g > sphere`), and an `&` inside `:has()` or `:not()` counts as one. A parent list and a nested list give every pair, parent first. A nested item is a rule when a `{` comes before the next `;` or `}`, otherwise a declaration. The declarations after a nested rule become another rule after it, so the order of the text is the order of the cascade (CSS's nested declarations). `@media` goes inside a rule, with declarations and rules; inside another `@media`, the two queries are joined with `and`, and a list of queries (`,`) there is an error. `@scene`, `@keyframes` and `@property` inside a rule are errors, and so is `&` outside a rule. A rule that holds only nested rules gives no rule of its own; a block without nesting gives exactly the rules it gave before (all 246 shaders of the scenes and registry examples are identical, byte for byte).
- **The spaces**: the descendant combinator is read from the positions of the tokens in the source (`spaceBetween()`, moved from `cascade/resolve.ts` to `syntax/nesting.ts`). Where the parent meets the nested selector, the positions say nothing (`&:hover` puts `.a` next to `:hover`, far apart in the text): the token after the meeting point is copied, keeps the position of the original for the errors, and carries whether a space was written (a `WeakMap`, like the spans).
- **The editor**: autocompletion composes the selector of a nested rule the same way, and offers its properties; the VS Code grammar reads nested blocks, `&` and `@media`.
**Why**: Lucas's third item after 0.0.3. Unfolding in the parser costs nothing at run time and leaves the cascade untouched.
**Different from CSS**: in CSS, `&` is `:is(<the parent list>)`, so with `#a, .b { & cube { } }` both `#a cube` and `.b cube` weigh like `#a cube`. GSS has no `:is()` yet: each pair keeps its own specificity (Lucas's choice: the simple unfolding). The two only differ for a parent list whose selectors weigh differently. GSS reads `&` at the top of the file as an error, where CSS reads it as `:scope`.
**Accepted limits**: no `:is()` / `:where()`; a `@media` with a list of queries cannot hold a nested `@media`; nesting is not allowed in `@keyframes` or `@scene`.

## 107. `transform-origin`: the point an object turns and scales around

**Decision**: `transform-origin` takes the syntax of CSS: one or two of `left`, `center`, `right`, `top`, `bottom`, a percentage or a number, then a number for z; two keywords come in any order (`top left`). It goes around every other transform, like CSS (translate by the origin, then `translate`, the rotations, `scale` and the motion path, then back): in `map()`, `q -= <origin>` comes after the object's `translate` and `q += <origin>` after its motion path (`transformLines()`, `codegen/transforms.ts`). The motion path carries the origin along the path, as CSS does with `offset-anchor: auto`. A value at the center (`center`, `50% 50%`, `0 0 0`, or nothing) writes no line, so every shader without `transform-origin` is identical, byte for byte (249 shaders of the scenes and registry examples). It is animatable (`@keyframes`, `:hover`, `:active`) and reads `@property` variables of syntax `<number>` and `<percentage>`.
- **The box**: keywords and percentages are read on the box of the object (`objectBox()`, `codegen/origin.ts`): `size` for a cube, `2r` on each axis for a sphere, `2r × h × 2r` for a cylinder, a capsule or a cone (its largest radius), `2(r + t) × 2t × 2(r + t)` for a torus lying in the xz plane, `w × 0 × d` for a plane, the box of the bounding sphere for a path and a prism. `left` and `0%` are its left side, `top` and `0%` its top, y up. The box is computed only when a keyword or a percentage asks for it.
- **A group** has no box: it takes numbers and `center`; a keyword or a percentage is an error that says so (Lucas's choice).
- **The bounding spheres**: an object turned and scaled around its origin stays within its radius plus the distance to the origin, around the origin: its own sphere in `map()` is tested at `length(q - <origin>)` with that radius, and the sphere of the scene (`objectSphere()`, `codegen/bounds.ts`) moves to the origin before the scale and the rotations, and back after them. An origin that is animated, changed by `:hover` or set from JS gives up the object's own sphere (the object is then always computed), and the scene's sphere when its points are not known at compile time.
**Why**: Lucas's fourth item after 0.0.3: a door on its hinge, a bar that grows from the floor, a hand of a clock, without wrapping the object in a group moved to the pivot.
**Different from CSS**: in CSS, a length is measured from the top left corner of the box, y down. In GSS, a number is a point of the object's own space, from its center and y up, like `translate` and every position in GSS; it also works on a group, which has no box (Lucas's choice). The keywords and the percentages are those of CSS. There is no `transform-box`: the box is the shape's own.
**Accepted limits**: a group takes numbers only; the box of a path or a prism is the box of its bounding sphere, not of its outline.

## 108. `fog`: the scene fades with the distance

**Decision**: `scene { fog: none | [<color>] <start> <end> }`, `none` by default (Lucas's choices for each point below). The distances are measured from the camera, along the ray: no fog before the start, only fog after the end, linear between (`fogAmount(t)`, `codegen/fog.ts`). In `main()`, after the lighting and the reflections of the material and before the filters of the scene, `col = mix(col, <fog color>, fogAmount(t))`.
- **Without a color**, the fog color is `BACKGROUND`: each object fades into the background seen behind it, a gradient or an animated background included, and the background itself does not change (it is mixed with itself).
- **With a color**, `fogAmount()` is 1 for a ray that meets nothing (`t >= MAX_DIST`), so the background becomes the fog color too: past the end of the fog, only the fog is seen, even when the fog ends beyond the scene. The color comes first or last, a hex color, a name (`tomato`, read where a color is expected among the distances) or a color function.
- **Moving**: `fog` is animatable on the scene, with `animation` or through the variables of the scene, like `background` (decision 103 now lets a frame of the scene set `fog`). `none` is a fog that starts and ends at `MAX_DIST` with the background as its color, so an animation can move from `none` into a fog. A color and the background mix between frames too. `fog` reads `@property` variables (`<color>` and `<number>`), kept at 0 or more on the GPU.
- **The values**: the start and the end are numbers, 0 or more, the end not before the start (an error otherwise; a computed distance below 0 is 0, decision 104). The same start and end give a sharp edge (`step()`). Two known distances write `clamp((t - start) / (end - start), 0.0, 1.0)` with the difference computed; otherwise `max(end - start, 0.00001)` divides.
- `fog: none`, or no `fog`, writes nothing: every shader without fog is identical, byte for byte (251 shaders of the scenes and registry examples).
**Why**: Lucas's fifth item after 0.0.3: depth in a scene, and a way to hide the sharp end of the floor 20 units away.
**Different from CSS**: CSS has no fog; its syntax follows the shorthands of CSS (a color first or last, then numbers), and the docs say the scene ends 20 units from the camera.
**Accepted limits**: the fog is applied once, to what the camera sees: the reflections and refractions show the objects without fog, and the background they reflect is the scene's own, not the fog color. The fog is linear (no exponential density) and the same at every height (no ground fog). The colored lights of the next step may tint it later.

It covers `setProperty()`, `getPropertyValue()` and `removeProperty()` on what `mount()`, `mountAsync()` and `gss-lang/runtime` return and on the `scene` of `<gss-scene>`, the values each syntax takes, the error where CSS would ignore a value, the value kept by `update()`, and the trap of `<gss-scene>`: `scene` is `null` until `load`, and `load` comes again with each new scene, which starts from its start values.

## 110. Several lights, and colored lights: `light` elements in `@scene`

**Decision** (Lucas's choices for each point): a `light` in `@scene` is a point of light, styled like an object and never drawn: `@scene { group#lamp { sphere#shade; light#bulb; } }`, `#bulb { translate: 0 1.1 0; color: #ffd27a; intensity: 3; }`. The sun stays `scene { light }`, which now takes a color and an intensity after its two angles (`light: -45deg 54.7deg #ffd27a 0.8`, in any order) and `none`, which turns it off; adding a light never changes the sun. `ambient` takes a color after its number (`ambient: 0.2 #9db4ff`).
- **A light is an instance**: it goes through the cascade, the variables, the animations and the hover slots like an object (`hoverSlots()` sees it), but `generateShader()` splits it from the objects (`isLight()`, `codegen/lights.ts`): no `map()` line, no material, no texture, no filter, no bounding sphere, not counted in the objects of the scene. It takes `color` (the color of its light, white by default, a plain color), `intensity` (new, 1 by default), `translate`, the rotations and `transform-origin` (numbers only: a light has no size), the motion path, `animation` and `transition`; any other property on `light` is an error (`validate.ts`), like a property of another shape. It cannot be hovered or pressed, since it is never drawn (`drawn()`, `resolve.ts`): `#lamp:hover light` works, `light:hover` is an error; hovering a group never counts its lights. A scene has 8 lights at most (`MAX_LIGHTS`).
- **Where it is**: the transforms of `map()` move a point into the space of an object; a light needs the other way. `forwardLines()` (`transforms.ts`) and `offsetForwardLines()` (`offset.ts`) undo the lines of `transformLines()` and `offsetLines()` in the reverse order (rotations by the opposite angle, z then y then x), on `v`, for the light then each of its groups from the inside out. Each light gets `vec3 lightPositionN()`, called once per pixel by `animate()` into the global `lightN` (`animateCode()` takes these functions, written after the globals they read).
- **How much light**: `lamp(at, p)` gives the direction toward the light and the share that reaches `p`: 1 at 1 unit, then 1 / distance² (Lucas's choice: the inverse square, like three.js), the distance squared kept above 0.01. A light gives `color × intensity`, computed now when both are known, in `animate()` otherwise.
- **The lighting**: when the scene has a light, a colored or changing sun, `light: none` or a colored ambient light, `diffuse(n, color)` becomes `diffuse(p, n, color) = color × (AMBIENT_LIGHT + lighting(p, n))`, where `lighting()` adds `(1 − ambient) × SUN × max(dot(n, LIGHT_DIR), 0)` (the sun as before, `SUN` = its color × intensity) and each light. The highlights of metal, jelly and glass, which read `LIGHT_DIR`, are rewritten to add up every light (`lightShine()`, `lightWrap()`, `lightBump()`, written only when used): `rewrite()` replaces their few known lines, and an internal error says if a line reading `LIGHT_DIR` was left without a sun. Otherwise the shader is the one of always, line for line: all 254 shaders of the scenes and registry examples are identical, byte for byte. A white sun written in full (`light: -45deg 54.7deg #ffffff 1; ambient: 0.5 #ffffff`) renders the image of always on WebGL2 and WebGPU.
- **Moving**: a light plays animations and changes on `:hover` / `:active` through its group, like an object; the scene animates its sun (decision 103 now lets a frame of the scene set `light`, which lifts its limit for the sun): the direction moves as a normalized mix of vectors, and `none` is a sun of intensity 0, so it can rise. `intensity` and the color of a light read `@property` variables (`LIVE_PROPERTIES`), as the sun already did.
**Why**: Lucas's eighth item, brought before the noise function: a lamp, a warm and a cold light, a light that turns, a scene at night. As elements of `@scene`, lights follow their groups, play animations and answer `:hover`, with nothing new to learn.
**Different from CSS**: CSS has no lights. SVG has `fePointLight` with `lighting-color` on the filter that lights; GSS takes the element and gives it the `color` an element already has. `light: azimuth elevation` stays close to `feDistantLight`.
**Accepted limits**: point lights only (spots later), no shadows (the light goes through objects), 8 lights at most, the fog is not tinted by the lights, a light is never drawn (a shape stands for the bulb).

## 111. `noise()`: a gradient whose colors are placed by a 3D noise

**Decision** (Lucas's choices for each point): `noise([turbulence]? <scale> <octaves>? [seed <n>]? [at <x> <y> <z>]?, <color stops>)` goes wherever a gradient goes (`background`, `color`, the first argument of a material), modelled on SVG `feTurbulence`: the scale is how many patterns fit in a unit (`baseFrequency`), the octaves (1 to 8, 1 by default) add detail twice as fine each (`numOctaves`), `turbulence` folds each octave at 0 for sharp creases (`type="turbulence"`; soft fractal noise otherwise), `seed` draws another pattern, `at` moves it. Its colors are the stops of a gradient, completed like CSS (`readStops()`): a noise is a gradient whose position `t` comes from the noise instead of a place in the rectangle.
- **One more gradient**: `noise` is in `GRADIENT_FUNCTIONS`, so everything that takes a gradient takes it, with no new path: `readGradient()` reads its setup (`readNoise()`, `shader/gradient.ts`) into `Gradient.noise`; its kind, octaves and seed are its `shape`, which an animation cannot change; `noiseT()` writes `t = fractalNoise((point + at) * scale + seed, octaves)` (or `turbulenceNoise`), and the stops follow as for any gradient.
- **Where it is read** (`linesOf(…, point)`): on an object, `q`, the point in the object's own space, in 3D: a block of matter cut in the object, with no seam, that turns and moves with it; in the background, `rd`, the direction of the ray (reflections see it where they point).
- **The noise** (`codegen/noise-library.ts`, written only when used): gradient noise (a random slope at each point of a grid, quintic blend, like Perlin's, which `feTurbulence` uses), summed over the octaves; the sum is divided by its spread (the square root of the summed squared strengths), so more octaves add detail without washing out the colors, then stretched to 0–1 (measured: the 2nd to 98th percentiles fall between about 0.02 and 0.98).
- **Moving**: like the other gradients (decision 102), `scale`, `at`, the stops and the colors move with `@keyframes`, `:hover` and `:active`, and read `@property` variables; animating `at` makes the noise drift.
**Why**: Lucas's seventh item: clouds, stone, marble, smoke without images, and the first step toward 2D compositions (layers of `background`, masks, displacement) rather than a separate 2D mode.
**Different from CSS**: CSS has no noise image. SVG `feTurbulence` gives four channels of noise to filter further; GSS places colors on one channel, like a gradient, which is what a designer reaches for first.
**Accepted limits**: no `stitchTiles`; one channel; the noise of a material does not move (material is not animatable); a 3D noise on a flat face shows a slice of it.

## 112. The layers of background, and `background-blend-mode`

**Decision** (Lucas: the order that makes the most sense, and transparency in the layers): `background` takes several layers, like CSS, the first on top, the last one a color or an image: `background: noise(2 4, #ffffff00 45%, #ffffff 80%), linear-gradient(#2f6bd8, #9fc4ff);`. The colors of these layers can be transparent, which is the only place GSS has transparency: `transparent`, `#rrggbbaa` and `#rgba`, an alpha after `/` in `rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()` and `color()`, and a `color-mix()` whose percentages add up to less than 100% (its alpha is their sum, like CSS). `background-blend-mode` gives each layer one of the 16 modes of CSS (Compositing and Blending 1), the list repeated over the layers.
- **Reading**: `resolveColors(value, scheme, alpha)` lets the colors of `background` keep their alpha (`colorsOf()`), written as `#rrggbbaa` (`toHash()`); elsewhere a transparent color is the error of always, now "GSS has no transparency yet, except in the layers of background". A layer is read by `readGradient(value, alpha)`: its stops are premultiplied `vec4` and mixed so, like CSS, and its lines give `vec4 col` (`Gradient.alpha`, `opaque4()`). `isGradient()` says no to a list of layers instead of failing on it.
- **Drawing** (`layeredBackground()`, `codegen/gradients.ts`): each image layer is a function `vec4 backgroundLayerN(vec3 rd, vec2 at, vec2 size)`; `background()` starts from the base (the last layer when it is a color, composited over the default background when it is transparent; the default background `#080808` otherwise) and puts the layers over it from the bottom up: `normal` is the premultiplied over (`col * (1 - a) + layer.rgb`), any other mode `mix(col, blend(col, unpremultiply(layer)), layer.a)`, the backdrop being opaque. The blend functions (`codegen/blend-library.ts`) are those of the spec, the separable ones channel by channel, `hue`, `saturation`, `color` and `luminosity` with its `SetLum`, `SetSat` and `ClipColor`; only those a scene uses are written. A background of one opaque layer keeps the shader of always (all 268 shaders of the scenes and registry examples are identical, byte for byte).
- **Moving**: each layer moves like a gradient (decisions 102, 103): `movingGradient()` reads one layer of every value the background takes (`options.layer`); a background keeps its number of layers when it changes (an error says so), and its base color moves like a color.
**Why**: the first step of the 2D compositions of Lucas's seventh item: clouds over a sky, a grain over a gradient, two noises screened, without images.
**Different from CSS**: CSS paints the layers over a transparent canvas, and the page shows through; a GSS scene is opaque, so they go over the default background. Only the layers of background take a transparent color, not the objects, the materials or the floor. A transparent color inside `color-mix()` is not read yet.
**Accepted limits**: no `background-size`, `background-position` or `background-repeat` (a layer covers the canvas, like a gradient); the blend modes are for the layers of the background only, not for objects (`mix-blend-mode`).

## 113. `mask-image`: holes in an object

**Decision** (Lucas: sharp holes, of three options: holes, a real fade, a mask of the whole scene): `mask-image` on an object cuts holes in it, like a CSS mask: `sphere { mask-image: noise(4 3, black 48%, transparent 52%); }`. The image is a gradient or a `noise()`, read like a gradient in `color` (decision 82): seen from the front in the object's own space, `noise()` in 3D. Its colors can be transparent, like those of the layers of background (decision 112), and the errors elsewhere now say "GSS has no transparency yet, except in background and mask-image". `mask-mode` says what counts, like CSS: `alpha`, which the initial `match-source` means for a gradient, or `luminance` (the brightness times the alpha, with the coefficients of CSS Masking). Where the mask covers less than half of the surface, the surface is not there.
- **Reading** (`codegen/masks.ts`): `objectMask()` reads the mask of an object through `movingGradient()` with transparent colors, so it moves with `@keyframes`, `:hover` and the variables like a gradient in color (`mask-image` is animatable, and a variable set from JS can go in it); it cannot change from or into `none`. `maskCode()` writes `maskAlpha(id, p)`, the alpha (or the luminance) of the premultiplied color at a point of the object's space (`spaceN()`, written once per object, also when the object is painted or textured), and `hasHoles(id)`.
- **Marching**: in a scene with holes, `march()` has another loop (`MASKED_MARCH_LOOP`; the template's loop moved into `MARCH_LOOP` for it, which changes no shader). At a surface the ray stops if `maskAlpha() >= 0.5`, and goes on through a hole by small steps; it moves by `abs()` of the distance. While it marches, an object with holes is a skin: `shell()` takes `abs()` of its distance in the union when `throughHoles` is set, so an object inside it is not swallowed by its inside and shows through a hole. A subtracted or intersected object stays solid. The reflections of `trace()` and the picking pass use `march()`: they see the holes, and the mouse goes through a hole to the object behind it.
- **Lighting**: `holeNormal(p, rd, id)` replaces `calcNormal(p)` in `main()` and `trace()`. An object with holes takes the normal of its own distance; an object inside one takes the normal of the scene of skins, its own. The inside of an object, seen through a hole, has its normal turned toward the ray.
- A scene without `mask-image` keeps its shader: the 271 shaders of the scenes and registry examples are identical, byte for byte.
**Why**: the second step of the 2D compositions of Lucas's seventh item, and an effect of its own in 3D: lace, perforated metal, a dissolve (the stops of a `noise()` that move), a window into an object.
**Different from CSS**: a CSS mask fades the element by its alpha; GSS cuts at half, so the edge of a hole is sharp, like the silhouette of an object (a fade needs transparency in the objects, which GSS does not have). One image: no list of masks and no `mask-composite`; no `url()` image yet; no `mask-size`, `mask-position` or `mask-repeat` (the image covers the object like a gradient in color). On objects only: like `color`, it does nothing on a group.
**Accepted limits**: a ray that crosses holes takes more steps (the loop goes up to 200 instead of 100); glass and jelly see their inside without the holes; an object touching the skin of one with holes can take the skin's normal where they touch.

## 114. `displace()`: an image moved by a map, like `feDisplacementMap`

**Decision** (Lucas: an image function, of three options: an image function, a filter on the rendered image, a deformation of the shape): `displace(<image>, <map>, <amount>)` goes wherever a gradient goes, the color of an object or of a material, the background and its layers, `mask-image`: `color: displace(repeating-linear-gradient(45deg, #f4f1ea 0% 9%, #9a9385 10%, #f4f1ea 11%), noise(turbulence 1 4, black, white), 0.35)` is marble. The image is a gradient or a `noise()`. The map, a gradient or a `noise()`, is read at each point, and its colors move the point where the image is read, like `feDisplacementMap` with `xChannelSelector="R"` and `yChannelSelector="G"`: on a gradient, red moves it to the right and green down (y down, like SVG), by `amount × size × (channel − 0.5)`; on a `noise()`, read in 3D, red, green and blue move it along x, y and z. The amount is a share of the size of the image, a number or a percentage like the amounts of `filter`, so the look does not depend on the size of the object; in the background, a `noise()` follows the view, where the height of the canvas is 1 / 1.5.
- **A `noise()` map is a turbulence**: SVG `feTurbulence` draws each channel with a noise of its own; a GSS `noise()` places one value on its stops, so its red and green would be the same, and a gray map would move the image along one diagonal only (stripes at 45° along it did not move at all, seen in a capture). As a map, a `noise()` gives each channel a noise of its own, its seed then the next ones, like `feTurbulence`: a gray noise moves the image in every direction. A gradient map is read once, by its colors.
- **Reading** (`shader/gradient.ts`): `readGradient()` reads `displace()` into the `Gradient` of its image, with `displace: { map, amount }`; the map is read like a layer, so that a transparent color is an error of its own (its colors are opaque). `channels()`, `channel()` and `fromJs()` name its numbers `amount` and `map.…`, so `movingGradient()` moves them like those of a gradient (decision 102), with `@keyframes`, `:hover` and the variables set from JS; `sameKind()` keeps the kinds of the image and of the map. `displace` joins `GRADIENT_FUNCTIONS`.
- **Drawing** (`displaceLines()`): before the lines of the image, a block reads the map into `move`, each read in a block of its own so that its `t` and `col` are not the image's, then moves `at` (a gradient), `q` (a `noise()` on an object) or `rd` (a `noise()` in the background). No pass and no change of the shape: one more read of a gradient map at a pixel, two or three of a `noise()` map.
- A scene without `displace()` keeps its shader: the 275 shaders of the scenes and registry examples are identical, byte for byte.
**Why**: the last part of Lucas's seventh item, the 2D compositions (layers, masks, displacement): marble, wood, water, clouds drawn out, the ragged edge of a mask, without images.
**Different from SVG**: no channel selectors (red for x, green for y, blue for z in 3D); a `noise()` map draws each channel with a noise of its own, like the output of `feTurbulence`, not one color through its stops; the amount is a share of the size of the image, not a length in pixels, since an image on an object has no pixels; the colors of the map are read as they are, opaque, not in linearRGB (`color-interpolation-filters`). Like SVG, the map is read at the point of the result.
**Accepted limits**: one `displace()` per image (its image cannot be another `displace()`); not for `texture: url()` or `element()`; a moved gradient on an object can show the gradient past its box, which goes on like its first and last stops.

## 115. Shadows: `scene { shadows: none | hard | soft }`

**Decision** (Lucas, for each point: soft shadows as the next step, the keywords `none`, `hard` and `soft`, every light casting shadows, the reflections without them): `scene { shadows: soft; }` lets the objects cast shadows, on the floor and on each other. `none`, the default, keeps every scene as it was. Each point that `main()` shades sends a ray toward each light, the sun and the lights of `@scene` (up to the light, for a light of `@scene`); an object on the way keeps that light from it, so only the ambient light is left. `soft` draws a penumbra that grows with the distance to the object that casts it, Inigo Quilez's soft shadows (`min(lit, 12 h / t)` along the ray); `hard` is all or nothing.
- **Code** (`codegen/shadows.ts`, `codegen/lights.ts`): `readShadows()`; `shadowFunction()` writes `shadow(ro, rd, far)`; with shadows, `lightingCode()` never returns null (even for the white sun of always, whose light is then the same), declares a factor per light (`sunLit`, `lit0`…, 1 by default) and `castShadows(p, n)`, which `main()` calls once, right after the normal, starting each ray a little off the surface. Every sum of the lights, `lighting()` and the highlights of metal, jelly and glass, multiplies each light by its factor.
- **The reflections and the refractions** see the objects without shadows, like without fog (decision 108): `trace()` calls `diffuseOpen()`, made of `lightingOpen()`, the same sum without the factors. This also keeps the factors of the point `main()` shades: `trace()` does not compute any.
- **The holes of mask-image** (decision 113) let the light through: in a scene with holes, `shadow()` goes through the skins like `march()` (`throughHoles`, `abs()` of the distance, a surface stops the light only where `maskAlpha() >= 0.5`). A ray through a hole passes right by the skin, which would darken it with the penumbra: an object with holes casts a sharp shadow (`hasHoles()`), lace on the floor.
- A scene without `shadows` keeps its shader: the 278 shaders of the scenes and registry examples are identical, byte for byte.
**Why**: the most visible gain for the 3D scenes once Lucas's list of Oct. 2 was done; opt-in, since each light costs one more ray per pixel ("Shadows on by default or not" is still open: off by default for now).
**Different from CSS**: CSS has no cast shadows (`box-shadow`, `text-shadow` and `drop-shadow()` are drawn shapes); GSS's own property, like `fog`.
**Accepted limits**: one setting for every light (no `light { shadows }` yet); one softness; the reflections and the refractions without shadows; an object with holes casts a sharp shadow; glass and jelly cast shadows like opaque objects (no light through them, no caustics); each light costs a ray of up to 64 steps per pixel.

## 116. `opacity`: transparent objects, over what is behind them

**Decision** (Lucas, for each point: the transparency of the objects next, all of it like CSS, of which this is the first part, `opacity`, the transparent colors and `opacity()` coming in decision 117; behind a transparent object, its back face then what is behind it; colored shadows; on a group, multiplied into each object): `opacity: <number> | <percentage>` on an object, like CSS, from 0, invisible, to 1, opaque and the default; a value outside is kept between them, like CSS.
- **Drawing** (`codegen/transparency.ts`): in a scene with a transparent object, the lit surface of the template (`SURFACE`, moved out of `main()` into a constant for this, which changes no shader) goes into a function, `shadeSurface(ro, rd, t, id)`, with its fog and the filters of its object; `main()` draws the surfaces along the ray from the front, each over what is behind it (`LAYERS`, premultiplied: `col += (1 − cover) × a × c`), up to 6, the background or the 6th surface covering what is left. `pastSurface()` takes the ray out of the surface it met, and `march()` goes on from there. `t` and `id` stay those of the first surface, which the picking and the passes of the filters read: the mouse points at a transparent object, like CSS.
- **Skins**: a transparent object is a skin while the ray marches, like an object with holes (decision 113): `shell()` in `map()`, `abs()` of the distance in `march()` (`SKIN_MARCH_LOOP` when the scene has no holes), and `holeNormal()` asks `isSkin()`, which lists the objects with holes and the transparent ones. So its back face shows from the inside, and so does what is inside it.
- **Opacity**: `surfaceAlpha(id, p)`, the object's opacity times those of its groups (`objectAlpha()`), the numbers known now multiplied now. It moves with `@keyframes`, `:hover` and `transition`, and can be set from JS.
- **Shadows** (decision 115): the light goes through a transparent object like through stained glass. `shadow()` then gives a color: each surface it crosses, once, multiplies it by `mix(1, color, a)`, what the surface does not cover passing untinted and what it covers taking its color (`surfaceColor()`), and in the last tenth before opaque, `min(10 × (1 − a), 1)` brings it down to the black shadow of an opaque object. The factors of the lights become `vec3`. Only the solid objects draw a penumbra.
- A scene without `opacity` keeps its shader: the 281 shaders of the scenes and registry examples are identical, byte for byte.
**Why**: the biggest gap left with CSS, and the base of the transparent colors; the skins of `mask-image` carried most of it.
**Different from CSS**: on a group, the opacity multiplies into each object, which then show through each other; CSS fades a group as one picture. A closed object shows two surfaces, its front and its back. The light through a transparent object is GSS's own: CSS has no light.
**Accepted limits**: 6 surfaces along a ray at most; each surface is lit in full, which costs more on the transparent pixels; the reflections and the refractions show the transparent objects opaque.

## 117. Transparent colors and `opacity()` on objects

**Decision** (Lucas: the transparency of the objects, all of it like CSS; decision 116 was its first part): the color of an object can be transparent, and `filter: opacity()` goes on objects and groups. Both make the object transparent like `opacity` (decision 116), and multiply with it.
- **Colors**: `color` takes a transparent color, like `background` and `mask-image` (decisions 112, 113): `#ff000080`, `transparent`, an alpha after `/`, a `color-mix()` under 100%. `getMaterial()` takes the color without its alpha (`readSurfaceColor()`), and `surfaceAlpha()` multiplies its alpha (`readColorAlpha()`), which moves with the color in `@keyframes` and on `:hover`. A color set from JS stays opaque: its uniform has no alpha.
- **Gradients**: a gradient in `color` with transparent stops (`paintsTransparent()`) is read with its alpha (decision 112): its lines give a premultiplied `vec4`; `gradientColor()` gives its color without its alpha, and a new `paintAlpha(id, p)` its alpha at the point, which `surfaceAlpha()` multiplies. Its mean color (`gradientMean()`, for the reflections) reads a transparent stop by its color. `noise()` and `displace()` follow, being gradients.
- **`opacity()`**: a step of its own in `filter` (`kind: "opacity"`, 0 to 1 like CSS), which the passes skip and `objectAlpha()` multiplies, from the object and each of its groups. On the scene it is an error (`readSceneSteps()`): the scene stays opaque.
- **Still opaque**: the floor, the fog, the lights ("A light takes an opaque color"), the ambient light, and the colors written in a material ("A material takes an opaque color: the transparency of an object goes in color or opacity"); the error elsewhere is now "Only color, background and mask-image take a transparent color". `drop-shadow()` is not there yet.
- An animation that keeps an alpha at 1 is not a transparency: `objectAlpha()` checks every value first, since the animated value of a color that never changes its alpha is `mix(1.0, 1.0, …)` (it made four scenes transparent before this check). The 284 shaders of the scenes and registry examples are identical, byte for byte.
**Why**: CSS makes an element transparent by its color, its `opacity` and `filter: opacity()`; the three now do the same in GSS.
**Different from CSS**: a transparent color makes the whole object transparent, its lighting included (CSS: only what the color paints). `opacity()` on a group multiplies into each object, like `opacity` (decision 116). The colors of a material stay opaque (CSS has no materials).
**Accepted limits**: no `drop-shadow()`; a color set from JS has no alpha; the transparent stops of a gradient written in a material are an error.

## 120. The dpr of the docs and the playground: a menu over the render, auto follows the frame rate

**Decision**: in the playground and in the "Try it" of the docs, a menu at the top right of the render picks the dpr: `auto` (the default), or a number among 0.5, 1, 1.5 and 2 that the screen can show, and the screen's own ratio when it falls between. `auto` starts at the scene's ratio (`pixelRatio(dpr, screen)`, decision 67) and never goes above it. It follows the frame rate, measured over half a second: below 45 fps it drops at once to `ratio × √(fps / 55)` (the pixels cost the square of the ratio), rounded down by 0.25, never under 0.5 unless the scene asks for less; from 57 fps it climbs one step of 0.25 every 2 s. A ratio that was too slow is tried again 8 s later, then twice as late after each try that fails, up to 64 s. A new scene (or `@media` variant) forgets them, and its compile is not measured; neither is a hidden page nor the first frame after a pause (more than 250 ms). A number replaces the scene's `dpr`, never above the screen, like decision 67. The choice is kept in `localStorage` (`gss-dpr`) for the whole site; a choice this screen cannot show is `auto` here. `createDensity()` (`runtime/dpr.ts`) holds the logic, pure, tested with fake times; `createDprPicker()` (`runtime/dpr-picker.ts`) is the menu, a sibling of the canvas placed from its box each frame, like the scroll slider. `ViewOptions.dprPicker` turns both on, in the WebGL and the WebGPU view. The look follows DESIGN.md: signal outline and text, mono 11px, on the void at 60%, 22px high (32px on a touch screen). The `dpr` page of the docs has a note that says so.
**Why**: the docs and the playground run on every visitor's machine, and the dpr is the strongest lever on the GPU cost (decision 67): a heavy scene at 2 on a weak GPU falls to a few frames per second, where 1 keeps it fluid. Lowering at once and climbing slowly keeps a slow machine from stuttering, and the retry lets a hitch pass (a garbage collection, a resize) without keeping the render coarse for good. A number lets a viewer compare, or see sharper. CSS has no density a viewer chooses: nothing to follow.
**Accepted limits**: the frame rate is that of `requestAnimationFrame`, so a page busy elsewhere lowers the dpr as a slow GPU would. A ratio that is really too slow stutters for half a second at each retry. The profiler of the playground measures at the ratio `auto` picked: choose a number to compare. The showcase, the home page and `<gss-scene>` keep the scene's `dpr`: a page that embeds a scene gets no menu.

**Why**: Lucas asked for a review of every text and title of the docs: descriptions far too long (three paragraphs at most, spaced by elements, like an infographic or an example), "light" twice in the navigation, sentences out of the context of a reference ("As before", "not there yet", the Shadertoy export), code that read as plain text, and pages that the docs of a popular language would cut into chapters. Backticks keep the registry readable as plain text, and the autocompletion keeps a plain tooltip. The example names were anchors ("selector-has" three times) or the name of the page five times ("animation"): they are the headings of "On this page" and the names of the Examples menu of the playground.
**Accepted limits**: the code of the prose is not linked to its page yet. A few facts were left out of the reference as implementation details (`ease-in-out` computed as a smoothstep, the bounding sphere of an object a variable moves) or as playground details (what the Shadertoy export keeps). The chapters of a guide are trusted HTML, written by hand.

## 122. An image on the floor: a gradient, a `noise()` or a `displace()`

**Decision** (Lucas: the square of 40, of two options: 40 or 10): `floor` takes the images `color` takes, as well as a color and `none`: a gradient, a `noise()`, or one of them moved by `displace()` (`floor: noise(2 2, #10182b, #273d62 55%, #0b1020)`). A gradient covers a square of 40 units centered under the scene, the square of everything the scene draws (`MAX_DIST`, 20 units around the camera), seen from above like on a `plane` (`at = vec2(q.x, -q.z)`, its top away from the camera at rest); past it, it goes on with its first and last colors, like a gradient on an object. A `noise()` is read at the point of the floor, in the units of the scene, and a `displace()` moves by a share of the square, like on an object by a share of its box.
- **Reading** (`floorGradient()`, `codegen/gradients.ts`): an image is read by `readGradient()` with opaque colors, so a transparent stop is the error of always; a list of layers is an error that names `floor`, and so is any other value, instead of the error of `color` that Lucas met.
- **Drawing**: `gradientColor()` gets a branch for the floor, id 0, after the objects; `main()`, `trace()` and the shadows call it as soon as the floor or an object is painted. `getMaterial()` keeps the mean of its colors, like for an object (decision 82). A floor of one color keeps its shader: the 248 scenes and registry examples keep theirs, in GLSL and WGSL, byte for byte.
**Why**: the floor is the largest surface of most scenes, and Lucas wrote `floor: noise(…)` expecting it to work: the error spoke of `color`. Stone, a pool of light under the objects, stripes, marble: what `color` already paints on an object. 40 rather than 10: a `linear-gradient()` changes across all the floor that is seen, from the horizon to the camera, where a square of 10 would leave the floor plain past 5 units from the center; a spot under the scene is a `radial-gradient()` with a small percentage.
**Different from CSS**: CSS has no floor. A CSS gradient covers the box of its element; the floor has no box, so the square of 40 stands for it, with no `background-size` or `background-position` to change it.
**Accepted limits**: one image, no layers and no blend modes; no transparent colors (the floor cannot fade into the background through its alpha: `fog` or a gradient that ends with the color of the background does it); the floor is not animated, so its image only moves with the variables set from JavaScript; the square is fixed, so a pattern in percentages is sized by 40 units (`repeating-linear-gradient(#000 0% 1%, #fff 1% 2%)` gives stripes of 0.4 units); a `noise()` on the floor is the slice of a 3D noise at y = 0.

## 130. `lathe`: a contour, filled, then turned around the y axis

**Decision** (Lucas's choices: the axis at x = 0 of the contour, a filled contour only): `lathe` takes the contour of a `prism` (`d: polygon(…)` or `d: path(…)`, holes with the even-odd rule) and turns it around the vertical axis, where a `prism` pushes it along z. The author draws half the outline, right of the axis: x is the distance from the axis, y goes down like SVG and is flipped. The height is centered on the contours or on the `view-box` (only its y and height count); x is never moved, since x = 0 is the axis. A contour away from the axis turns into a ring.
- **How**: `latheFunction` (`path.ts`) brings the point into the half plane of the contour, `q = vec2(length(p.xz), p.y)`, and the 2D distance there is the 3D distance: the same `segment2()` and `crosses()` as a prism, shared by `fillBody()` (cut from `polygonFunction`; every shader of the scenes and registry examples stays the same). A side that lies on the axis is left out: once turned it is inside the solid, and a glass or transparent lathe would show it as a surface. `crosses()` counts toward +x, so it never met that side anyway. Bounded like a prism (`BOUNDED`): its sphere holds its widest point and its centered height.
- **Errors**: an x below 0 ("a lathe turns its contour around x = 0: every x must be 0 or more"), and a contour with no point right of the axis. A point a hair from the axis (a billionth of the contour's size), where a curve ends on it, counts as on it.
- **Curves**: a lathe cuts the curves of a `path()` 50 times finer than a prism (`size / 50000`, at most 64 segments per curve, the limit of `readSvgPath`): its whole surface is made of them, and the light showed each segment as a band, where a prism only has them on its walls.
- **The docs**: a page under Shapes and groups, `since: "0.0.5"`, whose first example turns the same contour into a prism and a lathe, both turned by 60deg, so a reader sees the difference; the `prism` page sends round objects to `lathe`. `d` and `view-box` apply to it.
**Why**: the round shapes of GSS (sphere, cylinder, cone, capsule, torus) have a fixed profile, and a prism is flat: a vase, a bottle, a bowl or a chess piece took a stack of blended shapes tuned by hand, never the profile that was drawn. Turning a contour is the other basic operation of 3D tools (Blender's Screw, Three.js's `LatheGeometry`, whose axis is also x = 0), and the word says what it does (decision 41).
**Accepted limits**: no `stroke-width` for a thin shell yet: a hollow bowl is a contour that goes up its outer wall and down its inner one. The box of `transform-origin` keywords and of a gradient is the bounding sphere's, like a prism. A curve of more than a quarter turn can still show faint bands under a sharp metal, at 64 segments.

## 131. `view: shaded | distance`: the isolines of the distance field, and chips to switch them

**Decision** (Lucas's choices: a property of the scene with chips over the render, the scene with isolines on a plane): `scene { view: distance; }` draws the scene as usual, then the isolines of the distance to the objects over it, the field the shader marches through. `shaded`, the default, draws the same shader as no `view` at all. DESIGN.md promised it ("the playground's `view: distance` toggle draws the scene's actual isolines", and its chips on the viewport).
- **What is drawn**: a line every 0.25 units from the objects, 0.34 of opacity for the first and 0.75 times less for each next one, like the rings of the GSS mark. They lie on the plane that faces the camera through `camera-target`, and show where that plane is in front of what the ray meets (`t`), the background included. The plane gives a pixel the same width everywhere (`depth / (1.5 × height)`), so the lines are one pixel wide without derivatives, which WGSL only allows in uniform control flow. The lines are light (bone) on a dark pixel and dark on a light one, by its luminance. They come after the filters of the scene (they are not part of the picture), before the passes of `blur()` and `bloom()`.
- **The field**: `map()` becomes `mapObjects()`, the objects alone, and `map()` adds the floor to them (`withObjectsAlone()`, `codegen/view.ts`); only in this view. The bounding tests of the objects then compare with `res.x`, not with the floor, or an object further than the floor would be missing from the field. Far from a `path`, a `prism` or a `lathe`, the field is the distance to its box, the shortcut of decisions 35 and 41: the lines show that box, which is the field the shader really uses.
- **The option**: `compileScene(source, { view })` replaces the view of the scene in the shader; `CompiledScene.view` stays what the code asks for (`"distance"`, absent for shaded). Every `@media` version takes the option.
- **The chips** (`src/playground/view-chips.ts`): `view: shaded` and `view: distance`, mono 11px, a line border, the active one in signal (DESIGN.md § 6), at the top left of the render of the playground and of Try it, on the row of the dpr menu; under it when the render is narrower than 360px, the panel of variables then under them. A chip calls `renderer.setView()` and `editor.refresh()`: the code compiles again in that view and is not touched. The choice holds while the code compiles again with the same view; when the code changes its `view`, the code wins again, and since there are two views the shader is already right. Nothing is kept in the browser. `mount()`, `mountAsync()` and `<gss-scene>` draw the view of the scene.
- **The docs**: a page `view` under Rendering, `since: "0.0.5"`, with a note on the chips, like `dpr` and its menu.
**Why**: the distance field is what GSS is, and the design's isoline motif is a real feature, not a decoration: the view shows what the shader measures, where an object's bound cheats, and why a ray takes many steps near a surface. A plane through the target shows the field around the objects the camera looks at; the true distance from the field at one point per pixel costs one more `map()`, only in this view. A property of the scene makes it a feature the reference describes and an embed can show (a teaching page); the chips let a reader look without editing, like the dpr menu.
**Different from CSS**: CSS has no such property. Its name and its keywords come from DESIGN.md.
**Accepted limits**: one plane, through the target: the field in front of or behind it is not shown. The lines are as wide as one pixel of the shader, half a CSS pixel at a dpr of 2. `blur()` and `bloom()` blur them. The chips follow the view of the scene without `@media`; a version of `@media` with another `view` is drawn as the code asks, while the chips show the first.

## 132. A tree of spheres around the objects, built by where they are

**Decision**: in `map()`, the objects that can be skipped (plain unions whose sphere of decision 76 is known) are grouped by where they are, whatever the groups of the GSS: a tree of spheres built at compile time (`grouped()` and `boundedMap()`, `codegen/bounds.ts`). Each group of the tree gets the test of decision 77, `if (length(p - C) - R <= nearest) { … }`, and the groups inside it their own tests. It replaces the tests on the groups of the GSS.
- **The cut**: of every way to cut a group in two along x, y or z (its objects sorted by their center), the one where the boxes around the two halves, their half-diagonal squared times their number of objects, cost the least (the surface-area heuristic of ray tracers); between equal cuts, the most even one. Down to fewer than 3 objects, which keep one line each. A big object then ends up alone rather than make a small group as big as itself. The boxes of the halves are built from both ends in one pass, so a scene of hundreds of copies still compiles at once.
- **When a group keeps its test**: inside its parent, a group's test passes about as often as its sphere covers its parent's, (r / R)²; it costs about one object, and saves its n objects when it fails. A group keeps its test when (r / R)² < 1 − 1/n: 16 keys that turn on the same ring have the sphere of their parent and lose theirs; 7 petals inside a bigger flower keep it.
- **The order**: between two operations that are not plain unions (a subtraction cuts what comes before it), the objects are free to move, since a union does not depend on the order: those whose sphere is not known first (always measured, they give the tests of the tree a near object to beat), then the tree. A run of fewer than 3 objects with a known sphere keeps its order.
- **The value of `map()`** is the same: a skipped object is never the nearest.
**Why**: decision 77 only grouped what the author grouped, and only `path`, `prism` and `lathe` had a test of their own: 80 cubes outside a group were 80 shapes at every step of every ray. The tree gives every scene the tests a careful author would write. Measured (bench, dpr 2, M4 Pro, the machine shared with other apps; three runs, one of them three alternating rounds on ten scenes): camera-cutaway 75 → 18–20 ms (−74 % to −76 %; −36 % against a faster run of `main`), grass 25.8 → 5.0–5.5 ms (−79 % to −81 %), ripple 18.6 → 7.6 ms (−58 %), noise-atmosphere 17.1 → 6.9 ms (−60 %), spiral −55 %, proximity −62 %, todal hovered −28 %; glass-circuit and soft-relic the same (their cost is in the glass, decision 133). The scenes under 3 ms move within the noise of the machine: logo-3d, whose `map()` did not change, measured 1.4 then 3.1 ms. Images: identical or stray pixels on 31 scenes; on astral-greenhouse, 16 touching pixels where two thin rings cross change by up to 39 levels, an exact tie between two distances that the new order breaks the other way, invisible at full size.
**Accepted limits**: the cut ignores the cost of each shape (a `path` costs more than a sphere) and an object that moves far gets a large sphere, as in decision 76. The groups of the GSS no longer guide the bounds: an author who grouped better than the tree could lose a little; none of the 32 scenes of the bench did beyond the noise. An exact tie between two objects can resolve the other way.

## 133. No mask of the objects a ray can meet: measured, set aside

**Decision**: `map()` does not skip the objects whose sphere a ray never comes near. The idea, tried on the branch `perf/ray-mask-experiment` (Lucas's request, Oct. 4): before each march, `aimRay()` tests the ray once against the tree of decision 132 and keeps one bit per object (31 to an int); `map()` skips an object whose bit is off, and a group whose objects are all off, before measuring how far they are; soft shadows aim a cone as wide as their penumbra, glass the ray inside the object, and `openRay()` turns every bit on for the normals.
**Why**: measured against the tree alone (bench, dpr 2, three alternating rounds): camera-cutaway −18 %, grass −13 %, noise-atmosphere −4 to −10 %, but glass-circuit +34 %, astral-greenhouse +20 %, starorbit +13 %, the others the same. Glass and reflections cast many short rays, and testing about 130 spheres per ray costs more than it saves. A second version, with the bit operators (taught to the WGSL lowering) and the mask on the rays from the camera only, one test per pixel, was worse still: glass-circuit +40 %, grass +70 %, noise-atmosphere +13 %. The test in front of every object, inside `map()`, costs about what skipping it saves: the tree already skips most objects with one distance per group. And the image changes: next to a skipped object the steps grow, so edge pixels and the far horizon move (grass, 693 pixels; watch, 318), where the tree changes nothing.
**Accepted limits**: a ray that passes close to many objects without touching them still takes small steps near each. Worth trying again only with a cheaper way to skip a whole group per ray (a list of groups per tile of the screen, computed once per frame).

## 134. Render on demand: a frame is drawn only when it can have changed

**Decision**: the render loop of both backends (`runtime/view.ts`, `runtime/webgpu.ts`) still runs at every animation frame, but draws only when what the frame shows can have changed (`runtime/demand.ts`). At each frame it gathers what the shader reads: the size of the canvas (and its CSS width, which the passes read), the time when the scene moves with it, the camera, how far each `:hover` and `:active` has glided, the timelines of `scroll()` and `view()`, the variables of `@property`, and how many images have arrived or element textures were drawn again. The same numbers as for the last frame drawn: nothing is drawn, the canvas keeps its frame and the GPU rests.
- **The time**: a scene moves with time alone when its shader, or a pass of its filters, reads `iTime` somewhere other than its declaration (`movesWithTime()`); then the time is part of the state and every frame is drawn, as before. `prefers-reduced-motion` stops the time: such a scene rests too.
- **The mouse**: a pointer that moves over a resting frame still sends the picking pass (one pixel), with the uniforms of the frame on screen; when the object under it changes, its transition changes the state, and frames are drawn while it glides. `picker.request()` now says whether it sent the pixel (not while the previous one is on its way), so a move is never lost.
- **The profiler**: while its panel is open, every frame is drawn (`FrameProbe.measuring()`), so it measures the scene, not the rest; a probe without `measuring()`, the bench's, always measures.
- A new scene, a new `@media` version or a new `view` draws its first frame (`demand.forget()`). The frame counter of the playground still counts the frames of the page.
**Why**: a still scene (the logo, spiral, llm, the zdog burger) and a scene that only reacts to the mouse drew 60 or 120 frames a second of the same image: the GPU worked, the fans turned and the battery ran down for nothing, on every page that embeds a scene. The CSS of a page does not repaint what did not change; a scene should not either. The image is the same: only frames identical to the one on screen are skipped.
**Accepted limits**: the loop still runs (a few numbers compared per frame, no GPU work); stopping it would need every source of change to wake it. A shader that reads the time without moving (a `steps()` animation between two keyframes) is drawn every frame, as before.

- **Animation keywords**: answered by decision 70 (delay, iteration count, direction, fill mode). Still open: `animation-play-state` and several animations on one object.

- **`@for` / `@each`**: are they worth adding, for what `* n` and `sibling-index()` cannot do (decision 52): a different shape at each step, or a list of values?
- **Gamma**: colors are lit as if they were linear and written without gamma correction, which gives hard shading. Correcting it would change the look of every scene.
- **Shadows**: objects cast no shadow, so they seem to float. A soft shadow costs one more march per pixel; should it be on by default, with `scene { shadows: none; }`?

## 141. An animation started by `:hover` or `:active`

**Decision**: `animation` (and its longhands) can go in a `:hover` or `:active` rule, with the syntax of CSS: `cube:active { animation: topple 0.8s ease-in forwards; }`. The state starts the animation, and the animation plays to its end.

- **The start**: the moment the state begins (the press, or the pointer arriving), not the load of the scene. The shader plays it from `iTime - uStart[k]`, a new uniform, `uniform float uStart[K]`, one float per state that starts an animation, in slot order; `CompiledScene.triggers` lists them (`slot`, `start`, `hold`). Written only when a state starts an animation: every other scene compiles exactly as before (shaders compared byte for byte on every scene and example). In WGSL, `start` comes last in the uniform struct, after `properties`, so no offset moves; Shadertoy shows the rest (`const float uStart[K]`).
- **Once**: an animation a state starts plays once unless it says how many times (a count or `infinite`), where an animation of the rest loops (decision 70): a button fires, it does not loop. `cube:active { animation: topple 0.8s forwards; }` topples once and stays.
- **The hold**: once started, the slot of the state stays at 1 until the animation ends (`delay + iterations × duration`), the button up or the pointer gone, and for good when the last frame stays (`forwards`, `both`, or an infinite animation). `runtime/triggers.ts`, between `pointerValues()` and the transitions, on both backends. A state that only changes properties holds nothing: nothing changes for it.
- **Again**: the next start of the state (a new press, the pointer coming back) restarts the animation from its first frame, like CSS when a class is taken off and put back. The cascade says which state writes its own animation (`starts.hover`, `starts.active`): the base animation of the object, or the `:hover` one under `:active`, keeps its own clock and is not started again.
- **The docs**: `:active` (an example, "a click starts an animation"), `:hover` and `animation` say it.

**Differences from CSS**: in CSS, an animation in a `:active` rule stops the moment the rule stops applying, at the release; GSS plays it to its end, and keeps the state on meanwhile. A pressed state is read as a trigger, not as a condition.

**Why**: the first thing asked of a click is "do this once": a lid that flips, a coin that drops, a sign that falls over. CSS has no way to say it; a transition with `linear()` can fake a short move, but not a choreography of several keyframes, and it comes back the moment the button goes up. Keeping the syntax of CSS, and writing the one difference down, costs the reader nothing: `animation` in a state rule reads as what it does. `@run <name>` was considered and left out: a new word that would have to repeat the duration, the easing and the fill mode `animation` already carries.

**Accepted limits**: one animation per state (the last `animation` wins, like CSS). A scene with a started animation reads `iTime`, so it draws every frame like an animated scene does, even at rest. A started animation along a timeline (`animation-timeline: scroll()`) follows the scroll, not the start.


## 142. A scene starts light, follows the computer, and stops when it is too heavy

**Decision**: readers wrote that the home page froze their browser (Oct. 6). They had a graphics card, a weak one: decision 137 does not stop a slow GPU, and the density that follows the frame rate (decision 120) only ran in the docs and the playground. The hero of the home page drew at its `dpr` of 1.5, full width, from its first frame. Now every view has the density of decision 120 (`createDensity()`, `runtime/dpr.ts`), with three changes:
- **It starts light.** `auto` draws its first frames at 0.5 (or the scene's ratio when it asks for less), then climbs by 0.5 at each measure of 200 ms where the frames keep up (57 fps), up to the scene's ratio: 0.5 → 1 → 1.5 → 2 in under a second on a GPU that keeps up. The first slow measure (under 45 fps) ends the start: from there, decision 120 as before (drops at once, one step of 0.25 every 2 s back up, retries). Choosing `auto` again in the menu starts light again; a new scene (or `@media` variant) keeps the ratio it had, so typing in the playground does not blur the render.
- **It is everywhere.** `mount()`, `mountAsync()`, `<gss-scene>`, the hero and the live demo of the home page, the showcase. `ViewOptions.adaptDpr: false` keeps the `dpr` as written and never stops, for what must draw at a known density: the bench, the films of `video/`, the GPU tests that compare pixels. The dpr menu (`dprPicker`) still picks the choice where it is.
- **Too heavy, it stops.** More than 1.5 s of frames under 5 fps, over at least two measures, at the lowest ratio (0.5 in `auto`, the chosen number otherwise), or a single measure of 3 s or more (one frame of seconds: the freeze itself): the view stops drawing and fires `gss-too-heavy` on its canvas. `play()` draws it anyway, and the view never stops on its own again. The embed's `observe()` takes it as a pause from the page, so coming back on screen does not wake it up. `<gss-scene>` shows its gate with "This scene is too heavy for this computer: drawing it could freeze the page." and the "Draw it anyway" button. The site (`renderGate()`, which was `softwareGate()`, `runtime/software-gate.ts`): the same notice over the canvas of the playground, the Try it of the docs, the live demo of the home page and the studies of the showcase; the hero of the home page leaves the SVG alone, as without a GPU. Without a GPU, the reader who clicked "Draw it anyway" already chose to wait: a too-heavy scene goes on.
- **What is not a slow frame**: the first frame after a new scene (it may wait for the compile of its shader: SwiftShader takes 20 s for the orrery, a GPU driver on Windows can take seconds), a hidden page (`visibilitychange`), the first frame after `play()`. The pause of decision 120 is no longer guessed from a gap of 250 ms: a frame of seconds is exactly what must be measured now.

**Why**: the density is the strongest lever on the cost (decision 67), and the first frame is the one that freezes: no measure can lower a ratio before a frame was drawn at it, so the first frames must be cheap. Starting at 0.5 costs a quarter of the pixels of 1, a sixteenth of 2; climbing by 0.5 at each fast measure keeps the blur under a second on a GPU that keeps up. A stop with a button, like decision 137, rather than a lower floor: under 0.5 a scene is no longer readable, and a page that freezes is worse than a scene that waits. The thresholds are far from a slow scene (5 fps, 1.5 s, two measures): a scene at 20 fps still draws, at 0.5.

**Accepted limits**: a GPU that keeps up still shows a coarser render for under a second at the start. The frame rate is that of `requestAnimationFrame`: a page busy elsewhere for 3 s at once stops a scene at its lowest ratio. A frame of seconds is drawn once before anything can know: the first frame at 0.5 on a GPU that cannot draw it still freezes the page for its length. `scripts/capture-showcase.mjs` photographs `<gss-scene>`, which now starts light: its images are to check before the next capture.

## 149. `shape-rendering: geometricPrecision` smooths silhouettes, opt-in, and costs GPU time for now

**Decision**: `scene { shape-rendering: auto | geometricPrecision; }`, taken from SVG. `auto`, the default, leaves the shader byte for byte as before (checked on every scene and registry example). `geometricPrecision` smooths silhouettes from the camera ray itself: the march keeps the last sample that passed closer than its pixel's width (`t * pixelSize`) without hitting, and only once the next step proves the ray moved away from it, or another surface became nearest; the floor (id 0) is never an edge. If the ray then misses, or hits a farther surface, that point is shaded and blended in by its coverage. The sphere of the scene is widened by one pixel in this mode only, so it cannot discard a grazing ray. GLSL and WGSL share the code. The registry page says, in a note, that the property makes the scene heavier to draw. Contributed by Michael Silva (#7, after issue #2).
**Differences from SVG**: in SVG `shape-rendering` is a property of each shape, inherited, with four values (`auto | optimizeSpeed | crispEdges | geometricPrecision`), and `auto` lets the browser smooth edges. Here it is a property of the scene, with two values, and `auto` keeps the sharp edges GSS has always drawn: smoothing by default would change the render of every existing scene and cost every scene.
**Why**: sharp edges are the first thing a new visitor notices (issue #2), and supersampling (4 times the pixels) was refused: antialiasing must not make a scene cost much more to draw. This is the cheapest correct technique found so far; it ships opt-in so a scene that needs smooth edges can have them now, and the cost is to be removed later rather than holding the feature back.
**Accepted limits**: it is not free yet, against the goal set in issue #2. Measured with `bench:compare`, `auto` against `geometricPrecision` at DPR 2: macropad +13 % GPU time (+15 % with `:hover`); the contributor measured +17 % (macropad) and +24 % (orrery) on an M1. Moving the shading into a function is free (+1 %, within noise); the cost is in the tracking inside the march loop or in the second shading of edge pixels, not yet separated. Only silhouettes are smoothed: not the edges of textures, shadows, reflections or the floor. `crispEdges` and `optimizeSpeed` are not accepted.

## 150. A WebGL2 scene links without blocking the page

**Decision**: the WebGL2 view asks for `KHR_parallel_shader_compile`. It still compiles the two shaders and checks `COMPILE_STATUS` at once, so a GLSL error throws from `show()` as before, before the scene on screen is touched. It then starts the link and asks `COMPLETION_STATUS_KHR` once a frame, and only then reads `LINK_STATUS` and the uniform locations, both of which would wait for the driver. Until the program is linked, the scene before it stays on screen. `show()` returns a promise that settles once the scene is on screen, rejected if the driver cannot link it; `mount()` and `createRenderer()` stay synchronous and send such a late error to the console. `<gss-scene>` without `backend` goes through `mountAsync(…, { backend: "webgl" })`, still WebGL2, so it keeps its poster and fires `load` only once the scene draws. A newer `show()` drops a program still linking. Without the extension, nothing changes.
**Why**: a visitor reported the home page freezing (Oct. 6). Decision 142 made a heavy scene cheap to draw, but the first frame after a compile is not measured, and the compile itself was not protected: on Windows, ANGLE turns the GLSL into HLSL and the Direct3D compiler, at link time, can take seconds on a large GSS shader, while the page waits on `LINK_STATUS`. The home page (hero and demo), the Try it of the docs and the `<gss-scene>` of the showcase all draw with WebGL2; WebGPU already compiled without blocking (`createRenderPipelineAsync`).
**Accepted limits**: not timed on Windows, where it matters: the tests play a slow driver in Chromium (the program reads "not ready" until the test says it is linked) and check that nothing waits for it. A tester on Windows confirmed the freeze gone from the preview of the branch (Oct. 8). A browser without the extension (Safari) still blocks during the link. A driver may still do part of the work at the first draw. A `@media` variant links the same way when the screen changes; the passes of `filter` still link at once, since they are small.

## 151. `@paint` and `texture: paint(name)`: a texture drawn by a fragment shader

**Decision** (Lucas, Oct. 8, issue #10, for 0.0.6): `@paint <name> { <GLSL> }` holds a standard WebGL fragment shader, and `texture: paint(<name>)` shows what it draws, like any image: on each face, with `texture-size` and `image-rendering`. Lucas's choices: the code inline in the at-rule (not a `.frag` file); standard WebGL shaders only (not Shadertoy's `mainImage`); a fixed 512 × 512 texture for now; custom properties as uniforms later.
- **Syntax.** The tokenizer reads the block after `@paint <name>` as one `GLSL` token, from its `{` to the `}` that closes it, counting braces outside the `//` and `/* */` comments of GLSL: a `// it's` in a shader would otherwise open a CSS string. The formatter writes the token as it is, and the highlighter of the docs and the playground, and the VS Code grammar, color it as GLSL. A `@paint` no object uses is left out, like an unused `@keyframes`; the last one of a name wins; `paint(waves)` without a `@paint waves` is an error where the object asks for it.
- **The shader.** GLSL ES 1.00 when it writes `gl_FragColor` (or `gl_FragData`), 3.00 otherwise; GSS adds `#version 300 es` and `precision highp float;` when the code has none, and a vertex shader of the same version (a buffer for the triangle: 1.00 has no `gl_VertexID`). GSS fills, by name and by declared type, `time` / `u_time` (the clock of the scene), `resolution` / `u_resolution` (512, 512), `mouse` / `u_mouse` (the pointer over the canvas, in the pixels of the texture, from the bottom left like `gl_FragCoord`; the last position stays when it leaves). The uniforms are read from the linked program, so one the compiler optimized away does not count.
- **Drawing.** Way B of the issue: each `@paint` is its own program drawing into its own texture (a framebuffer), before the scene samples it. Drawn once, again at every frame when the shader reads `time` (the scene then moves, decision 134), and when the pointer moves when it reads `mouse`. Several objects showing one `@paint` share its texture.
- **Errors.** The paints compile in `show()`, before the scene's program, so their GLSL errors throw at once (decision 150): `@paint fill, line 5: 'nope' : undeclared identifier`, the line in the `.gss` file, counted from the `{` of the block.
- **Backends.** WebGL2 only, like `element()` (decision 101): `mountAsync()` in `auto` and the playground at start pick WebGL2 for a scene with `paint()`; with WebGPU, the object keeps its color, the console says why, and the playground shows "paint() is drawn with WebGL2". GSS cannot turn arbitrary GLSL into WGSL without shipping a translator.
**Differences from CSS**: CSS `paint(name)` draws with a JavaScript worklet registered by `CSS.paintWorklet.addModule()`, on a 2D canvas, at the size of the box. In GSS the code is GLSL, written in the stylesheet itself, and draws a square of 512 pixels; `paint()` takes no arguments yet.
**Why**: textures gradients and `noise()` cannot express, and every shader written for the web pastes in. Drawing into a texture keeps the cost fixed per frame whatever the scene does, keeps the shader's names away from GSS's own, and reuses everything textures already do. Inline code keeps a scene one file, for the playground and its share links.
**Accepted limits**: not CSS: the docs say so in a note, and point to gradients and `noise()` first. The resolution is fixed at 512. No custom properties as uniforms yet. A heavy shader can make the scene too heavy, which then stops (decision 142). Shadertoy shaders need `mainImage` turned into `main()` by hand. In the playground, a scene that starts on WebGPU and then gets a `paint()` keeps its color until WebGL2 is chosen, as with `element()`.

## 152. copper, silver, brass and aluminum: metal() presets, like gold and chrome

**Decision** (Lucas's list for 0.0.6, Oct. 8): four more material keywords, each a `metal()` with its color and roughness: `copper` = `metal(#c8784a, 0.25)`, `silver` = `metal(#e3e4e6, 0.1)`, `brass` = `metal(#c9a24d, 0.2)`, `aluminum` = `metal(#c4c8cc, 0.35)`. Like `gold`, `silver` stays the CSS color `#c0c0c0` where a color is expected (`color: silver`), and is the metal in `material` (decision 58).
**Why**: the metals of everyday objects, easy to guess for a person or an LLM, at no cost: a keyword is the `metal()` it stands for.
**Accepted limits**: the colors are chosen by eye on the matte GSS lighting, not measured reflectances. `aluminium` (British spelling) is not accepted, like CSS keeps `color`, not `colour`.

## 153. `emissive()`: a surface that gives its own light

**Decision** (Lucas's list for 0.0.6, Oct. 8): `material: emissive([<color>,] [<strength>])`. The surface is lit like `matte()`, but never darker than its color times the strength: `col = max(col, m.color * m.density)`, the strength stored in the `density` field of `Material`, which no other use of this kind reads. The strength goes from 0 (the same as `matte()`) to 4, 1 by default, and can come from `@property` like the other settings. Without a color, `color` (like every material). A named color works as its first argument (`emissive(red, 2)`). Like the other materials, its GLSL is in the shader only when the scene uses it. The keyword `emissive`, for `emissive()` with the color of `color`, came with decision 156.
**Why**: lamps, screens and neons, and the natural partner of `bloom()`, which makes the bright parts glow. It costs one addition per pixel.
**Accepted limits**: it does not light the objects around it: GSS has no light from surfaces, only from the sun and the `light` elements; put a point light inside the object for that. In the reflections of a metal or glass, an emissive object looks matte (`trace()` lights what it hits with `diffuse()`). The canvas is 8 bits per channel: above 1, the channels that pass 1 clip, so a strength of 2 gives a lighter color rather than more light. Adding the glow on top of the light (the first version) clipped all three channels and turned an orange into a pale yellow: `max()` keeps the hue.

## 154. `pyramid`, `octahedron` and `tube`

**Decision** (Lucas's list for 0.0.6, Oct. 8): three shapes, centered on their origin like the others (decision 36), each with an exact distance function of Inigo Quilez's, written without assigning to a swizzle (`p.xz = …`), which the WGSL lowering does not take.
- `pyramid`: a square base, pointing up, sized by `size` like a cube: `size: <base width> <height> <base depth>`, one value for all three. The unit pyramid of the distance function is stretched to the size, scaled by the smaller side of the base: stretched, the distance is never more than the true one, so the march stays safe (exact when the base is square and the height follows it). Bounding sphere: the half-diagonal of its box.
- `octahedron`: `radius` from its center to each tip, 0.5 by default.
- `tube`: a hollow cylinder, open at both ends: `radius` (outer, 0.5), `height` (1), and `thickness` (the wall, 0.1), the property of the tube of a torus. The wall goes inside the radius, so the outer size does not change; a `thickness` above the `radius` is an error, and one set from JS is held at the radius. Not a `path`, which draws a tube along any line: the docs of `tube` say so.
Gradients and `transform-origin` read a pyramid like a cube, an octahedron like a sphere, and a tube like a cylinder.
**Why**: common shapes, cheap distance functions, from Lucas's list; `lathe` (decision 130) already covers vases and bottles.
**Accepted limits**: a pyramid has a square-based look: a rectangular base works, but its distance is only a lower bound, so the march takes a few more steps near it. No rounded edges on these three. `ellipsoid`, `hex-prism` and `text` wait.

## 155. `checker()` and `stripes()`: patterns, like `noise()`

**Decision** (Lucas's list for 0.0.6, Oct. 8, layer 1 of the texture shaders: named procedural textures, no GLSL): two image functions, wherever a gradient goes (`color`, a material's color, `background`, `floor`, the map of `displace()`), built on `noise()` (decision 111): a value at the point, 0 or 1, and the colors placed on it like the stops of a gradient.
- `checker(<scale> [at x y z], <color>, <color>)`: a grid of cubes of 1 / scale, the parity of `floor(x) + floor(y) + floor(z)`.
- `stripes(<scale> [x | y | z] [at x y z], <color>, <color>)`: bands along an axis, `y` by default, half of each color.
They read the point in the object's own space, like `noise()`: the cells keep their size whatever the shape, there is no seam, and they move and turn with the object; on the floor, the units of the scene; in the background, the direction of the view. Internally they are a `noise` with a `pattern` and an `axis`, so they animate (into another of the same function and axis), take numbers from JS, and work in `displace()`, with no code of their own for that.
**Changed from the plan**: the plan proposed triplanar `u`/`v`, like `texture`. In the object's space, like `noise()`, a pattern has no seams between the faces and works the same on a sphere; it is also what the other procedural image of GSS does.
**Differences from CSS**: CSS has no `checker()` or `stripes()`; a CSS checkerboard is a `repeating-conic-gradient()` tiled with `background-size`, and CSS stripes a `repeating-linear-gradient()`, which GSS has, seen from the front. These two are GSS functions, like `noise()`.
**Accepted limits**: sharp edges, so a fine pattern shimmers far away (no antialiasing: the derivatives are not available where the color is read).
**Fixed** (Oct. 9, Lucas: the checkered floor of the docs flickered): the floor is the plane y = 0, and a point hit on it lands a hair above or below, so `floor(y)` flipped between two cells from one pixel to the next. On the floor, `checker()` and `stripes()` read the point at y = 0 exactly; a `noise()` floor is read as before. `dots()` waits: a grid of dots cut in 3D shows no dot where a flat face passes between two rows, depending on the size of the object. `voronoi()` and `gradient-map()` wait too.

## 156. `iridescent()`: a thin film whose colors turn with the angle of view

**Decision** (Lucas's list for 0.0.6, Oct. 8): `material: iridescent([<color>,] [<strength>])`, and the keyword `iridescent`; `emissive` became a keyword too (decision 153), like `jelly` and `glass`. The light a thin film reflects interferes with itself, so its color depends on the angle it is seen at: `shadeIridescent()` stands for that with a cosine palette of `1 - dot(-rd, n)`, lit like `matte()`, mixed over the object's own lit color by the strength (0 to 1, 0.7 by default), more at grazing angles (from 35 % of the strength seen from the front to all of it at the edge), plus a highlight of the sun. The strength is stored in `density`, like `emissive()`.
**Why**: soap bubbles, oil on water, beetles, the back of a CD: a look that "creative coding" scenes ask for, at the cost of a few lines per pixel, only on the objects that use it.
**Accepted limits**: not a physical thin film (no film thickness or index to set): one palette, the same for every object, tinted by its color. Like the other materials, its reflections see matte objects.

## 157. `vignette()` and `chromatic-aberration()`: the effects of a lens, in `filter`

**Decision** (Lucas's list for 0.0.6, Oct. 8, "grow `filter` with a couple more post effects"): two functions of `filter`, on the scene only.
- `vignette(<amount>)`, 0 to 1, 0.5 by default (above 1 kept at 1, like the other amounts): a pixel filter, one line at the end of the scene's shader like `grain()`, no extra pass: `c *= 1 - amount * smoothstep(0.3, 1.0, distance from the center)`, the distance 1 at the corners.
- `chromatic-aberration(<length>)`, in px, 2px by default (0 does nothing): one pass, like `blur()`, that reads red further out and blue further in, by the length at the corners and 0 at the center, so a lens seems to bend each color its own way. CSS pixels, like `blur()` (`uRatio`).
On an object or a group, both are an error that says to put them on the scene: a lens sees the whole image.
**Differences from CSS**: CSS `filter` has neither; like `bloom()` and `grain()`, they are GSS functions, named for what they imitate.
**Why**: the two most asked "film" effects after bloom and grain, and cheap: a line, or one pass of three reads per pixel.
**Accepted limits**: the vignette is round on a wide canvas only in its distance, not its shape (an ellipse that follows the canvas). The aberration reads straight lines from the center: no blur of the split colors, as a real lens would add.

**Decision** (Lucas, Oct. 9: "under the title of the feature, or beside it, the number of the version that introduced it"): `since` is now required on every entry of the registry and of the guide, so `tsc` refuses a new property, function, shape, selector, at-rule or guide page without its version. ## 160. `display: none` and `visibility`

**Decision** (Lucas, Oct. 9, after Claude proposed `outline` and three smaller properties: "Fait tout"): two properties of objects, like CSS.
- `display: none | block`: `none` leaves the object out of the scene when it compiles, every object of a group with it, and turns a `light` off. It stays in the tree: `:nth-child()` and `sibling-index()` count it, like an element of the DOM. Set at compile time, it follows `@media`; it cannot change on `:hover` or in `@keyframes`.
- `visibility: visible | hidden | collapse`: a hidden object is not in `map()`, so it is not drawn, casts no shadow and cannot be pointed at, like CSS. Inherited, like CSS: an object without its own takes the one of its closest group, and can be `visible` in a hidden group. It changes on `:hover` and in `@keyframes`: visible is 1, hidden 0, and the object is in `map()` while the value is above 0, which is the discrete interpolation of CSS (visible for the whole way between the two). A hidden object that never changes is left out of `map()`; one that changes is wrapped in `if (v > 0.0)`, its value computed once per pixel in `animate()`. A group's own visibility is read at compile time.
**Why**: the two ways CSS hides an element, for `@media` (fewer objects on a phone), blinking lights, and objects shown by hovering another one. They cost nothing when unused: the shaders of every scene and registry example are the same.
**Differences from CSS**: `display` takes `none` and `block` only, and does not change on `:hover`. `collapse` is `hidden`, as outside tables in CSS.
**Accepted limits**: a hidden object cannot be hovered, like CSS, so `cube:hover { visibility: hidden; }` flickers, like CSS. The bounding spheres still count a hidden object: no time saved by hiding.

## 161. `cursor`

**Decision** (Lucas, Oct. 9, the same list): `cursor: <keyword>` on objects, the keywords of CSS (`pointer`, `grab`, `grabbing`, `help`, `crosshair`, `zoom-in`…; no `url()`). The compiler gives the runtime `cursors`: for each object whose cursor is not `auto`, its cursor hovered and pressed (`:active`). The runtime already reads the id under the pointer for `:hover` (decision 62); it now does so when the scene has cursors, and sets `canvas.style.cursor` from `cursorAt()`: the cursor of `:active` when the object under the pointer is the pressed one, its hovered cursor otherwise, and `""` (the page's own) over nothing or `auto`. A shader with cursors and no `:hover` declares the picking uniforms and `uHover[1]`, whose slot the WebGPU buffer always keeps. Like CSS, it is inherited from the groups, and `:hover` and `:active` rules can set it without being animatable, like `transition`.
**Why**: a scene with `:active` is a button; the cursor says so. It reuses the picking pass, with no new GPU work.
**Accepted limits**: the cursor follows the picking pass, one or two frames late, like `:hover`. Over the floor and the background, the page's cursor. The runtime budget of the npm package went from 14,000 to 14,500 bytes gzipped (13,912 → 14,251 with this and decision 162).

## 162. `animation-range`

**Decision** (Lucas, Oct. 9, the same list; a "later" of decision 96): `animation-range`, `animation-range-start` and `animation-range-end`, like CSS: `normal`, the named ranges of `view()` (`cover`, `contain`, `entry`, `exit`, `entry-crossing`, `exit-crossing`) with an optional percentage, a percentage or pixels alone (of the whole timeline). A name alone is the whole of that range (`animation-range: entry`); as an end, its 100 % (`contain exit`). The range joins the timeline it applies to: a timeline with another range is another component of `uTimeline`, and the runtime sends its progress inside the range (`rangeProgress()`), from the sizes of the scene and of its scroll container. The shader does not change: a scene without a range compiles as before. The longhands win over the shorthand wherever they are written, like the longhands of `animation` in GSS (decision 70). The slider of the playground stands in for the place along the whole timeline, and the range is read from it.
**Why**: "start when the scene is half in view, finish when it is all in" is the common case of scroll-driven animations, and the one `view()` alone cannot say.
**Differences from CSS**: a range on an animation that plays in time is an error, where CSS ignores it. The named ranges are refused on `scroll()`, where CSS has none to give. Outside the range the animation holds its first or last frame, as GSS already did before and after a timeline.
**Accepted limits**: `calc()` mixing a percentage and pixels is not read. Up to 4 different timelines a scene, ranges included.

## 163. `outline`, in the units of the scene

**Decision** (Lucas, Oct. 9: "le contour, pas en pixel"): `outline` and its longhands `outline-width`, `outline-style`, `outline-color`, `outline-offset`, like CSS, with the width and the offset in the units of the scene. Like CSS, a style is needed (`none` by default: `outline: 0.05 red` draws nothing); `solid` and `auto` draw a plain line; the other styles of CSS are an error. `thin`, `medium` and `thick` are 0.01, 0.02 and 0.04. The color is the object's own `color` by default, like `currentColor` (a gradient gives its mean). The longhands win over the shorthand, like the other longhands of GSS. Width, color and offset change on `:hover` and in `@keyframes`; the style on `:hover` and `:active` only.
How it is drawn: `map()` measures each outlined object once (`float dOutline`), and `outlineAt()` keeps the outlined object the point is closest to, in widths of its line past its offset: `m = (d - offset) / width`, in the line between 0 and 1. In the primary march, a sample whose `m` grows again, or whose closest outlined object changes, is a closest point the ray passed; the first one in a line is kept (`lineT`, `lineId`), as `geometricPrecision` keeps its edges (decision 149). `main()` paints the line's color there, flat, when the ray hit another object (or nothing), or hit the same object more than two reaches further (the hole of a torus); the fog covers it at its own distance. An outlined object's bounding spheres, and the sphere of the scene, grow by its reach (offset plus width) when it is known at compile time; otherwise the object is not bounded. Only the march of the primary ray tracks lines: reflections and shadows do not see them.
**Why**: a drawn, "toon" look, and an outline to show what is hovered, both common in CSS. In units, a line belongs to the object: it gets thinner far away, like the object, and costs a division and a test per outlined object per step of `map()`, which measured the same as without it (about 1 ms at 800 × 600).
**Differences from CSS**: the width and the offset are in units, not pixels, and a line far away can be thinner than a pixel and break up. CSS draws around the border box; GSS around the silhouette seen by the eye. The styles came the same day (decision 164).
**Accepted limits**: the line is found where the ray passes close to the object: where another object comes closer than the outlined one at that moment, the line can stop short (two outlined objects touching share one line at their junction). A line on an object that a nearer object hides is hidden too, like the rest. No antialiasing of the line, even with `geometricPrecision`. Not in the reflections.

## 164. The styles of `outline-style`

**Decision** (Lucas, Oct. 9, on staging: "none, solid, auto is pointless; and what does auto do?"): every style of CSS `outline-style`: `none`, `auto`, `solid`, `dashed`, `dotted`, `double`, `groove`, `ridge`, `inset`, `outset`. `auto` is, in CSS, the browser's own line (the ring of a focused field); GSS has no look of its own, so it draws `solid`, and the docs say so. The march keeps how far across its line the ray passed (`lineM`), and `main()` draws:
- `dashed`: dashes three widths long, gaps as long; `dotted`: round dots one width wide, one width apart. Both are placed by the angle around the object seen from the camera (`atan` of the line's point around its center, on the camera's right and up), and as many as fit around its size, rounded, so they close without a broken one. The center is the object's `translate` (animated too) when it is not in a group, the center of its bounding sphere otherwise; the size, its shape's bounding radius times its scale.
- `double`: the outer and the inner thirds of the line.
- `inset`, `outset`, `groove`, `ridge`: the line at half its color on one side, the light coming from the top left of the screen like the borders of CSS; `groove` and `ridge` split the line in two halves, like CSS.
The style is the one at rest, or the one of `:hover`, then `:active`, when the object has none at rest. A scene whose outlines are all `solid` or `auto` has none of this code.
**Why**: the styles are what makes `outline` more than a line, and CSS has them all.
**Differences from CSS**: CSS draws dashes along the border box, from its corners; GSS around the silhouette, by angle, so dashes are longer where the silhouette is further from the center (the corners of a cube). The shaded styles use half the color for their dark side, where browsers each pick their own.
The compiler of the package grew past its budget: `mount` goes from 97,000 to 98,000 bytes gzipped (97,114), `embed` from 99,000 to 100,000 (99,013).
**Accepted limits**: the style does not glide: between rest and `:hover`, the line keeps the style that is drawn. An object in a moving group places its dashes around the center its bounding sphere had: they slide as it moves.

## 165. In the playground and Try it, `@media` reads the size of the render

**Decision** (Lucas, Oct. 9, after narrowing the render of the playground and seeing `@media (max-width: 900px)` do nothing: "it should work in the playground too, without needing `@container`"): the playground and every Try it read the queries of `@media` in the render, like the result of CodePen, which is its own window. The view takes `viewport`, a function of the canvas that says where the queries are read; `elementMedia` reads them in an empty, hidden `iframe` kept at the size of the canvas by a `ResizeObserver` (`elementMedia()`, `runtime/media.ts`): its `matchMedia` answers every feature of `@media` (width, height, aspect-ratio, orientation) for that size, and the preferences of the system as the page does, and its `change` events switch the version of the scene when the render is resized, like a window. A page (`mount()`, `<gss-scene>`) keeps the window, like CSS, by default, and the shaders do not change. A function rather than a keyword, so the runtime of the package, which only pages use, does not ship `elementMedia`.
**Why**: in the playground, the render is what the author sizes, and what a narrow screen looks like: a scene with `@media` must be testable there without resizing the browser.
**Accepted limits**: one more `iframe` per view in the playground and the docs. `@container`, for a scene on a page that follows its column rather than the window, waits.

## 166. A material's own color wins over a gradient in `color`

**Decision** (Lucas, Oct. 9, a bug: `silver` and `brass` on a striped object looked the same; his choice, the rule for every material rather than for the named metals only): a material with a color of its own keeps it when `color` is a gradient, a `noise()`, a `checker()`, a `stripes()` or a `displace()`, as it already did over a plain color. Its own color is a hex or a color set from JS as its first argument (`metal(#3a7bff, 0.3)`, `glass(#74a8ff)`), or a keyword that stands for one: `gold`, `chrome`, `copper`, `silver`, `brass`, `aluminum`, `ice`. `objectGradient()` asks `hasOwnColor()` (`materials.ts`, the same first arguments as `readMaterial()`): such an object is not painted, and `gradientColor()` has no branch for it. `matte()`, `metal(0.2)`, `jelly`, `glass`, `emissive` and `iridescent` still take the gradient, and so does a gradient as the first argument of the material (decision 82). The transparent stops of the gradient still show (`paintAlpha()`, decision 117), as the alpha of a plain color makes `gold` transparent: such an object keeps its gradient for its alpha only (`alphaOnly`). `readMaterial()` now takes the color as a function, read only by a material without its own, so a gradient that an animation or `:hover` changes is never read as a plain color.
**Why**: the rule of `currentColor` in CSS, already the one of GSS for a plain color: a color written in the material wins. `brass` is `metal(#c9a24d, 0.2)` (decision 152): fixing the keywords only would make the two differ. The bug was there since gradients on objects (decision 82, v0.0.2), for `gold` and `chrome` too: not a regression.
**Changed scenes**: two examples of the playground wrote `glass(#hex, …)` with a `displace()` in `color`, and showed the gradient: `noise-atmosphere` (`#lake`) and `mask-displacement` (`#outer`). Their `glass()` lost its hex, so they draw what they drew: their shaders differ only by the mean color in `getMaterial()`, which the gradient replaces before any shading. Every other scene and registry example compiles to the same shader.

## 167. The end of an animation is its last keyframe, exactly

**Decision** (Lucas, Oct. 9, reporting that an animation with `both` ending on `visibility: hidden` right after a `visible` keyframe left the object visible): where an animation stops, the shader gives its keyframe exactly, like CSS, where floats stopped short of it.
- The last segment of an animation whose progress can stay on 1 (a count of iterations, a scroll or view timeline, a first iteration played backwards during a delay that holds it) is measured from the end: `1.0 - (1.0 - p) / length`, which is exactly 1 when `p` is 1. `(p - 0.99) / 0.01` gave 0.9999991 there. A loop never stays on 1, and a last segment that is the whole animation (`(p - 0.0) / 1.0`) was already exact: their shaders do not change.
- `cubicBezier()` returns its ends as they are, 0 at 0 and 1 at 1: its bisection stopped 2⁻¹⁷ short of them, so a segment that had not started weighed about 2 × 10⁻⁶ with `ease`, not 0.
- The start of the first segment, where a reversed animation ends, was already exact. A `transition` of `:hover` ends on exactly 0 or 1 (`uHover`): nothing to change there.
**Why**: `visibility` (decision 160) keeps an object in `map()` while its value is above 0, so any weight short of its end shows it: a last keyframe `hidden` after a `visible` one, held by `forwards` or `both`, left the object visible; with `ease` and the others of `cubic-bezier()`, a segment from `hidden` to `visible` showed the object before it started, for the whole of the hidden keyframes before it, and a reversed animation ending on `hidden` did too. `steps()` and `step-end` take the floor of the same number: an animation whose last segment started at 80% or 99% stopped on the step before the last one, for any property.
**Accepted limits**: 12 shaders of the scenes and examples change (the fall of the Mistral 4, the examples with `cubic-bezier()`), their values by a millionth of a step or less. Only the ends a progress can stay on are exact: a keyframe between two others is only passed through.

## 168. A canvas inside `element()`, captured as it draws

**Decision** (Lucas, Oct. 9, after a playground test: a WebGL canvas inside the element, live on the cube): the docs say a `<canvas>` inside the element is captured with it, and a second `element()` example shows one — a one-line WebGL shader on the front face. Nothing changes in the runtime: the element is already drawn again at each paint of the scene (decision 101), so the example's scene animates, and every paint catches the canvas's newest frame. In the example's HTML, the script rides an `<img onerror>` attribute, because the playground and the docs insert the HTML with `innerHTML`, which runs no `<script>`; in a page, a plain `<script>` does the same. Its WebGL context takes `preserveDrawingBuffer: true`, so the buffer still holds the frame when the browser reads it.
**Why**: `element()` already covers live content — a canvas is the clearest proof, and a shader inside a shader makes the point of the language.
**Accepted limits**: a still scene keeps the canvas's last captured frame: nothing watches the canvas itself. The capture still needs HTML-in-Canvas (the note of `element()`).

## 171. The studies of the showcase wait for play

## 172. The archive of the showcase: every scene, its version and what it uses

**Decision** (Lucas, Oct. 9: the small demos at the bottom of the showcase become an archive, as a grid or a list, with a thumbnail, the name, what the scene is, the features of GSS it uses, and a badge of the version it arrived with; his choices: the features read from the code, the studies in the archive too): the inspiration grid becomes the **Archive**, section 06 (`#archive`). It holds every scene of the page: the 30 of the grid (the six use cases among them) and the 8 studies, each once.
- **What each scene says**: its capture, its name and a sentence or two on what it is (`name`, `description` in `content.ts`; a study takes its title and its description), the version of GSS it arrived with, and the features it uses.
- **The version** (`since`): the first tag that holds the commit that added the scene to the page, written in `content.ts` (a clone of the site may not have the history). A scene keeps its version when it is changed later. The scenes of the newest version that is out have their badge in `signal`, like the "new" of the docs; the others are outlined, like "since" beside a title of the docs. The archive is sorted newest first, and keeps the order of the lists within a version.

- **Grid or list**: a segmented control (`DESIGN.md`) above the archive; the grid is three columns of cards, the list a row per scene with a small capture. The choice is kept in `localStorage` for the next visit; without storage, the grid.

**Why**: the grid only had a capture and a title, some of them wrong ("with a glass ball and a crown" on four scenes that have none). An archive tells what each scene shows, when GSS could first do it, and where to read about what it uses.
**Accepted limits**: a feature outside the list does not show, and the list is a judgment, written once in `features.ts`. The studies are in the archive and in the viewer. Links to `showcase#inspiration` now land at the top of the page.

## 178. The docs on GitHub, generated from the reference

**Decision** (Lucas, Oct. 10: a reader who lands on the repository should be able to start with GSS without going to the site; his choice among a short guide written by hand, the docs generated from the site, or the wiki of GitHub: generated): `docs/` holds the reference of the site as Markdown, one page per section of its contents (`getting-started.md`, `installation.md`, `selectors.md`…), and an index, `docs/README.md`, the page GitHub shows for the folder: each section by category, with the names of its entries. `src/docs/github-docs.ts` builds them from the HTML of the site (`renderDocs()`), converted by `articleToMarkdown()`, the converter of "copy page", so the guide and every entry of the registry come out as they read on the site.
- **What changes for GitHub**: each entry is a `##` title under the title of its page, after an `<a name>` with the anchor of the site (`#at-scene`, `#selector-class`), so a link of the site becomes a link between the pages (`textures.md#fn-paint`); an anchor the pages do not have goes to the site. "Try it" is left out: a line under each title sends to the same section of the site, where the examples run. GSS is shown as `css`, which GitHub colours; the snippets of the three ways to embed a scene, coloured as GSS on the site, in their own language. The examples are formatted, as the site shows them. A callout of the site is a `[!NOTE]` of GitHub.
- **Kept in sync**: `github-docs.test.ts` compares each page with its file (`toMatchFileSnapshot`) and fails on a page the reference no longer has; `npm run docs:github` writes them again. It also checks that every link between the pages lands on an anchor, and that the pages, like the README, never mention how GSS is made.
- **The README** sends to them: a "Documentation" section (Getting started, Installation, every page), and each line of "What it can do" links to its page. Absolute links to `main`, so they also work on npm.
**Why**: a second copy written by hand would drift from the site at each version; the registry is already the one source of the reference, the playground and the autocompletion. The wiki is not versioned with the code, nor reviewed in a pull request.
**Accepted limits**: every change to the registry or the guide now asks for `npm run docs:github` (the test says so). The pages describe the branch they are on: on `main`, the published version. No live example on GitHub; the values of an entry are a list, not the table of the site, and a link in the table of "Embedding a scene" is lost (the converter reads the name of a row as text).
